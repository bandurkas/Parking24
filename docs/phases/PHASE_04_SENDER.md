# Ф4, шаг 0. Отправщик сообщений и предохранители

Дорожка Д3, первая фаза. Код на `19cc5f2`. Источники решений: `docs/TZ_2026-09-21_PLAN.md` §1 (включая «Решения пользователя 23.09»), `docs/TZ_STATUS_2026-09-22_night.md` §3 «Ф4» и §4, `docs/TZ_2026-09-21_SOURCE.md` §2, `docs/MESSAGE_TEMPLATES_2026-09-22.md`, `docs/phases/PHASE_01_SCHEDULER.md` §5 (контракт скана), `docs/WAZZUP_INTEGRATION.md` §2 (чтобы адаптер подошёл Wazzup без переделки).

## 1. Зачем

Сейчас сообщения клиенту копятся в `Outbox` и не уходят никуда: отправщика в системе нет вообще, а тик планировщика из Ф1 умеет только писать пульс. Шаг 0 строит всё, что можно построить без токена бота: сам отправщик в тике, интерфейс адаптера канала (чтобы Telegram и Wazzup потом подключались как модули), предохранители против рассылки старого и неутверждённого живым людям, честные статусы очереди в карточке брони и клиента.

Отдельная и главная причина делать это до бота: на stage висят 5 неотправленных сообщений за 08–21.09 и активны два правила со скидкой 10 % (`before_checkout_2d`, `after_checkout_7d`), которых заказчик не утверждал. Первый же работающий отправщик без предохранителей разошлёт это реальным людям. Поэтому предохранители пишутся **раньше** любого канала, а на stage фаза выкатывается с отправщиком в положении «выключено».

## 2. Что входит и что не входит

**Входит:**

1. `src/server/automations/sender.ts` — проход отправщика: аренда записей, предохранители, вызов адаптера, разбор результата, повторы, счётчики.
2. `src/server/automations/sender-core.ts` — чистые правила (выбор канала, решение «отправлять / пропустить / повторить», пауза перед повтором, план прохода). Без базы, под юнит-тесты — как `tick-core.ts` в Ф1.
3. `src/server/automations/adapters/index.ts` — тип `ChannelAdapter` и реестр адаптеров, **пустой** в шаге 0 (как `SCANS = []` в Ф1). Плюс поддельный адаптер для локальных тестов под переменной окружения, недоступный в production-сборке.
4. Встраивание отправщика в минутный тик отдельным «шагом» (не сканом): `tick-core.ts` получает необязательный список `steps`, `scheduler.ts` — реестр `STEPS`.
5. Предохранители: выключатель с режимом «пробно», порог по возрасту сообщения, список разрешённых номеров, «не беспокоить», потолки «за тик» и «за час», не больше одного сообщения одному клиенту за проход, бюджет времени на проход, лимит попыток с нарастающей паузой, самоотключение после серии ошибок.
6. Две добавляющие миграции: поля аренды и повторов у `Outbox` плюс индекс; новые значения `OutboxStatus` (`EXPIRED`, `SKIPPED`) и `NoticeKind` (`MESSAGE_FAILED`).
7. Выбор канала — одно правило в одном месте (`channelForClient`), его используют `enqueue`, отправщик и карточка клиента (перенос канала у неотправленных при смене мессенджера).
8. Карточка «Отправка сообщений» в настройках владельца: режим, список разрешённых номеров, порог по возрасту, счётчики за сутки, кнопка «Убрать устаревшие из очереди».
9. Честный статус очереди в карточке брони и клиента: русские подписи всех статусов, время по Москве, причина и число попыток (строка `bookings/[id]/page.tsx:198-208` целиком — по §4 её делает Ф4).
10. Уборка перед первой отправкой: `before_checkout_2d` и `after_checkout_7d` создаются и держатся **выключенными** в seed; старые PENDING на stage убираются кнопкой.
11. Строгая проверка «ЧЧ:ММ» одним помощником (§4: «строгое время — одним помощником в шаге 0 Ф4, он раньше; Ф3 доделывает поверх»).
12. Громкий сбой seed в `docker/entrypoint.sh`.

**Не входит (граница с соседями, по §4 сверки):**

## 3. Как это работает

```
минутный тик (Ф1)
  ├─ сканы (в шаге 0 их нет; Ф2б и Ф7 добавляют свои)
  └─ ШАГИ: sender            ← новое, выполняется ВНЕ транзакции скана
        режим из Setting "scheduler.scans" → { "sender": "off" | "dry" | "on" }
        "off"  → шаг не запускается вовсе
        пауза планировщика → шаги тоже не запускаются

проход отправщика (runSenderPass)
  1. читает настройки sender.* своим клиентом базы (клиент планировщика, не основной)
  2. потолок за час: SENT за последние 60 мин ≥ sender.maxPerHour → проход пустой, одна строка в лог
  3. КОРОТКАЯ транзакция (10 с):
        UPDATE "Outbox" SET claimedAt = now, attempts = attempts + 1
        WHERE id IN (SELECT id … status='PENDING' AND scheduledAt ≤ now
                     AND (nextAttemptAt IS NULL OR nextAttemptAt ≤ now)
                     AND (claimedAt IS NULL OR claimedAt < now − аренда)
                     ORDER BY scheduledAt LIMIT N FOR UPDATE SKIP LOCKED)
        RETURNING …
     → по каждой записи решение decide() (чистая функция):
        устарело / нет получателя / «не беспокоить» / номер не в списке /
        канал не выбран / нет адаптера / текст длиннее лимита канала  → терминальный статус тут же
        остальные остаются «в работе» (claimedAt проставлен)
     режим "dry" → в конце транзакции откат: в базе не меняется ничего,
                   число «ушло бы» попадает в пульс тика (dry.sender)
  4. ВНЕ транзакции, по одной, по порядку scheduledAt:
        adapter.send(сообщение, получатель, таймаут 10 с)
        ok            → SENT + sentAt + запись в ленту брони (userId = null)
        ошибка, можно повторить, попыток меньше лимита
                      → PENDING + nextAttemptAt = now + пауза (1 → 5 → 25 мин)
        иначе         → FAILED + причина + уведомление администратору MESSAGE_FAILED
        бюджет прохода (30 с) исчерпан → оставшиеся арендованные освобождаются
  5. ошибок в проходе ≥ sender.stopAfterFails (накопительно, счётчик в Setting)
        → режим переводится в "off", уведомление CHANNEL_DOWN, счётчик обнуляется
```

Ключевая мысль: **в транзакции нет ни одного внешнего вызова** — это прямое требование контракта из Ф1 §5. Транзакция только выбирает и арендует; сеть живёт снаружи; повторная отправка предотвращается арендой, ключом идемпотентности и счётчиком попыток.

## 4. Решения

1. **Отправщик — «шаг» тика, а не скан.** Выбрано: новый необязательный массив `steps` в `TickDeps`, выполняется после сканов и до пульса, режим берётся из той же карты `scheduler.scans` по коду `sender`. Почему: контракт скана из Ф1 прямо запрещает внешние вызовы внутри транзакции скана и заранее называет отправку «отдельным шагом вне транзакции». Отвергли: (а) сделать отправщик обычным сканом — сеть под блокировкой, дубли при откате, долгая блокировка; (б) завести отдельный таймер — второй источник расписания, вторая пауза, вторая точка отказа.

2. **Выключатель — та же карта режимов, что у сканов, ключ `sender`.** Почему: одно место для всех переключателей тика, «пробно» уже означает «выполнить и откатить», пульс уже печатает `done` и `dry` по коду, а будущий экран режимов сканов (Ф2б) получит отправщик бесплатно. Отвергли отдельный ключ `sender.mode`: два механизма для одной вещи, два экрана, два действия на запись.

3. **«Пробно» = проход с откатом транзакции.** Почему: совпадает с уже принятым смыслом «пробно» в Ф1, адаптеры при этом не вызываются вовсе, в базе не остаётся ничего, в пульсе видно число «ушло бы». Отвергли «пробно = пишем решение в запись, но не отправляем»: пришлось бы заводить поле «решение принято в пробном режиме», иначе каждую минуту одно и то же попадало бы в журнал.

4. **Аренда записи полями, а не новым статусом.** Выбрано: `Outbox.claimedAt` + `Outbox.nextAttemptAt`, аренда 5 минут. Почему: добавляющие необязательные поля дешевле, чем статус `SENDING`, который пришлось бы вводить отдельной миграцией и учитывать во всех выборках и подписях; упавший процесс сам отпускает запись по истечении аренды. `attempts` увеличивается **в момент аренды**, чтобы упавшая отправка не крутилась вечно. Отвергли `SELECT … FOR UPDATE` на всё время отправки: блокировка строки держалась бы на время сетевого вызова.

5. **`nextAttemptAt` отдельно от `scheduledAt`.** Почему: `scheduledAt` — «к какому моменту относится сообщение», от него считается возраст и по нему показывается «запланировано» в карточке; сдвигать его при повторе значит врать человеку и ломать порог по возрасту. Отвергли повторное использование `scheduledAt` как времени следующей попытки.

6. **Порядок предохранителей фиксирован и проверяется по возрастанию цены ошибки:** возраст → пустой текст → нет получателя → «не беспокоить» → номер не в списке разрешённых → канал не выбран → нет адаптера → текст длиннее лимита канала. Почему список разрешённых стоит **выше** проверки адаптера: на stage в шаге 0 адаптеров нет, и человеку важнее увидеть «номер не в списке разрешённых» (режим теста работает), чем «канал не подключён».

7. **Пропуски терминальны, повторяются только сетевые сбои.** Почему: сообщение, которое нельзя отправить по правилу, не должно висеть в очереди с подписью «запланировано» и однажды уйти. В карточке видна причина, администратор звонит. Отвергли «оставлять PENDING до истечения возраста»: очередь растёт, статус врёт, а результат тот же — через N часов «устарело».

8. **Порог по возрасту считается от `scheduledAt` и по умолчанию 6 часов.** Почему: простой сервера дольше 6 часов у нас не случался, а подтверждение брони, пришедшее назавтра, вредит сильнее, чем неприход сообщения. Значение — настройка, меняется без выкатки. Отвергли разный порог по типам сообщений: правило усложняется, а типов пока четыре; когда Д4 заведёт все тексты, порог можно будет уточнить по правилу.

9. **Список разрешённых номеров включён по умолчанию и пуст.** То есть до того, как владелец впишет туда номер, не уйдёт ни одно сообщение, даже при режиме «включено». Почему: предохранитель должен быть безопасен в состоянии «никто ничего не настроил». Отвергли «пустой список = слать всем»: ровно та авария, ради которой фаза и делается.

10. **Два потолка частоты: за тик (10) и за час (30).** Почему: тик минутный, значит «за тик» — это и есть ограничение частоты, а «за час» ловит редкий, но опасный случай — массовое изменение статусов или откат данных, когда за минуту встают в очередь сотни записей. Плюс «не больше одного сообщения одному клиенту за проход»: человек не получает подряд три сообщения.

11. **Бюджет прохода 30 секунд, отправка последовательная.** Почему: 10 отправок по таймауту 10 с не должны переехать границу минутного тика; последовательность сохраняет порядок сообщений и щадит провайдера. Не арендованное и не отправленное освобождается в конце прохода одним запросом.

12. **Повторы: не больше 3 попыток, паузы 1 → 5 → 25 минут.** Почему: перекрывает короткий сбой сети и перезапуск провайдера, но не превращается в суточный долбёж. После исчерпания — `FAILED` и уведомление администратору «сообщение клиенту не доставлено, позвоните».

13. **Самоотключение.** Накопительный счётчик ошибок в `Setting` (`sender.failStreak`), сбрасывается на первой удачной отправке; при достижении `sender.stopAfterFails` (5) режим переводится в `off` и создаётся уведомление `CHANNEL_DOWN`. Почему в базе, а не в памяти: модуль планировщика в одном процессе загружается дважды (решение 7 Ф1), состояние в памяти было бы двойным. Отвергли счётчик «подряд внутри одного прохода»: при трёх ошибках за тик он не сработает никогда.

14. **Интерфейс адаптера рассчитан на Wazzup и Telegram сразу.** `send` получает всю запись (её `id` идёт провайдеру как ключ идемпотентности — у Wazzup это `crmMessageId`), адрес (`phone` и/или `chatId`), `AbortSignal` с таймаутом; возвращает либо `ok`, либо `{ retry, code, message }`. Разбор кодов провайдера (`BAD_CONTACT`, `MESSAGES_NOT_TEXT_FIRST`, `REPEATED_CRM_MESSAGE_ID` и прочие из `WAZZUP_INTEGRATION.md`) — внутри адаптера; отправщик знает только «повторять или нет». У адаптера есть `textLimit` (Telegram через Wazzup — 1 024 символа), отправщик отбраковывает слишком длинное сам, не тратя вызов. Отвергли интерфейс «адаптер на канал с методом sendText(phone, text)»: Telegram-бот адресует `chat_id`, а не телефон, и Wazzup один адаптер обслуживает три канала.

15. **Выбор канала — одна функция `channelForClient(client)` в `sender-core.ts`.** Возвращает `{ channel, known }`: `client.messenger`, иначе первый из `client.channels`, иначе канал по умолчанию с пометкой «не выбран». Её зовут `enqueue` (заполняет `Outbox.channel` — это то, что видно в карточке), отправщик (решает по `known`, что делать с невыбранным каналом) и карточка клиента (перенос канала у неотправленных). Почему не хранить «канал не выбран» в записи: понадобилось бы либо необязательное поле-дубль, либо снятие `NOT NULL` — это не добавляющая миграция.

16. **Удачная отправка пишется в ленту брони** (`Interaction`, тип `MESSAGE`, направление `OUT`, канал, `userId = null`). Почему: администратор должен видеть переписку в одном месте, и это же место Ф14 использует для входящих. Отвергли «только Outbox»: лента брони осталась бы без исходящих, и Ф14 пришлось бы их туда задним числом переносить.

17. **Отправщик ничего не инвалидирует.** `revalidatePath` по документации Next 16 (`03-api-reference/04-functions/revalidatePath.md`) вызывается только из Server Functions и Route Handlers; таймерный тик — не запрос, вызов оттуда упадёт. Страницы CRM динамические (за авторизацией), свежие данные они и так читают на каждый заход. Инвалидацию делают только серверные действия карточки настроек.

18. **Отправщик работает клиентом планировщика.** Все функции отправщика получают клиент базы параметром; `senderSettings(db)` устроен как `siteLinks(db)`. Почему: решение 8 Ф1 — у тика свой клиент без логов и с лимитом соединений.

19. **Правила `before_checkout_2d` и `after_checkout_7d` держит выключенными seed.** В seed появляется список `OFF_BY_DECISION`; для кодов из списка `isActive: false` пишется и при создании, и при обновлении. Почему не одноразовый `UPDATE` в миграции: seed на stage идёт при каждом старте, и правило, включённое вручную, молча вернулось бы в строй. Когда заказчик утвердит скидку, код убирается из списка — это одна строка и видимое решение. Отвергли удаление правил и шаблона `thanks_discount`: миграции только добавляющие, а текст ещё пригодится Ф5.

20. **Строгая проверка «ЧЧ:ММ» — в `src/lib/periods.ts`, рядом с `DEFAULT_TIME` и `TIME_OPTIONS`.** Там уже живёт та же нестрогая проверка (`periods.ts:17`), и файл безопасен для клиента. Один регулярный шаблон `HHMM` и `isHhMm()` заменяют три копии (`validation/booking.ts:4`, `dates.ts:75,83`, `periods.ts:17`). Отвергли новый файл `src/lib/time.ts`: четвёртое место для одного правила.

21. **Сбой seed останавливает старт контейнера** (`exit 1`), с аварийным выходом `SEED_STRICT=0`. Почему: от seed зависят тексты сообщений, `dedupGroup` и условия правил; молчаливый провал означает, что клиенту уйдёт старый текст или сработает неутверждённое правило. Отвергли «писать уведомление и продолжать»: уведомления видит тот, кто зашёл в CRM, а выкатку делает человек у консоли.

22. **Поддельный адаптер для тестов.** Регистрируется только при `SENDER_FAKE` и `NODE_ENV !== "production"`, значения `1` (успех), `fail` (временная ошибка), `bad` (постоянная ошибка). Почему: без него в шаге 0 нельзя проверить ни одну ветку «отправили / повторили / сдались» — адаптеров нет. На stage сборка production, поэтому попасть туда он не может.

## 5. Изменения схемы (только добавляющие)

**Миграция 1 — `outbox_sender_fields`** (поля и индекс, значений enum не добавляет):

```prisma
model Outbox {
  // …как сейчас…
  nextAttemptAt DateTime?   // не раньше этого момента пробовать снова (повтор с паузой)
  claimedAt     DateTime?   // взято отправщиком в работу; аренда истекает через sender.leaseMinutes

  @@index([status, scheduledAt])
  @@index([status, nextAttemptAt])   // выборка отправщика
}
```

**Миграция 2 — `outbox_sender_enums`** (только `ALTER TYPE … ADD VALUE`, в этой же миграции значения не используются):

```sql
ALTER TYPE "OutboxStatus" ADD VALUE 'EXPIRED';   -- устарело, не отправлено
ALTER TYPE "OutboxStatus" ADD VALUE 'SKIPPED';   -- пропущено по правилу отправки
ALTER TYPE "NoticeKind"   ADD VALUE 'MESSAGE_FAILED'; -- сообщение клиенту не доставлено
```

Разделение на две миграции — требование проекта («новое значение enum отдельной миграцией, без использования в той же»). Порядок папок при слиянии перенумеровывает оркестратор.

Итоговый смысл статусов `Outbox` (шесть уже есть, два новых):

| Статус | Когда | Подпись в карточке |
|---|---|---|
| `PENDING` | ждёт отправки или повтора | «запланировано 23 сент, 14:05» (по Москве) |
| `SENT` | адаптер подтвердил | «отправлено 23 сент, 14:05» |
| `FAILED` | попытки исчерпаны или постоянная ошибка | «не доставлено: <причина>, попыток 3» |
| `CANCELLED` | бронь отменена/отклонена, откат статуса | «отменено» |
| `SKIPPED_NO_PROVIDER` | нет адаптера для канала или канал не подключён | «канал не подключён» |
| `EXPIRED` (новый) | старше порога по возрасту | «устарело, не отправлено» |
| `SKIPPED` (новый) | «не беспокоить», номер не в списке, канал не выбран, нет получателя | «пропущено: <причина>» |

```ts
// Чистые правила отправщика: канал клиента, предохранители, паузы перед повтором.
// Без базы и без server-only — как tick-core.ts: логика под юнит-тестами, Prisma живёт в sender.ts.
import type { Channel } from "@prisma/client";

export const SENDER_CODE = "sender";

export type Recipient = { phone: string | null; chatId: string | null; doNotDisturb: boolean; channelKnown: boolean };
export type SkipStatus = "EXPIRED" | "SKIPPED" | "SKIPPED_NO_PROVIDER" | "FAILED";
export type Decision = { kind: "send" } | { kind: "skip"; status: SkipStatus; reason: string };

// Канал клиента — одно правило на всю систему: enqueue, отправщик, карточка клиента.
// PHONE и SITE — не мессенджеры, в выбор не идут.
export function channelForClient(c: { messenger: Channel | null; channels: Channel[] } | null, def: Channel = "WHATSAPP") {
  const picked = c?.messenger ?? c?.channels.find((x) => x !== "PHONE" && x !== "SITE") ?? null;
  return { channel: picked ?? def, known: picked !== null };
}

// Порядок проверок — по возрастанию цены ошибки; всё, кроме сетевых сбоев, терминально
export function decide(row: OutboxRow, to: Recipient, cfg: SenderConfig, now: Date, ch: { ready: boolean; textLimit: number | null }): Decision {
  if (now.getTime() - row.scheduledAt.getTime() > cfg.maxAgeHours * 3_600_000)
    return { kind: "skip", status: "EXPIRED", reason: "устарело, не отправляем" };
  if (!row.renderedText.trim()) return { kind: "skip", status: "FAILED", reason: "пустой текст" };
  if (!to.phone && !to.chatId) return { kind: "skip", status: "SKIPPED", reason: "нет получателя" };
  if (to.doNotDisturb) return { kind: "skip", status: "SKIPPED", reason: "клиент просил не беспокоить" };
  if (cfg.allowlistOnly && !inAllowlist(to.phone, cfg.allowlist))
    return { kind: "skip", status: "SKIPPED", reason: "номер не в списке разрешённых (режим теста)" };
  if (!to.channelKnown && !cfg.sendWhenChannelUnknown)
    return { kind: "skip", status: "SKIPPED", reason: "клиент не выбрал мессенджер" };
  if (!ch.ready) return { kind: "skip", status: "SKIPPED_NO_PROVIDER", reason: "канал не подключён" };
  if (ch.textLimit && row.renderedText.length > ch.textLimit)
    return { kind: "skip", status: "FAILED", reason: `сообщение длиннее лимита канала (${ch.textLimit})` };
  return { kind: "send" };
}

// 1 → 5 → 25 минут, не больше получаса
export function backoffMs(attempts: number): number {
  return Math.min(30 * 60_000, 60_000 * 5 ** Math.max(0, attempts - 1));
}
```

## 8. Порядок выкатки на stage

1. Бэкап базы (`docker/backup.sh`), выкатка. Отправщик выключен: ключа `scheduler.scans.sender` в базе нет, значит режим `off`.
2. Проверить, что seed отработал: в логе нет строки про ошибку, правила `before_checkout_2d` и `after_checkout_7d` выключены.
3. Владелец открывает «Настройки», видит карточку «Отправка сообщений»: режим «Выключено», очередь 5, самое старое от 08.09.
4. Нажать «Убрать устаревшие из очереди» — 5 записей получают «устарело», очередь пустеет. Клиентам ничего не ушло.
5. Завести тестовую бронь (телефон `+7999…`), убедиться, что сообщение встало в очередь.
6. Режим «Пробно», дождаться тика: в карточке счётчик «в пробном режиме ушло бы: 1», статус записи не изменился.
7. Вписать в список разрешённых свой номер, режим «Включено», тик: запись получает «канал не подключён» (адаптеров нет) — предохранители и путь до адаптера проверены.
8. Вернуть режим «Выключено» до появления токена бота (Ф4, шаг 1). **«Включено» на stage при пустом реестре адаптеров держать не надо: каждое новое сообщение будет сразу помечаться «канал не подключён», и при появлении бота его придётся ставить в очередь заново.**
9. Записать в HANDOFF: что выкачено, в каком режиме оставлено, какие номера в списке.

## 9. Риски

| Риск | Что делаем |
|---|---|
| Старые PENDING уйдут живым людям | Три независимых заслона: режим по умолчанию «выключено», порог по возрасту 6 ч, пустой список разрешённых. Плюс ручная уборка кнопкой на шаге 4 выкатки |
| Неутверждённая скидка 10 % уйдёт клиенту | Правила выключены в seed и при создании, и при обновлении; включить их можно только сознательно, убрав код из `OFF_BY_DECISION` |
| Дубль отправки при зависшем проходе | Аренда 5 мин ≫ таймаута отправки 10 с; `id` записи идёт провайдеру ключом идемпотентности (Wazzup гасит повтор в течение 60 с); `attempts` растёт при аренде, поэтому вечного цикла нет. Остаточный риск принят и записан |
| Проход не укладывается в минуту | Бюджет 30 с + таймаут 10 с + 10 отправок за тик; флаг `state.running` из Ф1 не даёт двум проходам наложиться |
| Сбой провайдера превращается в шторм ошибок | Повторов не больше 3 с растущей паузой; самоотключение после 5 ошибок + уведомление `CHANNEL_DOWN`; лог по смене состояния (`ErrorLog` из Ф1) не забивается каждую минуту |
| Строгая проверка времени ломает существующие данные | Поля на сайте — выпадающие списки из `TIME_OPTIONS` (всегда валидны); старые кривые значения в базе не читаются строго, `fmtDayTime` и `plannedMoment` как и раньше подставляют 12:00 |
| `SEED_STRICT=1` уронит stage в цикл перезапусков | В логе первой же строкой видна причина; аварийный выход `SEED_STRICT=0` описан в HANDOFF и в `tests/README.md` |
| Сайт продолжает обещать сообщения, которых нет | Осознанная граница: экран результата делает Ф4 шаг 1 вместе с кнопкой «Открыть бота». Пока отправщик выключен, ситуация не ухудшается. Если заказчик смотрит stage сегодня — вынести правку текста отдельной мелкой задачей вне фазы |
| Конфликт с Ф2б по `tick-core.ts` и `scheduler.ts` | Ф2б дописывает в `SCANS`, Ф4 — новый массив `STEPS` и новый цикл; блоки не пересекаются. Действие `setScanModeAction(code, mode)` пишет тот, кто придёт первым, второй его использует (подпись зафиксирована здесь) |
| Конфликт с Ф2б по `notices.ts` | Ф4 только вызывает `notify`. Если Ф2б уже слита и подпись стала `notify(kind, text, bookingId, { tx, key })` — вызовы переписываются на неё, ключ `msg-failed:<id записи>` и `sender-down` |

## 10. Критерии приёмки (что проверяет человек глазами)

1. На `/admin/settings` у владельца есть карточка «Отправка сообщений»: режим «Выключено», порог 6 часов, список разрешённых номеров пуст, счётчики за сутки, строка «в очереди N, самое старое от …».
2. При выключенном режиме тик проходит как раньше: карточка «Планировщик» — «Работает», в очереди ничего не меняется.
3. В режиме «Пробно» через минуту появляется «в пробном режиме ушло бы: N», при этом ни у одной записи не поменялись статус, число попыток и время.
4. В режиме «Включено» с пустым списком разрешённых ни одно сообщение не уходит: в карточке брони у записи подпись «пропущено: номер не в списке разрешённых (режим теста)».
5. После добавления номера в список та же запись при следующем тике получает «канал не подключён» (в шаге 0 адаптеров нет) — видно, что предохранители пройдены и дело дошло до адаптера.
6. Сообщение возрастом больше 6 часов получает «устарело, не отправлено» и больше не трогается.
7. Кнопка «Убрать устаревшие из очереди» убирает все висящие PENDING старше порога; счётчик очереди обнуляется, в журнале появляется запись, клиентам ничего не ушло.
8. В карточке брони и клиента время очереди показывается по Москве (совпадает с часами в шапке CRM), статусы подписаны по-русски, у неудачных видно причину и число попыток.
9. В базе после перезапуска контейнера правила `before_checkout_2d` и `after_checkout_7d` выключены.
10. Заявка с сайта с выбранным Telegram по-прежнему встаёт в очередь с каналом Telegram; заявка, заведённая администратором по телефону, — с каналом по умолчанию.
11. Если сломать seed нарочно, контейнер не стартует и в логе видна строка «seed не прошёл».
12. Форма быстрой брони и заявка с сайта со временем «25:00» отвечают понятной ошибкой, а не принимают значение.

1. Настройки `sender.*` и `messaging.*` одним запросом клиентом планировщика; провайдер из реестра; `check()` провайдера — до любой транзакции, с таймаутом (критика: сеть под блокировкой).
2. `messaging.senderEnabled` = «вкл» **и** провайдер отвечает **и** список разрешённых не ограничивает. Пишется каждым проходом и сбрасывается в `false` при смене режима/провайдера и самоотключении.
3. Короткая транзакция (10 с): `pg_try_advisory_xact_lock(24_0924)` → зависшие аренды (`lockedUntil < now`) → `FAILED` «статус отправки неизвестен…» + `MESSAGE_FAILED`, **без повторной отправки** → счёт за час (`SENT` за 60 мин + арендованные) → кандидаты `PENDING, scheduledAt ≤ now, nextAttemptAt ≤ now или NULL, lockedUntil IS NULL` c `FOR UPDATE OF o SKIP LOCKED`, до 50 → `decide` → терминальные статусы и «ждёт» пишутся сразу → `planPass` → идущим к адаптеру `lockedUntil = now + 5 мин`, `attempts + 1`. В «пробно» — исключение-откат, журнал пишется в `sender.dryPreview`.
4. Вне транзакции, по одной, с таймаутом (сигнал + принудительный срок): `send` → результат сразу. Успех пишется безусловно (`SENT`, `sentAt`, `providerMessageId`), затем строка в ленту брони. Остальное — только пока аренда наша и запись не отменена.
5. Бюджет прохода 30 с: не успевшим аренда снимается, попытка возвращается.

**Даты в сыром SQL.** Локальный Postgres работает в поясе `Asia/Jakarta`, а `Date` в `$queryRaw` уходит как `timestamptz` и сравнивается с `timestamp(3)` по поясу сессии — сдвиг на 7 часов. В запросе кандидатов время приводится явно (`::timestamptz AT TIME ZONE 'UTC'`), `updatedAt` в сыром SQL — `now() AT TIME ZONE 'UTC'`. Любой будущий сырой запрос с датами обязан делать так же.

### Где отступил от документа и почему

1. **Файлы провайдера — `src/server/messaging/*`, интерфейс `MessengerAdapter`, аренда `lockedUntil`** вместо `automations/adapters/index.ts`, `ChannelAdapter` и `claimedAt`: так требует контракт, на который уже опирается Ф14 (`PHASE_14_WAZZUP.md` §4.2, `MAP_DEPENDENCIES.md` §2, п. Ф14). `check()` играет роль `ready()`; `textLimit(channel)` — необязательный метод по каналу (критика Ф14: у Wazzup три канала с разными пределами); `send` принимает необязательный `AbortSignal` — реализация Ф14 без него совместима.
2. **Ждут, а не пропускаются, два случая** (критика, блокеры 2 и 3): «номер не в списке разрешённых» и «провайдер не отвечает» оставляют запись `PENDING` с причиной в `lastError` и перепроверкой через 5 минут, попытку не тратят; снимает их порог по возрасту. Иначе при терминальном `SKIPPED` подтверждение реального клиента во время теста терялось бы навсегда (`dedupKey` держит запись). **Нет провайдера вовсе** (`messaging.provider = none`, заглушка на бою, нет ключа) — терминальный `SKIPPED_NO_PROVIDER`, как ждут оркестратор и Ф14. Терминальны также: нет получателя, «не беспокоить» для рекламы, канал записи — не мессенджер, мессенджер не выбран при `sendWhenChannelUnknown = false` (`SKIPPED`), пустой текст и длиннее предела канала (`FAILED` + уведомление).
3. **`attempts` растёт только у записей, реально идущих к адаптеру** (критика, «важно»): отсеянные потолком, пропущенные и не успевшие за бюджет попытку не тратят.
4. **Зависшая аренда не переотправляется** (критика, «важно»: окно Wazzup 60 с короче аренды 5 мин): `FAILED` «статус отправки неизвестен: … проверьте переписку с клиентом» и уведомление.
5. **«Не беспокоить» режет только рекламу** (`MARKETING_RULES` = правила со скидкой) — `DECISIONS_2026-09-24.md` §2; в документе блокировало всё.
6. **Список разрешённых — двумя слоями.** Карточка: `sender.allowlistOnly` (по умолчанию `true`) + `sender.allowlist` (по умолчанию пуст → не уходит никому, решение 9). Сервер: `OUTBOX_ALLOWLIST` в `.env` — пока задан, пишем только на эти номера, даже если в карточке ограничение снято; не задан — ограничения от него нет («адаптер обязан работать и при пустом allowlist», Ф14). Номера нормализуются `normalizePhone`.
7. **Ключи отправщика — в чистом `sender-core.ts`, не в `settings.ts`** (критика, «важно»: `settings.ts` тянет основной клиент Prisma в бандл планировщика). `settings.ts` не тронут. Уведомления отправщик пишет сам (`adminNotice.create`), а не через `notify()` — по той же причине.
8. **`sender.defaultChannel` не заведён** (критика, «важно»: его никто не читал бы): по умолчанию всегда WhatsApp (`DEFAULT_CHANNEL`). Канал отправки — `Outbox.channel` (его видит администратор); `channelForClient` на момент отправки даёт только признак «клиент выбрал сам».
9. **Заглушка выбирается настройкой, а не `SENDER_FAKE`** (критика, «важно»: e2e не может менять окружение сервера): `messaging.provider = fake`, ответ — `messaging.fakeMode`; на бою недоступна (`NODE_ENV = production`), сохранённое значение не действует.
10. **Режим пишется слиянием под блокировкой строки** (`SELECT … FOR UPDATE` + `mergeMode`) и в действии владельца, и при самоотключении (критика, «важно»). `setScanModeAction(code, mode)` не писал — это Ф2б; мои действия — в новом `src/app/admin/actions/sender.ts`, чтобы не конфликтовать в `actions/settings.ts`.
11. **Самоотключение считает только сбои канала** (`retry: true`, исключения, таймауты); «номера нет в мессенджере» — дело клиента, не канала.
12. **В ленту брони — короткая строка** «Отправлено клиенту в Telegram: <код>», полный текст — в блоке «Сообщения клиенту» (критика, «мелочь»: дубль на карточке).
13. **Нового индекса нет** (критика, «мелочь»): выборка идёт по существующему `(status, scheduledAt)`.
14. **seed не создаёт ключи `sender.*`**: значения по умолчанию в коде, строка появляется при первом сохранении карточки; меньше правок в общем `seed.ts`.
15. **«Убрать устаревшие»** не трогает записи с арендой (критика, «мелочь»).
16. **`leads.ts:61`** (перенос канала у дубля заявки с сайта) оставлен как есть: файл первой правит МФ-1 (`MAP_DEPENDENCIES.md` §3), а строка уже делает то же самое по брони. Свести на `moveClientPendingChannel` — при слиянии МФ-1.
17. **e2e — `tests/e2e/f4-sender.mjs`** (имя от оркестратора), только локально: нужна заглушка и доступ к базе для крайних случаев; на stage сценарий выходит с пропуском, проверка — руками по §8.

### Выкатка на stage (вместо §8)

1. Бэкап, выкатка: две миграции, seed (в логе `seed ok`; правила со скидкой выключены). Отправщик выключен — ключа `sender` в карте режимов нет.
2. «Настройки» → «Отправка сообщений»: «Выключено», провайдер «Не подключён», очередь N, «Убрать устаревшие из очереди (N)» — нажать: старые PENDING 08–22.09 со старыми ключами `on_*:<id>` получают «устарело», клиентам ничего не уходит. Даже без кнопки их не отправит порог 6 ч.
3. «Пробно» → через минуту журнал «ушло бы» в карточке; в базе ничего не меняется.
4. «Включено» при провайдере «Не подключён»: новые сообщения — «ждёт: номер не в списке…» (список пуст) или, для номеров из списка, «канал не подключён». До Ф14 держать «Выключено».

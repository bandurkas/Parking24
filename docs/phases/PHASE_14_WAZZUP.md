# Ф14. Wazzup: адаптер WhatsApp и окно чатов

Дорожка Д3, после шага 0 Ф4. Документ архитектуры, по нему пишется код. Версия 1, 23.09.2026, база — коммит `88c9425`.

Источники: `docs/WAZZUP_INTEGRATION.md` (разбор API целиком), `docs/TZ_2026-09-21_PLAN.md` §1 и §5 этапы 2а–2б, `docs/TZ_2026-09-21_SOURCE.md` разд. 2, `docs/TZ_STATUS_2026-09-22_night.md` §3 Ф14 и §4, `docs/MESSAGE_TEMPLATES_2026-09-22.md`.

## 1. Зачем

После отмены отдельного Telegram-бота (решение 23.09) Wazzup — единственный путь, по которому клиент вообще что-то получит: подтверждение брони, напоминание, сообщение о заезде и просьбу об отзыве. Ф14 подключает к канало-независимому отправщику Ф4 первый настоящий адаптер (WhatsApp через Wazzup), принимает от Wazzup статусы и ответы клиентов и встраивает в CRM готовое окно переписки, чтобы администратор видел сообщение клиента и мог ответить, не заводя второй мессенджер.

## 2. Что входит и что не входит

**Входит:**

- адаптер `wazzup` под интерфейс отправщика Ф4: одна отправка, разбор ответа, классификация ошибок «повторять / не повторять»;
- работа с каналами: поиск канала по транспорту (`channelId` нигде не хранится), кеш, состояния (`active`, `qridle`, `blocked`, `notEnoughMoney`, …);
- автонастройка аккаунта: регистрация адреса вебхука и синхронизация пользователей CRM, идемпотентно, при смене ключа — сама;
- вебхук `POST /api/webhooks/wazzup/<секрет>`: проверочный запрос, входящие сообщения, эхо ответов администратора, статусы доставки, смена состояния канала;
- входящие → запись в ленту брони и клиента + уведомление в колокольчик; статусы → «доставлено» и «прочитано» в карточке;
- окно чатов Wazzup: панель «Чат с клиентом» в карточке брони и клиента (`scope: card`), страница «Чаты» в меню (`scope: global`) со счётчиком неотвеченных; ключ в браузер не попадает;
- карточка «Сообщения» в настройках владельца: провайдер, состояние каналов, диалоги за месяц, кнопка «Проверить подключение»;
- собственный счётчик диалогов месяца с порогом — предохранитель на случай исчерпания лимита тарифа;
- заглушка (мок) Wazzup и тесты против неё: весь код проверяется до регистрации аккаунта, пробный период в 3 дня не тратится на разработку;
- выключатель `messaging.provider` в `Setting`: включение реального канала — настройка, а не выкатка;
- список каналов, доступных для обещания на сайте (только те, по которым мы реально можем написать первыми).

**Не входит (чужие зоны):**

- сам отправщик: очередь, аренда записи, повторы с паузой, отмена устаревших, список разрешённых номеров, режим «пробно» — **Ф4 шаг 0**;
- выбор канала клиента (`Client.messenger`), «не беспокоить», постановка в Outbox, `dedupGroup`, честная строка статуса очереди в карточке (`bookings/[id]/page.tsx:208`), экран результата на сайте — **Ф4**;
- тексты шаблонов, правила, страница «Сообщения» в настройках — **МФ-2 и Ф5**;
- механизм колокольчика (`notify` с ключом дедупликации, `AdminNotice.dedupKey`, опрос бейджа, права) — **Ф2б**; Ф14 только вызывает `notify`;
- сканы по времени и напоминания — **Ф7**;
- уведомление администратору в мессенджер (`admin.notifyPhone`) — **Ф4, последним шагом**; Ф14 даёт для него канал, но ключ и текст не заводит;
- заголовки безопасности, CSP, публикация порта, боевой номер WhatsApp в `tariffs.ts:30` — **МФ-3б**;
- телефония и запись звонков — отдельная работа, решение пользователя;
- собственный мессенджер внутри CRM: переписку показывает окно Wazzup, мы храним только копию в ленте.

## 3. Как это работает

```
ОТПРАВКА
  Ф4: тик → берёт Outbox под аренду → adapter.send({outboxId, channel, phone, text})
        Ф14 ▸ ensureReady()                     (раз в 10 мин или при смене ключа)
            ▸ канал = активный канал нужного транспорта (кеш 5 мин)
            ▸ POST /v3/message {channelId, chatType, chatId|phone, text, crmMessageId: outboxId}
            ▸ 201 → {ok:true, providerMessageId}
            ▸ ошибка → {ok:false, retry: да|нет, code, message} (+ уведомление, если надо)
  Ф4: пишет результат в Outbox отдельной короткой транзакцией

ВЕБХУК  POST /api/webhooks/wazzup/<секрет>
  секрет не совпал → 404 (тело не читаем)
  {test:true}                → 200, ничего не пишем
  statuses  sent/delivered/read/error → Outbox по providerMessageId, отметки только «вперёд»
  messages  isEcho=false     → Interaction(IN)  + колокольчик (один на клиента, пока не прочитан)
  messages  isEcho=true      → Interaction(OUT, «ответил {имя}»), наше же сообщение пропускаем
  channelsUpdates            → сброс кеша каналов, обновление Setting messaging.channels,
                               уход из active → уведомление CHANNEL_DOWN

ОКНО ЧАТОВ (ключ остаётся на сервере)
  страница/панель (сервер) → POST /v3/iframe {user:{id,name}, scope, filter} → ссылка
                           → <iframe src={ссылка}> в браузере
  счётчик  GET /api/admin/chats/unanswered → GET /v3/unanswered/<userId> (кеш 30 с)

САЙТ
  Setting messaging.channels (обновляется вебхуком и ensureReady)
    → какие мессенджеры предлагать как канал подтверждения
```

## 4. Решения

### 4.1 Ф14 — адаптер, а не второй отправщик

Выбрано: Ф14 реализует **один метод отправки одного сообщения** и ничего не знает про очередь, повторы, паузы и возраст сообщений. Отклонено: собственный цикл отправки внутри Ф14 — это второе место, где живёт правило «когда слать», а правило проекта «одно правило в одном месте». Следствие: без шага 0 Ф4 адаптер не отправит ничего, и это правильно — до Ф4 его проверяет только мок и юнит-тесты.

### 4.2 Интерфейс адаптера (ожидание к Ф4, §8)

```ts
// src/server/messaging/types.ts — владелец файла Ф4 шаг 0
export type SendRequest = {
  outboxId: string;   // → crmMessageId, защита от дублей на стороне провайдера
  channel: Channel;   // WHATSAPP | TELEGRAM | MAX
  phone: string;      // E.164: «+79991234567»
  text: string;
};
export type SendResult =
  | { ok: true; providerMessageId: string | null }
  | { ok: false; retry: boolean; code: string; message: string };

export interface MessengerAdapter {
  readonly code: string;                         // "wazzup"
  send(req: SendRequest): Promise<SendResult>;
  availableChannels(): Promise<Channel[]>;       // активные каналы: для сайта и выбора канала
  check(): Promise<AdapterHealth>;               // для карточки настроек
}
```

Правила, на которые опирается Ф14:

1. `send` вызывается **вне транзакции базы**: внутри сетевой запрос, транзакцию он бы держал открытой.
2. Адаптер сам не повторяет и не спит. `retry: true` — «оставь PENDING, вернись позже», `retry: false` — «FAILED, больше не пробуй».
3. `providerMessageId` Ф4 пишет в ту же запись Outbox **сразу** после успеха: иначе вебхук со статусом придёт к записи, которую не найти.
4. `message` — короткая строка для `Outbox.lastError`: код и человеческая расшифровка, без тела ответа и без ключа.
5. Адаптер **сам создаёт уведомления администратору по ошибкам отправки** (`notify`, вне транзакции). Причина: расшифровка кода — знание адаптера, а не отправщика; так Ф4 не обязан знать ни одного кода Wazzup.

### 4.3 Каналы ищем по транспорту, `channelId` не храним

`GET /v3/channels` кешируется на 5 минут в `globalThis` (модуль в одном процессе исполняется дважды — тот же приём, что в `scheduler.ts`), кеш сбрасывается вебхуком `channelsUpdates` и кнопкой «Проверить подключение». Соответствие:

| `Channel` в CRM | транспорты Wazzup, по приоритету | как адресуем |
|---|---|---|
| `WHATSAPP` | `whatsapp` (QR), затем `wapi` (WABA) | `chatType: "whatsapp"`, `chatId` — цифры номера без плюса |
| `TELEGRAM` | `tgapi` (личный, умеет писать первым), `telegram` (бот — первым не пишет) | `chatType: "telegram"`, `phone` — цифры |
| `MAX` | `max`, `maxbot` | `chatType: "max"`, `phone` — цифры |

Если активного канала нужного транспорта нет — берём активный канал в порядке WhatsApp → Telegram → MAX (правило `docs/WAZZUP_INTEGRATION.md` §3). Если активных нет вовсе — `{ok:false, retry:true, code:"NO_CHANNEL"}`: сообщение ждёт, канал может подняться. Транспорт `telegram` (бот) в список «можем написать первыми» **не входит** никогда: бот не пишет первым, это причина отмены своего бота.

Отклонено: хранить `channelId` в `Setting`. При переезде на аккаунт заказчика пришлось бы менять и ключ, и идентификаторы, а забытый старый `channelId` дал бы `CHANNEL_NOT_FOUND` без понятной причины.

### 4.4 Включение — настройка, а не выкатка

`Setting messaging.provider`: `"none"` (по умолчанию, в том числе на stage) или `"wazzup"`. Реестр адаптеров:

```ts
// src/server/messaging/registry.ts
export async function activeAdapter(): Promise<MessengerAdapter | null> {
  if ((await settingStr("messaging.provider", "none")) !== "wazzup") return null;
  if (!process.env.WAZZUP_API_KEY) return null;   // ключа нет — считаем, что провайдера нет
  return wazzupAdapter;
}
```

Ф4 при `null` ставит записи в `SKIPPED_NO_PROVIDER`, как и раньше. Таким образом боевой канал включается переключателем в настройках владельца, без сборки и перезапуска; замена ключа заказчика — правка `.env` и рестарт контейнера, без правок кода (`docs/WAZZUP_INTEGRATION.md` §4).

### 4.5 Автонастройка `ensureReady()` — ленивая, не скан планировщика

Регистрация вебхука (`PATCH /v3/webhooks`) и синхронизация пользователей (`POST /v3/users`) — идемпотентные операции, их надо повторять после смены ключа, добавления пользователя CRM и переезда на другой аккаунт.

Выбрано: **ленивая идемпотентная настройка** — функция `ensureReady()`, одиночное выполнение в процессе (флаг в `globalThis`), отметка в `Setting wazzup.setup = {at, keyHash, webhookHash, usersHash}`; повтор не чаще раза в 10 минут и всегда при изменении любого из хешей. Вызывается: перед первой отправкой в процессе, при открытии страницы «Чаты» или панели чата, кнопкой «Проверить подключение».

Отклонено: скан в реестре планировщика. Контракт скана (`tick-core.ts`) — «внутри транзакции только запись в базу»; сетевой вызов внутри держал бы `pg_try_advisory_xact_lock` до 30 секунд и тормозил остальные сканы. Отклонено также: вызов из `instrumentation.ts` при старте — это файл Ф1, и при недоступном Wazzup старт сервера задерживался бы.

`usersHash` считается по списку `User` с ролями OWNER и ADMIN (id + имя): охране чаты не нужны.

### 4.6 Вебхук: свой секрет в адресе, повторов не ждём

Механизм авторизации вебхуков в документации Wazzup не выяснен (упоминается `crmKey` без описания), политика повторов не описана. Поэтому:

- адрес вида `/api/webhooks/wazzup/<секрет>`, секрет — `WAZZUP_WEBHOOK_SECRET`, не короче 32 символов, только в серверном `.env`; сравнение — постоянное по времени, тем же приёмом, что `cronSecretOk` (sha256 + `timingSafeEqual`);
- не совпал — `404 Not found`, тело запроса не читаем и в лог не пишем (в адресе секрет — адрес не логируем нигде);
- **обработка синхронная, до ответа 200**: на повторы провайдера рассчитывать нельзя, а `after()` потерял бы событие при рестарте контейнера. Объём работы — один-два запроса в базу;
- обработчик устойчив к повторам: входящие дедуплицируются по `messageId`, статусы идемпотентны по правилу «только вперёд»;
- любая ошибка внутри события пишется в лог, остальные события пакета обрабатываются, ответ всё равно `200`: иначе Wazzup может счесть адрес мёртвым и отключить подписку;
- проверочный запрос `{test:true}` → `200` в пределах 30 секунд, ничего не пишем.

**Важно про stage.** `src/proxy.ts` закрывает весь сайт Basic Auth, а матчер захватывает `/api/...`. Как для `/api/cron`, добавляем исключение для `/api/webhooks/` — иначе Wazzup получит 401 и подписка не встанет. Единственная защита этого пути — секрет в адресе.

```ts
// src/app/api/webhooks/wazzup/[secret]/route.ts
export async function POST(req: NextRequest, ctx: RouteContext<'/api/webhooks/wazzup/[secret]'>) {
  const { secret } = await ctx.params;
  if (!webhookSecretOk(secret, process.env.WAZZUP_WEBHOOK_SECRET)) return new NextResponse("Not found", { status: 404 });
  let body: unknown = null;
  try { body = await req.json(); } catch { return NextResponse.json({ ok: true }); }
  for (const e of parseWebhook(body)) {
    try { await applyEvent(e); } catch (err) { console.error("[wazzup] событие", e.kind, err); }
  }
  return NextResponse.json({ ok: true });
}
```

`parseWebhook` — чистая функция без базы (юнит-тесты), `applyEvent` — запись в базу.

### 4.7 Статусы: «доставлено» и «прочитано» только вперёд

Ранг `sent < delivered < read`; событие с рангом не выше уже записанного игнорируется (сеть может переставить события местами). `error` после успешной отправки не переводит Outbox в `FAILED` — сообщение из очереди ушло, повторять его нельзя; пишем `failCode` и показываем в карточке «не доставлено».

Гонка «статус пришёл раньше, чем записан `providerMessageId`»: если запись не нашлась — одна повторная попытка через 1 секунду, потом событие отбрасывается с записью в лог. Принято осознанно: отметка доставки — индикатор, на деньги и статусы брони она не влияет.

### 4.8 Входящие: лента брони и колокольчик

Клиент ищется по цифрам `chatId`, приведённым к E.164 (`normalizePhone`), по `Client.phone` и по `Client.extraPhones`. Бронь — последняя нетерминальная (`NEW`, `AWAITING_PAYMENT`, `CONFIRMED`, `CHECKED_IN`), иначе последняя по `createdAt` за 30 дней, иначе `null`.

Запись: `Interaction { type: MESSAGE, channel, direction: IN|OUT, text, externalId: "wz:<messageId>", clientId, bookingId, userId: null, meta }`. Системные действия идут с `userId = null` — правило проекта; имя администратора из эха кладём в `meta.authorName` и показываем в ленте как «ответил {имя}».

Дедупликация — `Interaction.externalId @unique` и вставка с обработкой конфликта. Медиа не скачиваем: в текст подставляем `contentUri` ссылкой, файлы остаются в Wazzup.

Сообщение с неизвестного номера: пишем `Interaction` без клиента и брони с текстом «Сообщение с номера +7…: …» и создаём уведомление — администратор решит, чей это номер.

Колокольчик: `notify(NoticeKind.CLIENT_MESSAGE, "…", bookingId)` — **не на каждое сообщение**, иначе диалог из десяти реплик забьёт ленту уведомлений. Правило: новое уведомление создаётся, только если по этому клиенту нет непрочитанного `CLIENT_MESSAGE`. Когда Ф2б добавит `AdminNotice.dedupKey`, переходим на ключ `client-message:<clientId>`; до тех пор — проверка непрочитанного по `bookingId` (и без дедупа, если брони нет).

Наше же сообщение, вернувшееся эхом (`messageId` совпал с `Outbox.providerMessageId`), в ленту не пишется: оно уже видно в блоке «Сообщения клиенту».

### 4.9 Состояния канала: администратор узнаёт сразу

Событие `channelsUpdates` и каждый вызов `ensureReady()` сравнивают состояние с последним известным (`Setting messaging.channels`). Переход `active → любое другое` даёт уведомление `CHANNEL_DOWN` с человеческим текстом:

| Состояние | Текст уведомления |
|---|---|
| `qridle` | «Канал WhatsApp отключился: нужно заново отсканировать QR-код в кабинете Wazzup. Сообщения клиентам не уходят.» |
| `blocked`, `phoneUnavailable`, `unauthorized` | «Канал WhatsApp заблокирован. Сообщения клиентам не уходят, позвоните клиентам вручную.» |
| `notEnoughMoney` | «Канал WhatsApp остановлен: не оплачен тариф Wazzup. Сообщения клиентам не уходят.» |

Одно уведомление на переход (повтор того же состояния молчит). Возврат в `active` даёт отдельное уведомление «канал снова работает» — иначе администратор не узнает, что можно не звонить. В карточке настроек — строка по каждому каналу с состоянием и временем последней проверки.

### 4.10 Лимит диалогов: считаем сами

В документации не выяснено, что происходит при исчерпании лимита (Pro — 500 диалогов в месяц). Полагаться на неизвестный код ошибки нельзя, поэтому свой счётчик: число **уникальных клиентов**, которым в текущем календарном месяце по Москве ушло хотя бы одно сообщение (`Outbox.status = SENT`, `sentAt` в границах месяца). Значение кешируется в памяти на 10 минут, показывается в карточке настроек как «Диалогов в этом месяце: N из 500».

Пороги: при 80 % — уведомление владельцу, при 100 % — уведомление владельцу «лимит тарифа исчерпан, сообщения могут не уходить». Одно уведомление на порог на месяц (`Setting wazzup.dialogNotice = {month, pct}`). Жёсткая остановка отправки — настройка `wazzup.stopOnLimit`, **по умолчанию выключена** (вопрос 4): лучше упереться в ошибку провайдера, чем самим перестать писать клиентам из-за неточного счётчика.

Неизвестный код ошибки 4xx трактуется как «не повторять» + уведомление владельцу с кодом как есть: так исчерпание лимита в любом случае станет видно.

### 4.11 Окно чатов: ключ остаётся на сервере

Ссылка на окно запрашивается в серверном компоненте при открытии страницы и передаётся в браузер уже готовой строкой; `WAZZUP_API_KEY` в клиентский бандл не попадает (он читается только в модулях с `import "server-only"`, переменная без префикса `NEXT_PUBLIC_`). Срок жизни ссылки в документации не выяснен, поэтому:

- страницы с окном — `export const dynamic = "force-dynamic"`, ссылка каждый раз новая;
- в панели есть кнопка «Обновить окно» (перезапрос ссылки через server action) на случай, если iframe протух при долгой работе вкладки;
- `<iframe src={url} allow="microphone *; clipboard-write *">` — как требует Wazzup.

Размещение: панель «Чат с клиентом» в карточке брони и карточке клиента (`scope: "card"`, фильтр по основному и дополнительным телефонам клиента, по всем активным типам чатов), страница `/admin/chats` (`scope: "global"`) с пунктом в меню и счётчиком неотвеченных. Доступ — OWNER и ADMIN (вопрос 5); охране окно чатов не показываем.

Счётчик: `GET /api/admin/chats/unanswered` (наш роут, `requireActor(STAFF)`, кеш 30 с в памяти процесса) → `GET /v3/unanswered/<User.id>`. Роль «Руководитель» в кабинете Wazzup администраторам выставляет заказчик при переезде — это шаг инструкции, не код.

Для МФ-3б: когда появятся заголовки безопасности, в CSP нужен `frame-src` на домен Wazzup, иначе окно погаснет. Записано в риски.

### 4.12 Что показывать на сайте

Сайт сейчас предлагает три мессенджера, а писать первыми мы можем только в купленные каналы. Ф14 отдаёт серверный список доступных каналов (`Setting messaging.channels`, обновляется вебхуком и `ensureReady`), а сам файл `BookingCalculator.tsx` правит **последним**, после слияния Ф4 (экран результата) и Ф8 (форма): правка — один проп в сигнатуре и передача его в `ChannelPicker`. Что именно показывать вместо недоступных каналов — вопрос 2, рекомендация в §13.

Главная страница статическая; чтобы значение не замерзало на моменте сборки, на `src/app/page.tsx` ставится `export const revalidate = 300`. Полностью динамической главную не делаем — это лендинг.

### 4.13 Заглушка: код проверяем до пробного периода

`WAZZUP_BASE_URL` по умолчанию `https://api.wazzup24.com/v3`, в тестах — адрес мока. Мок `tests/mocks/wazzup-mock.mjs` — обычный `node:http` сервер: `POST /v3/message` (успех и любой заданный код ошибки), `GET /v3/channels` (состояние канала задаётся на ходу), `PATCH /v3/webhooks` (сразу шлёт нам `{test:true}`), `POST /v3/users`, `POST /v3/iframe`, `GET /v3/unanswered/:id`, плюс служебные ручки «пришли статус» и «пришли входящее». Пробный период в 3 дня начинается только после зелёного прогона против мока.

Все сетевые вызовы — `fetch` с `AbortSignal.timeout` (10 с на отправку, 5 с на служебные). В этой версии Next `fetch` по умолчанию не кешируется (`node_modules/next/dist/docs/01-app/02-guides/caching-without-cache-components.md`), дополнительных опций не нужно; `cache: "no-store"` ставим явно, чтобы не зависеть от будущего включения Cache Components.

```ts
// src/server/messaging/wazzup/adapter.ts
export const wazzupAdapter: MessengerAdapter = {
  code: "wazzup",
  async send({ outboxId, channel, phone, text }) {
    await ensureReady();
    const ch = await pickChannel(channel);
    if (!ch) return { ok: false, retry: true, code: "NO_CHANNEL", message: "нет активного канала" };
    const digits = phone.replace(/\D/g, "");
    const body = ch.transport === "whatsapp" || ch.transport === "wapi"
      ? { channelId: ch.channelId, chatType: "whatsapp", chatId: digits, text, crmMessageId: outboxId }
      : { channelId: ch.channelId, chatType: chatTypeOf(ch.transport), phone: digits, text, crmMessageId: outboxId };
    const r = await api("POST", "/message", body, 10_000);
    if (r.kind === "ok") return { ok: true, providerMessageId: r.json.messageId ?? null };
    if (r.code === "REPEATED_CRM_MESSAGE_ID") return { ok: true, providerMessageId: null }; // уже ушло
    const rule = classify(r);                 // errors.ts
    if (rule.notice) await notifyOnce(rule.notice);
    if (rule.dropChannelCache) resetChannelCache();
    return { ok: false, retry: rule.retry, code: r.code, message: rule.text };
  },
  // …
};
```

## 8. Что Ф14 ждёт от соседних фаз

**От Ф4 шаг 0 (жёсткая зависимость, без неё не отправить ничего):**

1. `src/server/messaging/types.ts` с типами `SendRequest`, `SendResult`, `MessengerAdapter` (§4.2) и `src/server/messaging/registry.ts` с выбором адаптера по `messaging.provider`.
2. `send()` вызывается вне транзакции; результат пишется отдельной короткой транзакцией.
3. `providerMessageId` записывается немедленно после успеха.
4. Раскладка результата: `ok` → `SENT` + `sentAt`; `ok:false, retry:false` → `FAILED` + `lastError`; `ok:false, retry:true` → остаётся `PENDING`, `attempts + 1`, следующая попытка с нарастающей паузой; адаптера нет → `SKIPPED_NO_PROVIDER`.
5. `Outbox.lockedUntil` и аренда записи (двойной отправки быть не должно).
6. Предохранители: не слать сообщения старше N часов, `OUTBOX_ALLOWLIST`, режим «пробно».
7. Честная строка статуса очереди в карточке брони (`bookings/[id]/page.tsx:208`, время по Москве) — Ф14 дописывает к ней только «доставлено» и «прочитано».

**От Ф2б:** `notify(kind, text, bookingId, tx, { key })` с дедупликацией и `AdminNotice.dedupKey`; `/api/admin/notices` для бейджа (Ф14 добавит рядом счётчик неотвеченных). До Ф2б работаем на текущем `notify` с проверкой непрочитанного.

**От МФ-2:** ничего не блокирует. Карточка «Сообщения» дописывается в конец `settings/page.tsx`.

**От Ф8:** форма на сайте. Проп «доступные каналы» вносим после её слияния.

**От пользователя и заказчика:** аккаунт Wazzup с оплаченным тарифом Pro или Max (Inbox не подходит — он не даёт писать первым); публичный HTTPS-адрес, на который Wazzup достучится (вопрос 3).

## 10. Критерии приёмки (что проверит человек глазами)

1. Без `WAZZUP_API_KEY`: `/admin/settings` → карточка «Сообщения» пишет «провайдер не подключён», переключатель недоступен; сообщения в карточке брони стоят как «канал не подключён»; сайт работает как раньше.
2. С ключом заглушки и `messaging.provider = wazzup`: кнопка «Проверить подключение» показывает список каналов, их состояния и время проверки.
3. Заявка с разрешённого номера на stage: сообщение приходит в WhatsApp в течение минуты; в карточке брони — «отправлено», затем «доставлено», затем «прочитано».
4. Клиент отвечает с телефона: текст появляется в ленте брони и в карточке клиента, колокольчик +1, на пункте «Чаты» — 1 неотвеченное.
5. Администратор отвечает из панели «Чат с клиентом» в карточке брони: ответ приходит на телефон, в ленте появляется «ответил {имя}».
6. Канал выключили в кабинете: в течение минуты приходит уведомление «нужно отсканировать QR», карточка настроек краснеет, сайт перестаёт предлагать WhatsApp как канал подтверждения; после восстановления — уведомление «канал снова работает».
7. На странице «Чаты» в исходном коде страницы (view-source) нет ни `WAZZUP_API_KEY`, ни `WAZZUP_WEBHOOK_SECRET`; окно переписки открывается и в нём можно ответить.
8. Запрос на `/api/webhooks/wazzup/<чужой-секрет>` отвечает 404; на правильный адрес с телом `{"test":true}` — 200.
9. `messaging.provider = none`: сообщения копятся в Outbox, ничего не уходит, ошибок в логах нет.
10. Подменили `WAZZUP_API_KEY` и перезапустили контейнер: вебхук и пользователи зарегистрировались сами, каналы нашлись, ручных шагов не потребовалось.
11. Номер клиента не в `OUTBOX_ALLOWLIST`: сообщение не уходит, в карточке видно почему (проверка предохранителя Ф4 через наш адаптер).
12. Счётчик «Диалогов в этом месяце» в карточке настроек совпадает с числом клиентов, которым в этом месяце уходили сообщения.

## 11. Тесты

**Юнит (`tests/unit/wazzup.test.ts`, `node --test`, база не нужна) — по одному на поведение:**

1. `Channel.WHATSAPP` выбирает канал с транспортом `whatsapp`, при его отсутствии — `wapi`.
2. При отсутствии канала нужного транспорта берётся активный WhatsApp, затем Telegram, затем MAX.
3. Транспорт `telegram` (бот) никогда не попадает в список «можем написать первыми».
4. Тело `POST /v3/message` для WhatsApp: `chatId` — цифры без плюса, `crmMessageId` равен `outboxId`.
5. Тело для Telegram и MAX: передаётся `phone`, а не `chatId`.
6. `BAD_CONTACT` → `retry: false` и уведомление администратору.
7. `MESSAGES_NOT_TEXT_FIRST` → `retry: false` и уведомление владельцу.
8. `REPEATED_CRM_MESSAGE_ID` → `{ok: true}` без `providerMessageId`.
9. `CHANNEL_NOT_FOUND` → `retry: true` и сброс кеша каналов.
10. Таймаут и 5xx → `retry: true`.
11. Неизвестный код 4xx → `retry: false` и уведомление владельцу.
12. `message` в результате не содержит ключа и тела ответа.
13. `parseWebhook` разбирает `{test:true}` в событие `test`.
14. `parseWebhook` разбирает пакет из нескольких событий разных видов.
15. `parseWebhook` на мусорном теле возвращает пустой список и не бросает.
16. Ранг статусов: `delivered` после `read` не затирает `read`.
17. `error` после `sent` пишет `failCode` и не переводит Outbox в `FAILED`.
18. Дедупликация входящего: второй вызов с тем же `messageId` не создаёт вторую запись.
19. Эхо с `messageId`, равным нашему `providerMessageId`, в ленту не пишется.
20. Эхо чужого исходящего пишется с `direction: OUT`, `userId: null` и именем в `meta`.
21. Входящее с номера, совпавшего с `extraPhones`, привязывается к клиенту.
22. Входящее с неизвестного номера пишется без клиента и без брони.
23. Уведомление `CLIENT_MESSAGE` не создаётся, пока прежнее не прочитано.

## Независимая критика архитектуры

Вердикт: **годится с правками**. Находок: 19.

### [блокер] Интерфейс адаптера выдуман заново и расходится с уже написанной и отревьюированной архитектурой Ф4 шаг 0. Весь §4.2 и §8 («ожидание к Ф4») требуют от соседа переделать то, что у него уже спроектировано и раскритиковано.

**Чем подтверждается.** Ф14 §4.2/§8: файлы `src/server/messaging/types.ts` и `registry.ts`, тип `MessengerAdapter {code, send, availableChannels, check}`, `SendRequest {outboxId, channel, phone, text}`, поле `Outbox.lockedUntil`. Фактически в репозитории: docs/phases/PHASE_04_SENDER.md §7 — `src/server/automations/adapters/index.ts`, тип `ChannelAdapter {code, channels: Channel[], textLimit, ready(), send(msg, to, signal)}`, `adapters()`; §4 решение 4 — поля аренды называются `claimedAt` и `nextAttemptAt`, никакого `lockedUntil`; §4 решение 14 — «интерфейс адаптера рассчитан на Wazzup и Telegram сразу», `id` записи идёт провайдеру как `crmMessageId`. Ф4 — фаза-предшественник по дорожке Д3 (TZ_STATUS_2026-09-22_night.md §4, «Д3: Ф4 (шаг 0) → Ф14»), значит подстраивается Ф14, а не наоборот.

**Что сделать вместо этого.** Переписать §4.2, §7 и §8 под существующий `ChannelAdapter` в `src/server/automations/adapters/index.ts`: `code: "wazzup"`, `channels: [WHATSAPP, TELEGRAM, MAX]`, `ready()`, `send(msg, to, signal)`. `availableChannels()` и `check()` — не общий интерфейс, а экспорты Wazzup-модуля для сайта и карточки настроек. Поля аренды в §5 называть `claimedAt`/`nextAttemptAt`. Из §8 убрать пункты 1, 2, 5 (это уже сделано) и оставить только то, чего у Ф4 действительно нет: запись `providerMessageId` и карта `textLimit` по каналам.

### [блокер] Обе фазы добавляют значение `MESSAGE_FAILED` в `NoticeKind` — две миграции `ALTER TYPE … ADD VALUE` на одно значение не сольются, вторая упадёт.

**Чем подтверждается.** Ф14 §5, миграция 2: `CLIENT_MESSAGE` и `MESSAGE_FAILED`. PHASE_04_SENDER.md §5 миграция 2 (`ALTER TYPE "NoticeKind" ADD VALUE 'MESSAGE_FAILED'`) и §7, строка `prisma/schema.prisma`: «`NoticeKind` += `MESSAGE_FAILED`». В prisma/schema.prisma:51-56 сейчас есть только BOOKING_REJECTED, CHANNEL_DOWN, CASH_MISMATCH, SHIFT_OPEN. Postgres без `IF NOT EXISTS` на повторе падает, а обе миграции идут в один `integration`.

**Что сделать вместо этого.** Ф14 добавляет только `CLIENT_MESSAGE`. `MESSAGE_FAILED` переносится в §8 «что Ф14 ждёт от Ф4» как готовое значение. То же самое проверить по `Outbox`: Ф14 добавляет `providerMessageId/deliveredAt/readAt/failCode`, Ф4 — `claimedAt/nextAttemptAt` и два значения `OutboxStatus`; поля не пересекаются, но обе миграции трогают одну модель — записать в §5, кто чьи поля не трогает.

### [блокер] «Нет активного канала» решается в двух местах по-разному, и уведомления об ошибках отправки создаются дважды. Прямое нарушение правила «одно правило в одном месте».

**Чем подтверждается.** Ф14 §4.3: нет активного канала → `{ok:false, retry:true, code:"NO_CHANNEL"}`, «сообщение ждёт». Ф14 §4.2 п.5: «адаптер сам создаёт уведомления администратору по ошибкам отправки». У соседа: PHASE_04_SENDER.md §4 решение 6 и §5 (таблица статусов) — «нет адаптера или канал не подключён» = терминальный `SKIPPED_NO_PROVIDER`, а §4 п.12 и набросок `sender.ts` в §7 сами шлют `notify("MESSAGE_FAILED", …)` при окончательном провале. Критика Ф4 (в конце PHASE_04_SENDER.md, блокер про SKIPPED_NO_PROVIDER) уже постановила: «adapter.ready() === false и коды «канал недоступен» → PENDING + nextAttemptAt … без расхода попытки; уведомление администратору один раз на смену состояния». Итог как написано сейчас: BAD_CONTACT даёт два уведомления (адаптерное «позвоните клиенту» + MESSAGE_FAILED отправщика), а «канала нет» даёт то терминальный статус, то вечное ожидание — в зависимости от того, где сработало.

**Что сделать вместо этого.** Один путь: состояние каналов проверяет `ready()` до транзакции; false → отправщик откладывает запись без расхода попытки (правка уже заложена в критике Ф4). В `send()` `NO_CHANNEL` остаётся только как гонка и тоже даёт «отложить». Уведомления: адаптер создаёт только те, о которых отправщик знать не может (тариф `MESSAGES_NOT_TEXT_FIRST`, `MESSAGES_IS_SPAM`, состояние канала `CHANNEL_DOWN`); `MESSAGE_FAILED` «позвоните клиенту» остаётся целиком за Ф4, адаптер отдаёт ему только `code` и человеческую строку.

### [важно] `ensureReady()` вызывается внутри `send()` — это до трёх сетевых запросов под чужим таймаутом; первая отправка после каждого рестарта будет падать по таймауту, а бюджет прохода отправщика поедет.

**Чем подтверждается.** Ф14 §7, набросок `adapter.send`: первая строка `await ensureReady()`; §4.5 «вызывается перед первой отправкой в процессе». `ensureReady` делает `PATCH /v3/webhooks` + `POST /v3/users` + (через `pickChannel`) `GET /v3/channels`. У Ф4: PHASE_04_SENDER.md §6 — `sender.timeoutMs = 10000`, `sender.budgetMs = 30000`; §7 — `adapter.send(msg, target, AbortSignal.timeout(cfg.timeoutMs))`. Интерфейс Ф14 вообще не принимает `AbortSignal` и ставит свои таймауты (§4.13: 10 с и 5 с), то есть адаптер игнорирует сигнал вызывающего. Критика Ф4 отдельно требует: `ready()` с таймаутом собирается ДО открытия транзакции.

**Что сделать вместо этого.** `ensureReady()` вызывать только из `ready()` (раз за проход, до BEGIN) и из server actions страниц «Чаты» и «Проверить подключение». `send()` делает ровно один сетевой вызов и обязан уважать переданный `AbortSignal` (свой таймаут — только если сигнала нет). Записать это в §4.5 и в §8 как контракт.

### [важно] Клиент может получить одно и то же сообщение дважды: защита `crmMessageId` живёт 60 секунд, а повторы отправщика идут через 1, 5 и 25 минут. В §9 этого риска нет.

**Чем подтверждается.** docs/WAZZUP_INTEGRATION.md §2: «`crmMessageId` защищает от дублей: повтор с тем же значением **в течение 60 секунд** отклоняется (`REPEATED_CRM_MESSAGE_ID`)». PHASE_04_SENDER.md §4 решение 12: «паузы 1 → 5 → 25 минут», §7 `backoffMs`. Ф14 §4.13 ставит таймаут 10 с на отправку; сетевой таймаут не означает, что сообщение не ушло. Вторая попытка идёт ровно на границе окна, третья — заведомо за ним, и клиент получает второе «Место забронировано». Ф14 §7 трактует `REPEATED_CRM_MESSAGE_ID` как «уже ушло» — это верно только внутри минуты.

**Что сделать вместо этого.** Добавить в §9 строку и решение: при неопределённом исходе (таймаут, обрыв, 5xx без тела) перед повтором сверяться с провайдером либо помечать запись как отправленную с пометкой «исход неизвестен» и не повторять сообщения-подтверждения. Минимум — честно записать остаточный риск и завести юнит-тест «таймаут на первой попытке не приводит к повтору за пределами окна дедупликации».

### [важно] `providerMessageId` в действительности никто не пишет, а без него весь блок статусов (§4.7) мёртв: каждый статус будет «сиротой».

**Чем подтверждается.** Ф14 §8 п.3 требует от Ф4 писать `providerMessageId` «немедленно». В PHASE_04_SENDER.md §7 набросок успеха: `data: { status: "SENT", sentAt, claimedAt: null, lastError: null }` — поля нет; в типе `SendResult` у Ф4 это `providerId?`, а не `providerMessageId`. Плюс сам Ф14 §7 на `REPEATED_CRM_MESSAGE_ID` возвращает `{ok:true, providerMessageId: null}` — систематический случай записи без идентификатора, и §4.7 её никогда не найдёт.

**Что сделать вместо этого.** Сформулировать это как конкретную правку к Ф4 (одно поле в `SendResult`, одна строка в `update`), а не как общее «ожидание». Для `REPEATED_CRM_MESSAGE_ID` решить явно: либо доставать `messageId` повторным запросом, либо записывать «доставка по этой записи не отслеживается» и так и показывать в карточке, чтобы администратор не ждал галочек.

### [важно] Потерян `textLimit`, хотя именно Ф14 обязан его знать: у Wazzup лимит зависит от канала, а не от адаптера.

**Чем подтверждается.** docs/WAZZUP_INTEGRATION.md §2: «Длина текста: WhatsApp до 10 000 символов, Telegram до 1 024, MAX до 4 096». PHASE_04_SENDER.md §4 решение 14 и §7: у `ChannelAdapter` есть `textLimit: number | null`, `decide()` отбраковывает длинное до вызова адаптера (тест 13 в §11). В интерфейсе Ф14 (§4.2) поля нет вовсе, в тестах §11 длины тоже нет. При этом один адаптер Wazzup обслуживает три канала с тремя разными лимитами — общий `textLimit` у Ф4 для него неверен.

**Что сделать вместо этого.** Добавить в §4.2/§8: адаптер отдаёт не число, а карту `channel → textLimit` (или `textLimit(channel)`), и это отдельное ожидание к Ф4 — поправить его `decide()`. Юнит-тест: текст 1 200 символов для TELEGRAM отбраковывается, для WHATSAPP уходит.

### [важно] На пустой базе и при аварии канала сайт остаётся вообще без мессенджеров — форма заявки перестаёт работать ровно тогда, когда это дороже всего.

**Чем подтверждается.** Ф14 §6: `messaging.channels` по умолчанию `{}`; `messaging.provider` по умолчанию `"none"` «в том числе на stage». §4.12: сайт показывает «только те каналы, по которым мы реально можем написать первыми», список берётся из этого снимка. §10 критерий 6 прямо ждёт: «сайт перестаёт предлагать WhatsApp». В коде `src/components/ChannelPicker.tsx:33-40` выбор канала обязателен (`invalid`, `aria-required` через `BookingCalculator.tsx:349`) — при пустом списке клиент не сможет отправить заявку вовсе. Первый запуск на бою и любой `qridle` дают ровно это состояние.

**Что сделать вместо этого.** Разделить два понятия: «что показываем на сайте» (настройка владельца, по умолчанию WhatsApp, не зависит от состояния канала) и «куда реально ушло сообщение» (снимок каналов, влияет только на очередь и уведомления). Написан параллельно с Ф4ш0 (отправщик — в соседней дорожке). Настоящий Wazzup не трогался: весь код проверен против заглушки `tests/mocks/wazzup-mock.mjs`.

**Как решены находки критики.**
- Интерфейс — по карте (решение оркестратора), а не `ChannelAdapter` из PHASE_04 §7.
- `MESSAGE_FAILED`: миграция enum с `ADD VALUE IF NOT EXISTS` — вторая из двух (Ф4ш0 и Ф14) становится пустой при любом порядке; в `schema.prisma` одна и та же строка.
- Уведомления адаптера — только то, чего отправщик знать не может (тариф `MESSAGES_NOT_TEXT_FIRST`, спам, баланс WABA, ключ 401, незнакомый 4xx с кодом как есть, смена состояния канала). «Позвоните клиенту» по окончательной ошибке (`BAD_CONTACT` и т.п.) — за Ф4 (`MESSAGE_FAILED`). Асинхронный статус `error` после отправки даёт то же `MESSAGE_FAILED` (один раз на запись), Outbox остаётся `SENT`, в карточке — «не доставлено (КОД)».
- `ensureReady()` нет: `send()` делает один сетевой вызов (плюс `GET /v3/channels`, если кеш каналов старше 5 минут), под сигналом отправщика. Вебхук регистрирует **только кнопка владельца** («Подключить вебхук и пользователей») и только на явный публичный https `WAZZUP_WEBHOOK_BASE` (localhost — лишь в тестовом режиме против заглушки). Пользователи CRM (владелец и администраторы, без охраны) передаются той же кнопкой и сами перед открытием окна чатов — идемпотентно по хешу списка и ключа.
- Дубль после 60 с: `classify()` помечает таймаут, обрыв и 5xx как `uncertain` (исход неизвестен). Адаптер повтор не решает — остаточный риск второго сообщения при повторе отправщиком за пределами окна `crmMessageId` остаётся и передан Ф4 (решение по типам сообщений — у отправщика).
- `REPEATED_CRM_MESSAGE_ID` → `{ok:true, providerMessageId:null}`: доставка по такой записи не отслеживается (отметок «доставлено/прочитано» у неё не будет).
- Подмены мессенджера нет (вопрос пользователю): канал выбранного транспорта не работает → `retry` (`CHANNEL_DOWN`), канала такого транспорта нет → не повторять (`CHANNEL_ABSENT`, «клиент выбрал Telegram, а такого канала в Wazzup нет»).
- Сайт: `siteChannelsFrom` — при `provider = none` или пустом снимке список не сужается; купленный канал в аварии со страницы не пропадает (убрать — решение человека); `BookingCalculator.tsx` и `page.tsx` не тронуты, главная остаётся статической — `ChannelPicker` сам берёт список из `/api/public/channels` в браузере.
- `webhook-auth.ts` — обёртка над `cronSecretOk` с минимальной длиной 32 (у `cronSecretOk` появился необязательный параметр `min`), одна реализация.
- Вебхук: без сна на «сиротах» (статус без записи — в лог и мимо), упавшее событие — сырым JSON в лог для ручного внесения, ответ всегда 200; время `dateTime` без пояса читается как UTC.
- Эхо нашего же сообщения, пришедшее раньше, чем Ф4 запишет `providerMessageId`, отсекается памятью процесса (последние отправленные `messageId`, 10 минут).
- Счётчик диалогов — нижняя оценка (клиент без карточки считается по телефону брони), пороги 80/100 % — одно уведомление на порог за месяц. `wazzup.stopOnLimit` не сделан: рекомендация «не останавливать» принята, выключатель без потребителя не заводим.

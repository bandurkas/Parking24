# Ф9а. Убрать ручное время (дорожка Д2, первая)

Архитектура. Код по этому документу пишет другой агент. Основание: ТЗ §3.3, `docs/TZ_2026-09-21_PLAN.md` §1 (решение 22.09 «ручное время убираем совсем») и решение 23.09 №5 («забытый заезд или выезд — через „Исправить статус“ датой без времени»). Срочность: `docs/TZ_STATUS_2026-09-22_night.md` §2 п.1 — дыра с деньгами на stage.

Код разрезан 23.09 (`19cc5f2`): `src/server/services/bookings/{create,transition,correct,payments,edit,queries,shared,index}.ts`. Номера строк в документах сверки относятся к старому `bookings.ts` — ищем по именам функций.

## 1. Цель

Убрать у администратора и охраны всякую возможность назвать время заезда или выезда: время события ставит сервер в момент нажатия. Забытую отметку администратор проставляет через «Исправить статус» — календарной датой без времени, с обязательной причиной и записью в ленту и журнал.

## 2. Зачем именно сейчас

Сегодня `transitionAction` принимает произвольный момент `at` от любой роли, включая охрану (`src/app/admin/actions/bookings.ts:45-48`). Нижней границы у него нет: с `ff68709` проверяется только «не в будущем» (`transition.ts:30`) и «в перестое — только текущими сутками» (`transition.ts:43-45`). Вне перестоя выезд можно поставить хоть раньше заезда.

Цепочка потери денег: выезд задним числом → меньше `actualDays` (`transition.ts:55`) → баннер «Стоянка по факту» → «Пересчитать по факту» без причины, доступно ADMIN (`payments.ts`, `decideRecalc`) → появляется переплата → администратор возвращает её наличными (причина нужна только у возврата). Плюс окно 00:00–01:00 по Москве: бронь с `dateTo = вчера` ещё не в перестое, и ограничение «текущими сутками» её не защищает.

Важно: убрать поле из интерфейса недостаточно. Серверное действие — публичная точка входа, его можно вызвать POST-ом мимо интерфейса (`node_modules/next/dist/docs/01-app/02-guides/server-actions.md`: «A Server Action runs as a POST request against the page that invokes it… Treat every action as an untrusted entry point»). Поэтому параметр удаляется из сигнатуры действия и из сигнатуры сервиса, а не прячется в UI.

## 3. Что входит

1. `transition` и `transitionAction` больше не принимают время. Момент события — `new Date()` внутри транзакции под блокировкой строки.
2. Из интерфейса исчезают: форма `datetime-local` в `TransitionButtons`, `window.prompt` про время при перетаскивании на доске, подсказка «Перестой: выезд — текущими сутками».
3. «Исправить статус» получает поля даты: «Дата заезда» и «Дата выезда» — показываются только когда исправление впервые проставляет соответствующую отметку. Дата обязательна, время не спрашивается.
4. Два новых поля-признака в `Booking`: отметка проставлена датой без времени. По ним карточка, полоса этапов и шаблоны сообщений показывают дату без времени, а не «12:00».
5. Проверки дат исправления: формат, не в будущем по Москве, выезд не раньше заезда (с учётом уже сохранённой второй отметки).
6. Правится текст записи в ленте и в журнале у исправления: видно, какую дату поставили.
7. Удаляется ставшее недостижимым правило `checkoutDateAllowed` и его тест.
8. Тесты: новые юнит на чистые правила, новый e2e-файл фазы, правка `crm-pipeline.mjs` и `overstay.mjs`.

## 4. Что НЕ входит (границы с соседями, §4 сверки)

- **Деньги от исправления — Ф10.** `correctStatus` как не считал `actualDays`, так и не считает. Значит после исправления датой баннер «Стоянка по факту» не появляется, пересчёт не предлагается, возврат сам собой не возникает. Начисление перестоя исправление по-прежнему не делает (это узаконенный путь для забытого выезда, решение 22.09). Ф10 решает: считать ли `actualDays` по датам исправления, «Исправить статус» из «Выехал» — только владелец, сторно платежа, остаток переплаты.
- **Занятость и потолок 405 — Ф3.** Ф9а не трогает `occupancy.ts`, `createBooking`, `updateBooking`, `quoteAction`.
- **Табло «Планируют выезд», фильтр, подписи кнопок, время в журнале — Ф9б.** Ф9а не меняет `labels.ts`, `today/page.tsx`, `GuardScreen`, `BookingsTable`, `Clock`, `audit/page`.
- **Тексты сообщений клиенту и отправка — Ф4/Ф5.** Ф9а делает в `dispatcher.ts` ровно одну правку (см. §7.10) — чтобы подстановка `{{booking.checkedInAt}}` не показывала выдуманное «12:00».
- **Уведомления администратору, колокольчик — Ф2б.**
- **`plannedMoment` как окно 24 ч — Ф3/Ф7.** Ф9а пользуется этой функцией, но её поведение не меняет.

## 5. Решения

### 5.1. Время события — всегда серверное «сейчас»
Выбрано: `const at = new Date()` внутри транзакции, после `lockBooking`. Отвергнуто: оставить `at` «только для владельца» — ровно та же дыра, просто у одной роли; и оставить `at` «в пределах текущих суток» — правило пришлось бы держать в двух местах (переход и исправление), а ТЗ §3.3 просит «фиксировать фактическое время перемещения карточки», то есть ровно момент нажатия.

### 5.2. Забытая отметка — дата без времени, через «Исправить статус»
Выбрано: решение пользователя 23.09 №5. Путь уже существует: `correctStatus` требует роль ADMIN или OWNER, обязательную причину, не запускает автоматизаций и отменяет запланированные сообщения. Отвергнуто: «время исправления с пометкой» (в карточке стоял бы заведомо неверный час) и «отдельная кнопка забытого заезда» (второй путь к той же записи, против правила «одно правило в одном месте»).

### 5.3. Как хранить «дату без времени»
Выбрано: в те же `checkedInAt` / `checkedOutAt` пишется **12:00 по Москве** этой даты (`plannedMoment(iso)`, у которого время по умолчанию как раз `12:00`), плюс булев признак `checkedInDateOnly` / `checkedOutDateOnly`.

Почему полдень, а не полночь: `actualParkingDays` в ветке перестоя считает день через `overstayDayIso`, то есть со сдвигом на льготный час (−60 мин). Отметка «00:00 по Москве» уехала бы во вчерашний день и втихую сняла сутки. Полдень безопасен при любом сдвиге в пределах ±11 часов и совпадает с уже принятым в проекте умолчанием (`fmtDayTime`, `plannedMoment`).

Отвергнуто: отдельные колонки `@db.Date` рядом с `checkedInAt`. Тогда у «когда заехал» стало бы два источника, и каждый потребитель (карточка, отчёт Ф12, `actualParkingDays`, шаблоны сообщений) должен был бы знать про оба — прямое нарушение «одно правило в одном месте».

Отвергнуто: обойтись без признака и вычислять «время неизвестно» из ленты — отображение полезло бы в чужую таблицу.

### 5.4. Какие даты спрашивать
Правило: спрашиваем дату только для той отметки, которую это исправление проставляет **впервые**. Если отметка уже есть и целевой статус её сохраняет — не спрашиваем и не трогаем.

- «Ожидает оплаты»/«Подтверждена» → «Заехал»: одна дата — заезда.
- «Заехал» → «Выехал»: одна дата — выезда.
- «Выехал» → «Заехал» (откат ошибки, в том числе кнопкой «Отменить» на доске): дат не спрашиваем, `checkedInAt` сохраняется, `checkedOutAt` снимается.
- Любой статус → «Ожидает оплаты»/«Подтверждена»/«Отменена»/«Не приехал»/«Отклонена»: дат не спрашиваем, отметки снимаются как сейчас.
- «Ожидает оплаты» → «Выехал» (забыли и заезд, и выезд): спрашиваем **обе** даты. Сейчас в этом случае `checkedInAt` остаётся пустым (сверка §3, Ф10) — оставлять полупустую запись, когда единственный источник времени именно эти поля, нельзя. См. вопрос 2.

### 5.5. Границы дат
Проверяем: формат `ГГГГ-ММ-ДД`; дата не в будущем по Москве; выезд не раньше заезда — причём вторая дата берётся из уже сохранённой отметки, если её не спрашивали. Это и есть закрытие дыры «выезд раньше заезда» на новом пути. Нижней границы («не раньше даты создания брони») пока нет — см. вопрос 3.

### 5.6. Выключателя в `Setting` не добавляем
Правило проекта требует выключатель для **нового автоматического поведения**. Автоматическая простановка времени уже работает (`at` по умолчанию = сейчас); фаза убирает ручной ввод, то есть снимает возможность, а не добавляет автоматизацию. Новых фоновых действий, сканов и отправок фаза не создаёт. Выключатель здесь означал бы «вернуть дыру с деньгами одним тумблером» — не делаем. Код-агент не должен придумывать ключ настройки.

### 5.7. `checkoutDateAllowed` удаляем
После §5.1 `overstayDayIso(at) === overstayDayIso(now)` тождественно, проверка не может сработать ни при каких данных. Оставлять непроверяемую ветку и тест к ней — создавать ложное ощущение защиты. Функция, её вызов, юнит-тест (`tests/unit/overstay.test.ts:68-77`) и e2e-проверки отказа удаляются. Смысл правила переезжает в §5.5: он теперь про даты исправления.

Честно про остаток риска: администратор по-прежнему может закрыть забытый выезд прошедшей датой и тем самым не начислить перестой. Это сознательно разрешённый решением 22.09 путь, и он обставлен: только ADMIN/OWNER, обязательная причина, строка в ленте «Перестой N сут. не начислен (X ₽) · причина», запись в журнал. Ужесточение (только владелец) — вопрос 5 и смежный вопрос Ф10.

### 5.8. Старые брони не трогаем
Миграция только добавляет два поля со значением по умолчанию `false`. Существующие `checkedInAt` / `checkedOutAt`, `actualDays`, `days`, `amount` не пересчитываются (правило PLAN §3). Такие брони показываются ровно как сегодня — с временем. Старые строки ленты с текстом «· по факту 21 сент, 14:05» остаются как исторический текст. Отдельно предлагается разовая **проверка чтением** на stage (§10) — см. вопрос 6.

### 5.9. Что увидит охрана
Ничего нового. `GuardScreen` уже вызывает `transitionAction(r.id, to)` без времени (`GuardScreen.tsx:35`) — одно нажатие, время ставит сервер. Формы времени охрана не видела и раньше (`TransitionButtons` на экране КПП не используется). «Исправить статус» охране недоступно и остаётся недоступным (`correct.ts:15`). Практическое следствие для смены: забытый заезд охрана не чинит — зовёт администратора, как и сегодня.

### 5.10. Одно нажатие вместо двух
Раньше «Заехал»/«Выехал» в карточке открывали форму и требовали второго нажатия. Теперь статус меняется сразу. Для охраны ничего не меняется, для администратора становится на шаг короче. Риск промаха и что с ним делаем — §9 п.1 и вопрос 1.

### 7.1. `src/lib/moscow.ts` — новый
Одно определение московской календарной даты на клиент и сервер. Сегодня `moscowIso` живёт в `src/server/lib/dates.ts`, а клиентской форме исправления нужен тот же «сегодня» для `max` у поля даты.

```ts
export const MOSCOW_TZ = "Europe/Moscow";
// Календарная дата момента по Москве: сутки парковки, перестой и «сегодня» считаются по ней, а не по UTC сервера
export function moscowIso(d: Date, tz: string = MOSCOW_TZ): string {
  return new Intl.DateTimeFormat("en-CA", { timeZone: tz, year: "numeric", month: "2-digit", day: "2-digit" }).format(d);
}
export function moscowToday(tz: string = MOSCOW_TZ): string {
  return moscowIso(new Date(), tz);
}
```

### 7.3. `src/lib/correction.ts` — новый
Чистые правила «Исправить статус»: какие даты спросить и допустимы ли они. Клиент-безопасный модуль (без `server-only`), потому что форма показывает ровно те же поля, что требует сервер. Одно правило в одном месте.

```ts
import type { BookingStatus } from "@prisma/client";

// Ранг статуса: исправление в статус ранга < 3 снимает отметку заезда, < 4 — отметку выезда (как было в correctStatus)
export const STATUS_RANK: Record<BookingStatus, number> = {
  NEW: 0, AWAITING_PAYMENT: 1, CONFIRMED: 2, CHECKED_IN: 3, CHECKED_OUT: 4, CANCELLED: 9, NO_SHOW: 9, REJECTED: 9,
};

export type Marks = { checkedIn: boolean; checkedOut: boolean };

// Даты спрашиваем только у тех отметок, которые исправление ставит впервые
export function neededDates(to: BookingStatus, has: Marks): { in: boolean; out: boolean } {
  const keepIn = has.checkedIn && STATUS_RANK[to] >= 3;
  const keepOut = has.checkedOut && STATUS_RANK[to] >= 4;
  return {
    in: (to === "CHECKED_IN" || to === "CHECKED_OUT") && !keepIn,
    out: to === "CHECKED_OUT" && !keepOut,
  };
}

// Текст ошибки или null. today — московская дата
export function checkDates(d: { in?: string; out?: string }, today: string): string | null {
  const re = /^\d{4}-\d{2}-\d{2}$/;
  for (const [what, v] of [["заезда", d.in], ["выезда", d.out]] as const) {
    if (v === undefined) continue;
    if (!re.test(v)) return `Дата ${what} в формате ГГГГ-ММ-ДД`;
    if (v > today) return `Дата ${what} не может быть в будущем`;
  }
  if (d.in && d.out && d.out < d.in) return "Выезд не может быть раньше заезда";
  return null;
}
```

## 9. Риски

1. **Промах мимо кнопки теперь сразу меняет статус, а в перестое сразу начисляет сутки.** Раньше спасала вторая кнопка в форме времени. Что делаем: на доске остаётся тост «Отменить» на 8 секунд, в карточке — «Исправить статус»; начисление снимается `waiveOverstay` с причиной. Нужно ли подтверждение перед «Выехал» — вопрос 1.
2. **`dispatcher.ts` общий с Ф5.** Одна строка, конфликт разрешается дописыванием. Записано в §7.10 и в комментарии рядом.
3. **`correct.ts` общий с Ф10.** По §4 сверки Ф10 идёт после Ф9а и строится поверх дат исправления. Ф9а не трогает `actualDays`, `decideRecalc`, `waiveOverstay`, `addPayment` — денежная часть остаётся нетронутой.
4. **Часовой пояс контейнера не московский** (`TZ=Europe/Moscow` — это МФ-3б). Все новые вычисления идут через `moscowIso` / `plannedMoment`, где пояс задан явно. Запрещено: `new Date("2026-09-21")`, `toLocaleDateString()` без `timeZone`, `d.getDate()`.
5. **Отметка «дата без времени» и льготный час.** Полдень выбран именно чтобы `overstayDayIso` не сдвинул день (§5.3). Юнит-тест это фиксирует.
6. **Деньги после исправления датой не двигаются** — `actualDays` не считается, баннер пересчёта не появляется. Это сознательная граница с Ф10, а не забытая ветка. Вопрос 4.
7. **e2e и полночь.** `overstay.mjs` уже нельзя гонять с 00:00 до 01:00 МСК; новый файл фазы использует даты относительно московского «сегодня» (`moscowPlus`) и ту же оговорку в шапке.
8. **Старые брони с уже кривым ручным временем.** Фаза их не чинит. Проверка чтением — §10, вопрос 6.

## 10. Критерии приёмки (что человек проверяет глазами)

1. Карточка брони в «Ожидает оплаты»: нажатие «Заехал» меняет статус сразу, поля времени нет. В полосе этапов у «Заехал» стоит сегодняшняя дата и текущее московское время.

3. Экран охраны (`/admin/today?guard=1`): всё как раньше — одно нажатие «Заехал»/«Выехал», никаких новых окон.

10. Старая бронь на stage, у которой время было проставлено вручную до выкатки, показывает его точно так же, как показывала.

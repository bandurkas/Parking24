# Ф1. Планировщик: минутный тик

Статус: **архитектура v2, критика учтена** (22.09.2026). Далее — код.

Порядок фазы (`docs/TZ_2026-09-21_PLAN.md` §5а): архитектура → критика → код → тесты → ревью → stage.

## 1. Зачем

Половина ТЗ завязана на время, а не на действие человека: перестой после даты выезда (Ф2), напоминание за 24 часа, «не приехали» через 24 часа, автопереход в «Не приехал» через 48 часов (Ф7), позже — отправка сообщений (Ф4). Сейчас в системе нет ничего, что просыпалось бы само: `RUN_SCHEDULER` на stage стоит в `1`, но код его не читает, `src/instrumentation.ts` и `/api/cron` нет.

Ф1 делает основу: процесс сервера раз в минуту запускает список задач («сканов»), и видно, что он жив. **Сканов, которые что-то меняют у клиентов или в бронях, в Ф1 нет.** Первый появится в Ф2 (перестой).

## 2. Что входит и что нет

**Входит:**
- минутный тик внутри процесса сервера (`src/instrumentation.ts`);
- защита от двойной работы: флаг в процессе и блокировка в базе;
- реестр сканов с контрактом (п. 5) и режимами «выкл / пробно / вкл»; в Ф1 реестр пустой;
- «пульс» — запись под той же блокировкой после каждого тика: так блокировка и транзакции реально работают на stage уже в Ф1;
- карточка «Планировщик» в настройках владельца: состояние, время последнего тика по Москве, упавшие сканы, **кнопка паузы** (аварийная остановка обоих входов без правки `.env`);
- запасной вход `POST /api/cron/automations` с секретом — для e2e и на случай аварии;
- исключение `/api/cron` из Basic Auth в `src/proxy.ts`;
- тесты, запись в `tests/README.md`.

**Не входит:** сканы с действиями (Ф2, Ф7); отправка сообщений (Ф4); интерфейс режимов сканов (появится в Ф2 вместе с первым сканом); уведомление в колокольчик, если планировщик встал (сторож должен быть вне тика — вопрос на будущее); вторая реплика сервера.

## 3. Как это работает

```
старт сервера → register()   [src/instrumentation.ts]
  1-я строка: NEXT_RUNTIME !== "nodejs" → return   (литерал: иначе Prisma попадёт в Edge-сборку)
  try { import scheduler → bootScheduler() }
          ├─ секрет крона короче 16 → предупреждение в лог (при любом RUN_SCHEDULER)
          └─ RUN_SCHEDULER === "1" → startScheduler(): первый тик через 15 с, дальше каждые 60 с после окончания предыдущего

runTick(source)            [таймер или HTTP, один и тот же код]
  ├─ в процессе уже идёт тик → { busy }            (пульс не пишется)
  ├─ настройки: пауза, режимы сканов  (ошибка базы → failed:["config"], выход)
  ├─ пауза → сканы не запускаются
  ├─ каждый скан с режимом ≠ "выкл": своя транзакция
  │     ├─ pg_try_advisory_xact_lock не взят → { busy }, выход без пульса
  │     ├─ «вкл»    → run(tx, now) → число в done
  │     ├─ «пробно» → run(tx, now) → откат транзакции → число в dry
  │     └─ ошибка   → код скана в failed, остальные сканы идут дальше
  └─ пульс: своя транзакция под той же блокировкой → Setting "scheduler.heartbeat"

POST /api/cron/automations   заголовок X-Cron-Secret
  неверный / короткий секрет → 404;  верный → 200 + результат тика (JSON с полем at)
```

## 4. Решения

1. **Файл — `src/instrumentation.ts`.** В проекте есть `src/`, поэтому по документации Next 16 файл кладётся туда. `register()` вызывается один раз на процесс, сразу при старте, до первого запроса; при `next build` не вызывается (проверено критиком на standalone и dev).
2. **Первая строка `register()` — литеральная проверка `process.env.NEXT_RUNTIME !== "nodejs"`**, до любого `import`. Next собирает этот файл и для Edge; если спрятать проверку в функцию, бандлер не выбросит ветку, и модуль с Prisma и `node:crypto` попадёт в Edge-сборку с предупреждениями.
3. **`register()` целиком в try/catch.** Если он бросит, сервер стартует, но отвечает 500 на все запросы до перезапуска, а контейнер выглядит живым.
4. **Выключатель запуска — `RUN_SCHEDULER === "1"`.** Любое другое значение — таймера нет. Локально и в e2e `0`, на stage `1`. HTTP-вход от него не зависит (он нужен e2e как раз при `0`).
5. **Пауза — `Setting "scheduler.paused"`**, кнопка у владельца. Проверяется в каждом тике, для обоих входов. Это аварийная остановка без правки `.env` и перезапуска. На паузе тик не запускает сканы, но пишет пульс с отметкой «пауза».
6. **Цепочка `setTimeout`, а не `setInterval`.** Следующий тик заводится в `finally` предыдущего. Next 16 сам ловит `unhandledRejection` и `uncaughtException` (процесс не падает), поэтому настоящий риск другой: исключение до перезавода таймера — и тик умирает навсегда при живом процессе. Отсюда `void runTick().catch(log).finally(rearm)`, а `runTick` по контракту не бросает.
7. **Состояние планировщика — всегда в `globalThis`, без условий.** В одном процессе модуль планировщика загружается дважды: бандл instrumentation и бандл маршрутов исполняют его отдельно (проверено критиком). Флаг занятости, таймер и журнал ошибок должны быть общими для обоих, поэтому лежат в `globalThis.__p24Scheduler`. Шаблон из `prisma.ts` (запись в `globalThis` только вне production) здесь не подходит.
8. **Свой клиент базы у планировщика** — `new PrismaClient({ log: [] })`, лимит соединений 2, в том же `globalThis`. Основной клиент печатает каждую ошибку многострочным `prisma:error`, и при лежащей базе лог забивался бы каждую минуту. Свой пул заодно не отнимает соединения у сайта.
9. **На верхнем уровне `scheduler.ts` ничего не выполняется** — ни лога, ни таймера, ни клиента базы. `next build` исполняет модули маршрутов (критик видел три исполнения), а `route.ts` импортирует планировщик.
10. **Одна транзакция на скан, блокировка на каждый скан.** Ошибка Postgres переводит транзакцию в «aborted», соседние сканы в ней упали бы. Блокировка `pg_try_advisory_xact_lock(24_0922)` (отличается от блокировки занятости `24_0921`) гарантирует «один скан одновременно», а не «один тик»: между сканами может вклиниться другой процесс. Это безвредно при идемпотентных сканах (п. 5). Второй процесс в нашей схеме появляется не при выкатке (compose гасит старый контейнер до старта нового), а, например, от `docker compose run web …`, который тоже стартует `server.js` с `RUN_SCHEDULER=1`. Блокировка дешёвая — оставляем.
11. **Таймаут транзакции скана 30 с, ожидание соединения 10 с** (у Prisma по умолчанию 5 с). Таймаут Prisma не прерывает зависший запрос, поэтому сразу после взятия блокировки — `SET LOCAL statement_timeout = '25s'` и `lock_timeout = '10s'` (находка ревью).
12. **Пульс пишется под блокировкой отдельной транзакцией после сканов.** Так в Ф1 каждую минуту реально берётся блокировка, и «Работает» значит «транзакция под блокировкой прошла». Тик, ответивший `busy`, пульс не пишет — иначе HTTP-вызов посреди таймерного тика затёр бы его результат. Значение: `{ at, source, ms, done, dry, failed, paused }`.
13. **Журнал ошибок — по смене состояния.** Первая ошибка по ключу печатается, повторы молча считаются, при восстановлении печатается «снова работает, пропущено N». Проще троттлинга по времени и даёт строку о восстановлении.
14. **Запасной вход.** Только `POST`; неверный или короткий секрет — 404 (`GET` отдаёт 405 — маршрут не скрыт, защищает только секрет). Сравнение через sha256 обеих строк и `timingSafeEqual`. Секрет короче 16 — вход выключен. Секрет на stage — 32 символа, **локальный — 15, перевыпускаем**. Без `export const runtime` и `dynamic`: `nodejs` и так по умолчанию, `POST` не кэшируется, а `dynamic` сломает сборку при включении `cacheComponents`.
15. **`/api/cron` мимо Basic Auth** в `src/proxy.ts`, точным сравнением: `pathname === "/api/cron" || pathname.startsWith("/api/cron/")`.
16. **Тестируемое ядро отдельно.** `tick-core.ts` без `server-only` и без Prisma: логика тика, режимы, журнал ошибок, `shouldStartScheduler`, разбор пульса и его состояние для карточки. Блокировка, чтение настроек и запись пульса подставляются. `settings.ts` только читает строки из базы.
17. **В dev таймер работает на коде, загруженном при старте**: `register()` после правок не перевызывается, а HTTP-вход уже на новом коде. Записать в `tests/README.md`; для проверки нового скана в dev — перезапуск или вызов через HTTP.

## 5. Контракт скана (для Ф2 и дальше)

- Сигнатура `run(tx, now) => число сделанного`. `now` приходит снаружи — скан не зовёт `new Date()`, чтобы тесты подставляли время.
- **Идемпотентный и «догоняющий»**: условие «момент прошёл, а действия ещё нет», а не «момент попал в последнюю минуту». Пропущенный тик, перезапуск или простой базы не теряют действий, повторный запуск не дублирует.
- **Внутри транзакции — только запись в базу**, никаких внешних вызовов. Отправка сообщений (Ф4) — отдельный шаг вне транзакции скана, иначе дубли при откате и долгая блокировка.
- **Лимит объектов за один вызов** (порядка 50): старые брони на stage не должны упереться в таймаут 30 с; остальное доберёт следующий тик.
- Нужна блокировка занятости (`OCCUPANCY_LOCK`) — брать после блокировки планировщика и держать коротко.
- Новый скан выкатывается в режиме «выкл», затем «пробно» (скан выполняется и откатывается, число видно в пульсе), затем «вкл». Режимы — `Setting "scheduler.scans"` = `{ код: "off" | "dry" | "on" }`, по умолчанию «выкл».
- Сервисы, которые вызывает скан, не держат состояние на уровне модуля (кэши, Map): у тика своя копия модулей.
- Действия от имени системы: `userId = null` в ленте и журнале, в интерфейсе «автоматически».
- Вставка в таблицы с уникальным ключом — без ошибки (`createMany({ skipDuplicates: true })` / `ON CONFLICT DO NOTHING`): ошибка уникальности внутри транзакции переводит её в «aborted», ловить `P2002` бесполезно.
- **Для Ф2:** у `AdminNotice` нет ключа дедупликации (`schema.prisma`, модель `AdminNotice`). «Уведомить о перестое один раз» потребует уникального ключа или проверки под блокировкой планировщика.

## 7. Карточка «Планировщик»

| Состояние | Условие | Текст |
|---|---|---|
| выключен | `RUN_SCHEDULER ≠ "1"` | «Выключен на этом сервере» + время последнего тика через HTTP, если был |
| не запускался | пульса нет | «Ещё не запускался» |
| отстаёт | пульсу больше 3 минут | «Отстаёт · последний тик N мин назад» (красным) |
| на паузе | свежий пульс и включённая настройка паузы (берётся сама настройка, а не отметка в пульсе — карточка не спорит с кнопкой до следующего тика) | «На паузе · последний тик 03:41» |
| работает | свежий пульс | «Работает · последний тик 03:41» |

Ниже — упавшие сканы последнего тика и кнопка «Поставить на паузу» / «Снять с паузы». Порог 3 минуты покрывает простой при выкатке (около 1–1,5 мин). Время — по Москве через `fmtDateTime`.

## 8. Критерии приёмки

1. С `RUN_SCHEDULER=1` в логе одна строка «[scheduler] минутный тик включён», пульс обновляется примерно раз в минуту, карточка «Работает».
2. С `RUN_SCHEDULER=0` таймера нет, карточка «Выключен на этом сервере»; тик через HTTP работает и показывается временем.
3. `npm run build` не запускает тик и не выдаёт предупреждений про Edge.
4. Вход: без секрета, с неверным — 404; `GET` — не 200; с верным — 200 и JSON с `at`, `done`, `failed`.
5. Параллельные вызовы — ни одного 500. «Второй одновременный тик отвечает busy и сканы не запускает» — юнит-тест с медленным подставным сканом.
6. Бросающий скан не мешает следующим и не роняет процесс.
7. Лежащая база: процесс жив, в логе одна ошибка; после подъёма — строка о восстановлении.
8. Пауза: после нажатия тик не запускает сканы и показывает «На паузе»; снятие возвращает «Работает».
9. На stage после выкатки: пульс свежий, карточка «Работает», вход 404 без секрета и 200 с секретом.

## 9. Тесты

**Юнит (`tests/unit/scheduler.test.ts`, без базы):**
- `cronSecretOk`: пустой ожидаемый, короче 16, `null`, неверный той же длины, другой длины (не бросает), верный.
- `shouldStartScheduler`: `"1"` → да; пусто, `"0"`, `"true"`, фаза сборки → нет.
- `runTickWith`: бросающий скан изолирован; второй вызов во время первого → `busy`, сканы не запускались, пульс не писался; блокировка не взята → `busy` без пульса; режим «пробно» → число в `dry`, откат запрошен; «выкл» — скан не вызывался; пауза — сканы не вызывались, пульс с `paused`; ошибка чтения настроек → `failed: ["config"]`, не бросает; ошибка записи пульса → `ok: false`, не бросает.
- `ErrorLog`: первая ошибка печатается, повторы молчат, восстановление печатает счётчик.
- `heartbeatState`: все пять состояний и мусор вместо JSON.

**E2E (`tests/e2e/scheduler.mjs`, вход владельцем):** вход без заголовка, с неверным секретом, `GET` — не 200; с верным — 200 и JSON; пять параллельных — нет 500; карточка показывает время тика из ответа; пауза → тик отвечает `paused` → снять паузу (в `finally`).

**Вручную:** `RUN_SCHEDULER=1 npx next dev -p 3100` — одна строка «тик включён», пульс идёт; `npm run build` — без строки про тик и без предупреждений Edge; на stage — остановить базу на 2–3 минуты: `parking24-web` жив, одна ошибка, после подъёма строка о восстановлении и свежий пульс.

## 10. Риски

| Риск | Что делаем |
|---|---|
| На stage `RUN_SCHEDULER=1`: тик заработает сразу после выкатки | Сканов с действиями нет, тик пишет только пульс. Есть пауза |
| Тик умер без перезавода таймера — процесс жив, работы нет | Перезавод в `finally`, `runTick` не бросает, карточка покажет «Отстаёт» |
| `register()` бросил — сервер отвечает 500 на всё | try/catch вокруг всего, импорт внутри try |
| Prisma в Edge-сборке | Литеральная проверка runtime первой строкой; критерий 3 |
| Два экземпляра модуля в процессе — два флага, два таймера | Всё состояние в `globalThis.__p24Scheduler` |
| Лог забит ошибками при лежащей базе | Свой клиент без логов + журнал по смене состояния |
| Код на верхнем уровне исполнится при сборке | Правило: в `scheduler.ts` на верхнем уровне только объявления |
| Локальный секрет 15 символов — вход молча 404 | Перевыпустить; предупреждение в `register()` при любом `RUN_SCHEDULER` |
| Аварийно остановить тик можно только правкой `.env` | Кнопка паузы у владельца, действует на оба входа |
| Планировщик встал, никто не заметил | «Отстаёт» в карточке. Уведомление в колокольчик — вопрос на будущее |

## 11. Выкатка

1. Локально: юнит, e2e, `npm run build` без предупреждений Edge.
2. Независимое ревью → правки → подтверждающее.
3. Stage: бэкап, выкатка (серверный `.env` не трогаем: `RUN_SCHEDULER=1` и секрет 32 символа уже там).
4. Проверка: лог «тик включён», пульс свежий, карточка «Работает», вход 404/200, e2e `scheduler.mjs` против stage.
5. HANDOFF, таблица фаз плана.

## 12. Вопросы пользователю

Бизнес-вопросов нет. По умолчанию: состояние и пауза — только у владельца; «отстаёт» — пульсу больше 3 минут.

## 13. Критика v1 (22.09) — что изменилось

Критик собрал мини-приложение на Next 16.3.1 (standalone и dev) и временный Postgres. Вердикт «поправить до кода». Учтено: свой клиент базы без логов (Prisma печатает каждую ошибку сама); состояние пульса в чистом модуле (`server-only` бросает под `node --test`); пульс под блокировкой (иначе блокировка в Ф1 не исполнялась бы ни разу); `globalThis` без условий (модуль грузится дважды); литеральная проверка runtime (иначе Prisma в Edge-сборке); без побочных эффектов на верхнем уровне (сборка исполняет модули маршрутов); исправлены доводы про падение процесса, перекрытие контейнеров и перегрузки `pg_try_advisory_xact_lock`; контракт скана с режимами «выкл / пробно / вкл» и лимитом; пауза для обоих входов; `busy` не пишет пульс; журнал ошибок по смене состояния; точное исключение в `proxy`; без `runtime`/`dynamic` в маршруте.

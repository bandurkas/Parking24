# Ф1. Планировщик: минутный тик

Статус: **архитектура** (22.09.2026). Код не начат.

Порядок фазы (`docs/TZ_2026-09-21_PLAN.md` §5а): архитектура → критика → код → тесты → ревью → stage.

## 1. Зачем

Половина ТЗ завязана на время, а не на действие человека: перестой машины после даты выезда (Ф2), напоминание за 24 часа, «не приехали» через 24 часа, автопереход в «Не приехал» через 48 часов (Ф7), позже — отправка сообщений (Ф4). Сейчас в системе нет ничего, что просыпалось бы само: `RUN_SCHEDULER` на stage стоит в `1`, но код его не читает, `src/instrumentation.ts` и `/api/cron` нет.

Ф1 делает только основу: процесс сервера раз в минуту запускает список задач («сканов»), и видно, что он жив. **Сканов, которые что-то меняют у клиентов или в бронях, в Ф1 нет.** Первый такой скан появится в Ф2 (перестой).

## 2. Что входит и что нет

**Входит:**
- минутный тик внутри процесса сервера (`src/instrumentation.ts`);
- защита от двойной работы: один тик за раз в процессе и блокировка в базе между процессами;
- реестр сканов с контрактом `(tx, now) => число сделанного`; в Ф1 он пустой;
- «пульс»: после каждого тика запись в `Setting` «когда, откуда, сколько длился, что сделано, что упало»;
- карточка «Планировщик» на странице настроек владельца: работает / отстаёт / выключен, время последнего тика по Москве;
- запасной вход `POST /api/cron/automations` с секретом: для e2e (тик по команде, без ожидания минуты) и на случай аварии;
- исключение `/api/cron` из Basic Auth в `src/proxy.ts`;
- тесты и запись в `tests/README.md`.

**Не входит:**
- любые сканы с действиями (перестой — Ф2, напоминания и «не приехал» — Ф7);
- отправка сообщений (Ф4);
- уведомление в колокольчик, если планировщик встал (сторожу нужен кто-то снаружи тика — см. п. 8, вопрос на будущее);
- вторая реплика сервера.

## 3. Как это работает

```
старт сервера
  └─ register()  [src/instrumentation.ts]
       ├─ не nodejs / сборка / RUN_SCHEDULER ≠ "1" → выходим, тика нет
       └─ import scheduler → startScheduler() → первый тик через 15 с
                                                   │
тик (каждые 60 с после окончания предыдущего) ◄───┘
  runTick("timer")
    ├─ уже идёт тик в этом процессе → пропуск (busy)
    ├─ для каждого скана: своя транзакция
    │     ├─ pg_try_advisory_xact_lock(SCHEDULER_LOCK) не взят → пропуск всего тика (busy)
    │     └─ scan.run(tx, now) → число; ошибка скана ловится, остальные сканы идут дальше
    └─ пульс в Setting "scheduler.heartbeat" (всегда, даже при ошибках сканов)

POST /api/cron/automations  (заголовок X-Cron-Secret)
  └─ неверный или короткий секрет → 404
  └─ верный → runTick("http") → 200 { ok, busy?, done, failed, ms }
```

## 4. Решения

1. **Файл — `src/instrumentation.ts`.** В проекте есть `src/`, поэтому по документации Next 16 (`file-conventions/instrumentation.md`) файл кладётся туда. `register()` вызывается один раз на запуск сервера и должен завершиться до приёма запросов, поэтому он только заводит таймер и сразу возвращает управление. При `next build` не вызывается.
2. **Выключатель один: `RUN_SCHEDULER === "1"`.** Любое другое значение, включая пустое, `0` и `true`, — тика нет. Локально и в e2e держим `0`, на stage уже `1`.
3. **Цепочка `setTimeout`, а не `setInterval`.** Следующий тик заводится только после окончания предыдущего, поэтому медленный тик не наслаивается на следующий. Handle таймера хранится в `globalThis` (как `prisma` в `src/server/db/prisma.ts`), повторный `startScheduler()` гасит прежний таймер. `unref()`, чтобы таймер не держал процесс.
4. **Процесс не падает от ошибок тика.** В таймер передаётся обычная функция, внутри — `void runTick().catch(log).finally(rearm)`: отклонённый промис в таймере в Node 22 роняет процесс. `runTick` сам не бросает: каждый скан в своём try/catch. `register()` целиком в try/catch: ошибка в нём не даёт серверу стартовать вообще.
5. **Одна транзакция на скан, а не на тик.** Ошибка Postgres внутри транзакции переводит её в «aborted», и все следующие запросы в ней падают. Если бы сканы делили транзакцию, один сбойный утащил бы остальные.
6. **Блокировка между процессами — `pg_try_advisory_xact_lock(24_0922)`.** Ключ отличается от блокировки занятости `24_0921` (`autoconfirm.ts`), иначе тик тормозил бы заявки с сайта. Вариант «try»: если блокировку держит другой процесс, тик пропускает работу, а не встаёт в очередь. Литерал ключа вставляется в SQL напрямую, как уже сделано в `autoconfirm.ts`: с параметром Postgres путается в перегрузках функции. Защищает от двух тиков при перекрытии старого и нового контейнера во время выкатки.
7. **Внутри процесса — флаг `busy` в `globalThis`.** Закрывает совпадение таймерного тика и вызова через HTTP.
8. **Таймаут транзакции скана — 30 с** (у Prisma по умолчанию 5 с, скану по большой таблице может не хватить), ожидание соединения — 10 с.
9. **Пульс — ключ `scheduler.heartbeat` в `Setting`**: `{ at, source, ms, done, failed, busy }`. Пишется после каждого тика отдельным запросом вне транзакций сканов, чтобы сбой скана не мешал пульсу. Запись раз в минуту на одну строку — нагрузка ничтожная. Отдельная таблица журнала тиков не нужна: для «жив ли» хватает последнего, ошибки — в логе контейнера.
10. **Состояние в CRM.** Карточка «Планировщик» на `/admin/settings` (страница только для владельца):
    - «Работает · последний тик 03:41 МСК», если пульсу меньше 3 минут;
    - «Отстаёт · последний тик 25 мин назад» красным, если больше;
    - «Выключен на этом сервере», если `RUN_SCHEDULER ≠ "1"`;
    - «Ещё не запускался», если пульса нет.
    Плюс список упавших сканов из последнего пульса. Порог 3 минуты = тик + запас на медленный тик и перезапуск.
11. **Запасной вход — только `POST`, ответ на любую неудачу — 404.** Снаружи маршрута как будто нет. Секрет сравнивается через sha256 обеих строк и `timingSafeEqual`, без раннего выхода и без утечки длины. Секрет короче 16 символов — вход выключен, при старте в лог уходит предупреждение. Секрет на stage — 32 символа, **локальный — 15, его перевыпускаем** (`openssl rand -hex 32`).
12. **`/api/cron` исключаем из Basic Auth** в `src/proxy.ts`: у крона свой, более сильный секрет. Сейчас Basic Auth на stage выключен, но при его включении крон без этого исключения получил бы 401.
13. **Логи с троттлингом.** Одна и та же ошибка печатается не чаще раза в 15 минут со счётчиком повторов: при лежащей базе лог за ночь иначе забьётся одной строкой.
14. **Тестируемое ядро отдельно.** Логика тика (флаг занятости, изоляция сканов, сбор результата) — в `tick-core.ts` без `server-only` и без Prisma; блокировка и список сканов подставляются. Так юнит-тесты работают без базы, как остальные 47.

## 6. Критерии приёмки

1. С `RUN_SCHEDULER=1` в логе сервера ровно одна строка «[scheduler] минутный тик включён», пульс обновляется примерно раз в минуту, карточка в настройках показывает «Работает».
2. С `RUN_SCHEDULER=0` тика нет, карточка показывает «Выключен на этом сервере».
3. `npm run build` не запускает тик.
4. `POST /api/cron/automations` без секрета, с неверным и с коротким секретом → 404; с верным → 200 и JSON; `GET` → 405 или 404, не 200.
5. Пять параллельных `POST` → ни одного 500, сканы в одно время выполняет не больше одного вызова, остальные отвечают `busy`.
6. Скан, который бросает ошибку, не мешает следующим и не роняет процесс; тик возвращает его в `failed`.
7. Упавшая база не роняет процесс; ошибка в логе одна, со счётчиком повторов.
8. На stage после выкатки: пульс свежий, карточка «Работает», вход 404 без секрета и 200 с секретом.

## 7. Тесты

**Юнит (`tests/unit/scheduler.test.ts`, без базы):**
- `cronSecretOk`: пустой ожидаемый секрет, ожидаемый короче 16, `given = null`, неверный той же длины, неверный другой длины (не бросает), верный.
- `shouldStartScheduler`: `nodejs` + `"1"` → да; `edge` → нет; `phase-production-build` → нет; `RUN_SCHEDULER` пустой, `"0"`, `"true"` → нет.
- `runTickWith`: скан №1 бросает → №2 и №3 отработали, результат `failed: ["a"]`, функция не бросает.
- `runTickWith`: пока идёт первый тик, второй вызов возвращает `busy` и сканы не запускает.
- `runTickWith`: блокировка не взята → `busy`, сканы не запущены.
- Состояние пульса: свежий / отстаёт / нет пульса / выключен — чистая функция от `(heartbeat, now, enabled)`.

**E2E (`tests/e2e/scheduler.mjs`, dev с `RUN_SCHEDULER=0` или stage):**
- вход без заголовка, с неверным секретом, `GET` — не 200;
- с верным секретом — 200, в JSON есть `done` и `failed`;
- пять параллельных вызовов — нет 500;
- после вызова карточка в настройках показывает время этого тика.

**Вручную:**
- `RUN_SCHEDULER=1 npx next dev -p 3100`: одна строка «тик включён», пульс идёт; правка файла в `src/` (HMR) второй строки не добавляет;
- `npm run build`: строки про тик нет;
- на stage: остановить контейнер базы на 2–3 минуты → `parking24-web` жив, в логе одна ошибка со счётчиком, после подъёма базы пульс возобновился.

## 8. Риски и что с ними делаем

| Риск | Что делаем |
|---|---|
| На stage `RUN_SCHEDULER=1`: тик начнёт работать сразу после выкатки | В Ф1 сканов с действиями нет, тик только пишет пульс. Проверяем это до выкатки |
| Ошибка в `register()` не даёт серверу стартовать | Весь `register()` в try/catch, импорт планировщика внутри try, первый тик через 15 с, `register()` его не ждёт |
| Отклонённый промис в таймере роняет процесс Node 22 | В таймер — синхронная функция с `.catch().finally()`, `runTick` по контракту не бросает; юнит-тест на бросающий скан |
| Два тика при перекрытии контейнеров во время выкатки | Флаг в процессе + `pg_try_advisory_xact_lock` на каждый скан |
| Два таймера в dev после повторного исполнения модуля | Handle в `globalThis`, прежний гасится |
| Локальный секрет 15 символов — вход молча отвечает 404 | Перевыпустить локально; предупреждение в логе при старте, если секрет короче 16 |
| Тип `setTimeout` разный в DOM и Node — сборка падает на присвоении | Тип `ReturnType<typeof setTimeout>`, `unref` через необязательный вызов |
| Планировщик встал, никто не заметил | Карточка «Отстаёт» в настройках. Уведомление в колокольчик — вопрос на будущее: его должен ставить не сам тик (он же и встал), а проверка при открытии CRM |

**Заметка для Ф2 и дальше (в Ф1 не нужна).** Разбор этапа 2 предлагал ловить ошибку уникальности `P2002` в `enqueue`, чтобы гонка двух тиков не валила скан. Внутри транзакции это не работает: в Postgres ошибка уникальности переводит всю транзакцию в «aborted», дальше любой запрос в ней падает. Для сканов, которые ставят сообщения в очередь, нужна вставка без ошибки (`INSERT … ON CONFLICT DO NOTHING`, в Prisma — `createMany({ skipDuplicates: true })`) или точка сохранения (savepoint). Решать в архитектуре Ф2/Ф7.

## 9. Выкатка

1. Локально: юнит, e2e, `npm run build`.
2. Независимое ревью → правки → подтверждающее.
3. Stage: бэкап базы, выкатка. На stage `RUN_SCHEDULER=1` и секрет уже есть, серверный `.env` не трогаем.
4. Проверка: лог «тик включён», пульс свежий, карточка «Работает», вход без секрета 404 и с секретом 200, e2e `scheduler.mjs` против stage.
5. Запись в HANDOFF и в таблицу фаз плана.

## 10. Вопросы пользователю

Бизнес-вопросов в Ф1 нет, фаза техническая. Решено по умолчанию:
- состояние планировщика видит только владелец (карточка на странице настроек, она и так только для владельца);
- «отстаёт» — если пульсу больше 3 минут.

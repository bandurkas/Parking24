# МФ-UI. Меню, роли и доступы, сверка интерфейса с ТЗ (идёт первой, перед Ф9а)

Архитектура. Код по этому документу пишет другой агент. Основание: решение пользователя 24.09 вечер — «сначала интерфейс, согласованный со всеми функциями ТЗ, потом код Ф9а» (`docs/TZ_2026-09-21_PLAN.md` §1, «Решения 24.09 (вечер)», п. 1, 2, 5, 6, 8–12). Материал — четыре проверки интерфейса против ТЗ: `docs/ui_check_2026-09-24/{A_bookings_notifications,B_boards_occupancy,C_money,D_roles_menu_shifts}.md`. Читать их не обязательно — разрывы, которые касаются этой фазы, собраны в §2–§5 ниже с точной ссылкой.

## 1. Цель

Дать всем следующим фазам готовую, окончательную структуру интерфейса, чтобы они не переставляли меню друг за другом и не изобретали доступ для новых ролей на ходу. Три вещи: (1) меню — окончательные группы, а не список «дописать в конец»; (2) роли — по реальному штату, включая вход водителя и парковщика; (3) навигация работает на телефоне, где сейчас её нет вообще.

## 2. Зачем именно сейчас

Три находки проверок — это не будущий риск, а нынешняя дыра, обнаруженная чтением уже существующего кода:

1. **На экранах уже 1024 px бокового меню нет совсем** (`Sidebar.tsx:26`, `hidden … lg:flex`), в шапке нет ни меню, ни кнопки «Выйти» (`Topbar.tsx`). С телефона администратор не попадёт в «Занятость», «Клиенты», «Кассу» (когда она появится) и не сможет выйти. Найдено во всех четырёх проверках независимо.
2. **Вход будущих ролей уйдёт в бесконечный редирект.** `requireUser` при чужой роли шлёт на `/admin/today` или `/admin` (`src/server/auth/guard.ts:16`); `/admin` через layout снова требует `OWNER`/`ADMIN` (`src/app/admin/(app)/layout.tsx:11`) → редирект туда же. Тот же обрыв в `login/actions.ts:31` и `login/page.tsx:9`. Без починки водитель или парковщик после входа увидят пустой цикл редиректов.
3. **`/admin/today` открыт любому вошедшему без проверки роли** (`src/app/admin/today/page.tsx:35`, `requireUser()` без списка). Это решение 24.09 п. 6 («денег и карточек броней не видят») прямо нарушает: полное табло с суммами и «не оплачено» получит кто угодно.

Плюс: решение 24.09 п. 4 («Отменить»/исправление статуса закрытой брони — только владелец) сейчас в коде не выполнено (`correctStatusAction`, `actions/bookings.ts:58`, пускает любого STAFF). Эта находка — не в этой фазе (см. §4), но фиксируется здесь, чтобы Ф9а её не забыла: документ Ф9а уже несёт это решение в §5.2/§12/§13.

## 3. Что входит

1. Роли `DRIVER` и `PARKER` в схеме (миграция, добавляющая значения enum, отдельной миграцией — правило PLAN §3).
2. Функция «домашний адрес роли» и её использование в трёх местах входа/выхода за роль (`guard.ts`, `login/actions.ts`, `login/page.tsx`).
3. Починка `today/page.tsx`: явный список ролей вместо `requireUser()` без аргумента.
4. Две новые страницы поля: `/admin/parking-lot` (парковщик, только просмотр) и `/admin/transfers` (водитель, только просмотр, машины с `transferNeeded`). Обе — вне группы `(app)`, без `AdminShell`, по образцу того, как сейчас устроен экран охраны внутри `today/page.tsx`.
5. Вынос запроса «Сегодня» (`loadRows` в `today/page.tsx`) в общий серверный модуль, чтобы новые страницы поля не дублировали Prisma-запрос.
6. Полная переработка `Sidebar.tsx`: группы вместо плоского списка, будущие пункты заявлены сразу серыми («скоро»), а не дописываются каждой фазой в конец.
7. Мобильная навигация для `OWNER`/`ADMIN`: нижняя панель + выезжающий лист «Ещё» с остальными пунктами, поиском и «Выйти».
8. Кнопка «Выйти» в `Topbar` на всех ширинах (сейчас есть только в подвале скрытого `Sidebar`).
9. У экрана охраны, открытого владельцем/администратором через «Экран КПП», — путь назад в CRM (сейчас там только «Обновить» и «Выйти»).
10. Слияние пункта «Дашборд» в «Отчёты» — один пункт меню вместо двух про одни и те же деньги (решение 24.09 п. 10).
11. `ROLE_LABEL`, ролевые константы (`guard.ts`), `seed.ts` — с учётом двух новых ролей.

## 4. Что НЕ входит (границы с соседями)

- **Исправление статуса закрытой брони «только владелец» — код у Ф9а.** Ф9а уже документировала это решение (§5.2, §12 решение 5, §13 п. 3, 6, 9) и владеет файлами `correct.ts`, `actions/bookings.ts`, `StatusCorrect.tsx`, `KanbanBoard.tsx`. МФ-UI даёт только общую инфраструктуру ролей (`guard.ts`), саму проверку внутри `correctStatus`/`correctStatusAction` не трогает.
- **Табель, самоотметка смены, справочник сотрудников — Ф13.** У парковщика и водителя после этой фазы есть вход, домашний экран и просмотр списка машин, но кнопки «Моя смена» нет: модели `Employee` в схеме ещё нет. Ф13 должна быть переписана под «логины есть» (её документ сейчас утверждает обратное — находка D, §4 «В документах фаз») и тогда добавит самоотметку на все четыре ролевых экрана (`GuardScreen`, `parking-lot`, `transfers`, и для администратора — отдельным путём). Это отдельная задача после текущей.
- **Касса, отчёты, автоподтверждение, шаблоны — Ф11/Ф12/МФ-1/МФ-2.** МФ-UI резервирует им пункты меню (серые, «скоро»), но страниц не пишет.
- **Занятость, окно 24 ч, табло «Планируют выезд», ручное время — Ф3, Ф9а, Ф9б.** Не трогаем.
- **Экран охраны (`GuardScreen.tsx`) не переписываем**, кроме одной строки — кнопки «← CRM», видимой только не-охране (см. §5.9). Всё остальное там — Ф9б.
- **Само содержимое `TodayBoard`/`GuardScreen` (московское время, часы) — Ф9б.** Вынос запроса в сервис (§3.5) не меняет ни одного поля выборки, только место, где она лежит.

## 5. Решения

### 5.1. Две роли, не одна общая
Выбрано решением пользователя 24.09: `DRIVER`, `PARKER` — отдельные значения `enum Role`. У каждой свой домашний экран и свой набор действий, проверки в коде проще, чем разбирать «сотрудник + должность» на каждом экране. Отвергнуто: одна роль `STAFF_FIELD` с полем должности — экран пришлось бы выбирать по данным, а не по роли, и это ломало бы `Record<Role, …>`-таблицы (`ROLE_LABEL`), которые сейчас ловят непокрытые роли на этапе сборки.

### 5.2. Домашний адрес по роли — одна функция в одном месте
```ts
// src/server/auth/guard.ts, рядом с STAFF/OWNER/ALL
export function roleHome(role: Role): string {
  if (role === "GUARD") return "/admin/today";
  if (role === "PARKER") return "/admin/parking-lot";
  if (role === "DRIVER") return "/admin/transfers";
  return "/admin";
}
```
Используется в трёх местах, которые сейчас держат один и тот же тернарник по отдельности (`guard.ts:16`, `login/actions.ts:31`, `login/page.tsx:9`) — они его теряют и зовут `roleHome(user.role)`. Отвергнуто: оставить тернарники и просто дописать в каждый ещё две ветки — правило было бы в трёх местах, разъехалось бы при следующей роли.

### 5.3. `today/page.tsx` — явный список ролей
`requireUser()` → `requireUser(ALL)` (`ALL` уже равна `["OWNER","ADMIN","GUARD"]`, `guard.ts:29`, ничего нового заводить не нужно). Дальше по логике страницы ничего не меняется: `GUARD` и `?guard=1` по-прежнему получают `GuardScreen`. Отвергнуто: заводить отдельную константу — `ALL` уже значит ровно то, что нужно, только не была применена.

### 5.4. Новые экраны поля — вне группы `(app)`, без общего запроса
`/admin/parking-lot` и `/admin/transfers` — по образцу того, как сейчас устроен `GuardScreen`: страница вне `(app)`, сама вызывает `requireUser(["PARKER"])` / `requireUser(["DRIVER"])`, не оборачивается в `AdminShell`, у каждой свой полноэкранный компонент под телефон (палец, а не мышь — как у `GuardScreen`, кнопки `h-14`+).

Обе экрана читают тот же набор броней, что и «Сегодня», поэтому запрос выносится в `src/server/services/today.ts`:
```ts
import "server-only";
// … содержимое сегодняшнего loadRows() из today/page.tsx, без изменений в логике …
export async function loadTodayRows(today: string, ctx: OverstayCtx): Promise<{ arrivals: TodayRow[]; departures: TodayRow[]; onSite: TodayRow[] }> { … }
```
`TodayRow` определяется там же; `TodayBoard.tsx` вместо своего `export type TodayRow = {…}` делает `export type { TodayRow } from "@/server/services/today";` — импорт `GuardScreen.tsx` (`import type { TodayRow } from "./TodayBoard"`) не меняется. `today/page.tsx` вызывает `loadTodayRows` вместо локальной функции.

**Парковщик** (`parking-lot/page.tsx`): два списка из уже загруженных `arrivals`/`departures` — «Ожидаем» и «Скоро выезд» (простая сортировка по `dateTo`/`dateFrom`, без `dueState` — та функция появится в Ф3/Ф9б и не должна блокировать эту фазу, это записано как открытый пункт в §9). Поля: госномер, тип машины, плановая дата/время. **Без** суммы, телефона, статуса брони, ссылки на карточку — решение 24.09 п. 6.

**Водитель** (`transfers/page.tsx`): тот же источник, отфильтрован `transferNeeded === true`, список только «отвезти в терминал» (заезды). Список «забрать из терминала» не делаем — он ждёт ответа заказчика «как клиент добирается от терминала после прилёта» (`DECISIONS_2026-09-24.md` строка 58, до сих пор без ответа). Поля: имя клиента (чтобы узнать пассажира), госномер, плановое время. **Без** телефона и кнопки звонка — вопрос об этом пользователю не задавался, по умолчанию не показываем (см. §9); добавить кнопку `tel:` — правка на один компонент, когда решится.

Отвергнуто: пускать `OWNER`/`ADMIN` на эти же экраны «посмотреть глазами». Не входит ни в одно принятое решение, а у владельца и так есть доска и «Сегодня» с той же информацией и даже больше — отдельного экрана ему не нужно.

### 5.5. Роль проверяется через разрешённый список, не через запрет
Сейчас службы (`transition.ts:16`, `correct.ts:15`, `edit.ts:15`, `payments.ts:137`) проверяют `role === "GUARD"` и всё остальное пропускают — при добавлении `DRIVER`/`PARKER` в `Role` они прошли бы этот запрет как администраторы. Это не баг этой фазы (действия и так закрыты списком ролей на входе, `STAFF`/`ALL`), но правило фиксируется здесь, чтобы Ф10/Ф13 и другие, кто такое найдёт, не тиражировали способ «проверка через запрет» на новых ролях. В файлах этой фазы такого паттерна не заводим.

### 5.6. Меню — группы, будущие пункты объявлены сразу
```ts
// src/components/admin/nav.ts — новый, данные меню отдельно от компонента
export type NavItem = { href: string; label: string; icon: LucideIcon; ready: boolean };
export type NavGroup = { title?: string; ownerOnly?: boolean; items: NavItem[] };

export const NAV: NavGroup[] = [
  { items: [
    { href: "/admin/boards/parking", label: "Парковка", icon: Car, ready: true },
    { href: "/admin/today", label: "Сегодня", icon: CalendarDays, ready: true },
    { href: "/admin/boards/rooms", label: "Комнаты", icon: BedDouble, ready: true },
    { href: "/admin/clients", label: "Клиенты", icon: Users, ready: true },
    { href: "/admin/occupancy", label: "Занятость", icon: LayoutGrid, ready: true },
  ]},
  { title: "Смена", items: [
    { href: "/admin/cash", label: "Касса", icon: Wallet, ready: false },       // Ф11
    { href: "/admin/staff", label: "Табель", icon: CalendarCheck, ready: false }, // Ф13
  ]},
  { title: "Владелец", ownerOnly: true, items: [
    { href: "/admin/dashboard", label: "Отчёты", icon: BarChart3, ready: true },
    { href: "/admin/audit", label: "Журнал", icon: ScrollText, ready: true },
    { href: "/admin/settings", label: "Настройки", icon: Settings, ready: true },
  ]},
];
```
`ready: false` — пункт виден, но серый, без ссылки, с подписью «скоро» (не 404 и не пустое место — администратор видит, что раздел придёт). Когда Ф11/Ф13 сдают свою фазу, они переключают `ready` на `true` в этом файле — **одна строка**, `Sidebar.tsx` и мобильное меню не трогают. Это снимает конфликт «каждая фаза дописывает NAV в конец» (правило было в MAP_DEPENDENCIES, теперь заменяется этим).

Пункт «Экран охраны» и «Комнаты» из общего списка не убираем (пользователь про «Комнаты» не спрашивался — это действующая часть бизнеса вне ТЗ 21.09, трогать без явного решения нельзя); «Экран охраны» уходит из групп в подвал, рядом с именем пользователя — реже нужен, чем «Занятость» или «Клиенты».

Отвергнуто: чужую доработку выключателем в `Setting` (спрятать пункт «Касса» по флагу из базы) — это меню на этапе сборки, не поведение времени выполнения, обычный флаг в коде проще и не требует миграции.

### 5.7. «Дашборд» и «Отчёты» — один пункт
Пункт меню `/admin/dashboard` переименовывается в «Отчёты» (по решению 24.09 п. 10), маршрут и страница не трогаются. Когда Ф12 сдаёт полноценный отчёт, она решает сама: расширить `/admin/dashboard` на месте или сделать `/admin/reports` и поменять `href` в `nav.ts` на новый — это её однострочная правка в готовом файле, не переоткрытие структуры меню.

### 5.8. Мобильная навигация — нижняя панель + «Ещё»
Для `OWNER`/`ADMIN` на ширине `< lg` (соответствует текущему порогу скрытия `Sidebar`, `Sidebar.tsx:26`): фиксированная нижняя панель, 5 кнопок — **Парковка · Сегодня · + (открыть быструю заявку) · Клиенты · Ещё**. «Ещё» открывает лист снизу (тот же паттерн `role="dialog" aria-modal="true"`, что уже есть в `QuickBookingDrawer.tsx:151`) со всеми остальными пунктами `NAV` по группам, полем поиска (сейчас `GlobalSearch` скрыт `hidden … sm:block`, `GlobalSearch.tsx:16` — на мобильном листе показываем то же поле без этого класса) и кнопкой «Выйти» внизу.

`Topbar.tsx` получает кнопку «Выйти» рядом с колокольчиком на всех ширинах (сейчас выход есть только в подвале `Sidebar`, которого на мобильном нет вовсе — находка Р1/Р5 в проверке C, п. 3/6 в проверке D). Решение 24.09 п. 11 (30 дней сессии, без сокращения) — эту кнопку не отменяет, наоборот: без неё сотрудник с открытой сменой не увидит напоминание об этом (Ф11), когда оно появится.

Отвергнуто: гамбургер-меню поверх текущего скрытого `Sidebar` (просто показать тот же список в выезжающей панели). Список без групп на телефоне длиннее и не даёт быстрого доступа к пяти самым частым действиям — решение 24.09 п. 2 просит «только самое нужное», а нижняя панель именно это и даёт.

### 5.9. Путь назад из экрана охраны
`GuardScreen.tsx` получает один необязательный проп `canLeave?: boolean` (или читает `user.role !== "GUARD"` — экран уже получает `user` пропом, `GuardScreen.tsx:16`): когда открывший — не охрана (т.е. `?guard=1` от `OWNER`/`ADMIN`), рядом с «Обновить» появляется ссылка «← CRM» на `/admin`. Для роли `GUARD` ничего не меняется — ей и так некуда возвращаться. Однострочная правка в шапке компонента (`GuardScreen.tsx:47-59`), остальное содержимое экрана не трогаем (это Ф9б).

### 5.10. Пароли и `seed.ts`
Два новых тестовых пользователя для разработки: `driver`/`parker`, пароли через `SEED_DRIVER_PASSWORD`/`SEED_PARKER_PASSWORD` (env, по образцу трёх существующих строк `seed.ts:11-14`), значения по умолчанию `driver12345`/`parker12345`. На stage они не заводятся сами — реальных сотрудников заводит владелец, когда появится «Пользователи» (МФ-2); это только для локальной и stage-разработки следующих фаз (Ф13 понадобится, кому логиниться при тестах).

### 5.11. Выход за периметр охраны в GuardScreen не расширяем
Не добавляем парковщику и водителю кнопки `GUARD_TRANSITIONS` — решение 24.09 (ответ на вопрос D №3): «только смотрит». Если пользователь позже передумает (на воротах фактически один человек и за охрану, и за парковщика), это одна строка в `canTransition`/`labels.ts`, не структурная правка.

## 6. Изменения схемы (только добавляющие)

`prisma/schema.prisma`:
```prisma
enum Role {
  OWNER
  ADMIN
  GUARD
  DRIVER
  PARKER
}
```
Новые значения enum — отдельной миграцией, без использования в той же транзакции (правило PLAN §3; `docs/phases/PHASE_09A_MANUAL_TIME.md` уже держит этот принцип для булевых полей, здесь то же для enum). Миграция:
```sql
-- AlterEnum
ALTER TYPE "Role" ADD VALUE 'DRIVER';
ALTER TYPE "Role" ADD VALUE 'PARKER';
```
Postgres требует каждое значение в отдельном `ALTER TYPE`, но обе строки можно в одной папке миграции (это не «использование в той же транзакции» — использование значит запись строки с новым значением, а не объявление). После этой миграции `seed.ts` (§5.10) уже может создавать пользователей с этими ролями следующим шагом/деплоем — Prisma применяет `ALTER TYPE` в отдельной транзакции автоматически.

## 9. Открытые вопросы — решены или взяты по рекомендации

Проверка D нашла ещё несколько мелких вопросов, отдельно не заданных пользователю. По общему правилу проекта (рекомендация принимается, если не сказано иного — так же, как в `DECISIONS_2026-09-24.md` §1) код-агент берёт следующее:

1. **Кнопка «позвонить» водителю.** Не делаем в этой фазе (§5.4). Дешёвая правка на будущее, ждёт отдельного решения пользователя.
2. **Список «забрать из терминала».** Не делаем — ждёт ответа заказчика (см. §5.4).
3. **Отмечает ли охрана свою смену сама, отмечает ли администратор свою.** Не в этой фазе — требует модели `Employee`, которой ещё нет (Ф13). Рекомендация для Ф13, когда та фаза перепишется: да, и охрана, и администратор отмечают сами.
4. **Экран парковщика/водителя владельцу и администратору «для просмотра».** Не делаем (§5.4, отвергнутый вариант) — у них уже есть доска и «Сегодня» с тем же и большим.
5. **Куда указывает «Отчёты» после Ф12.** Оставляем текущий маршрут `/admin/dashboard`; Ф12 решает сама, расширять его на месте или переехать (§5.7).

Больше открытых вопросов для этой фазы нет — всё остальное из четырёх проверок относится к другим фазам и уже сослано в их документы (см. §4).

## 10. Риски

1. **Вынос `loadTodayRows` может незаметно изменить поведение «Сегодня».** Требование: тело функции переносится дословно, без правок логики выборки. Проверяется существующими юнит/e2e на «Сегодня» и экран охраны — они не должны увидеть разницы (это регрессия, а не новая функциональность).
2. **Бесконечный редирект, если `roleHome` забудут применить в одном из трёх мест.** Контрольный grep в §8 п. 9 ловит старый паттерн, но не гарантирует, что новый применён везде — юнит-тест на `roleHome()` плюс e2e-логин под каждой новой ролью (§11) закрывают это надёжнее.
3. **`Record<Role, …>`-таблицы, забытые при добавлении ролей.** `ROLE_LABEL` (`labels.ts:113`) не соберётся без записей `DRIVER`/`PARKER` — это защита самим TypeScript, но проверить `npm run build`, а не только `npm test`.
4. **Мобильный лист «Ещё» и `QuickBookingDrawer` — два независимых `role="dialog"` в один момент.** Открытие «+» из «Ещё» должно закрывать лист, иначе на экране два перекрывающихся оверлея.
5. **`seed.ts` на stage.** Новые тестовые пользователи `driver`/`parker` не должны попасть на боевую базу без ведома владельца — `seed.ts` и так выполняется при каждом деплое (`upsert`, безопасно), но об этом стоит сказать в приёмке: на stage появятся два лишних тестовых логина, пока МФ-2 не даст управление пользователями.

## 11. Критерии приёмки

1. Вход под `driver`/`parker` (сид) ведёт сразу на `/admin/transfers`/`/admin/parking-lot`, без цикла редиректов и без мигания `/admin`.
2. `/admin/today`, набранный вручную под `driver`, отдаёт редирект на домашний экран роли, а не табло с суммами.
3. Экран парковщика и водителя не содержат ни одной суммы, телефона (кроме имени у водителя) и ссылки на карточку брони.
4. На ширине 390 px под `owner`/`admin`: внизу видна панель из 5 кнопок, «Ещё» открывает список остальных разделов, поиск и «Выйти» работают.
5. «Касса» и «Табель» видны в меню серыми, с подписью «скоро», без ссылки и без 404.
6. «Дашборд» в меню больше не значится — вместо него один пункт «Отчёты», ведущий на прежнюю страницу.
7. Владелец, открывший «Экран КПП», видит кнопку назад в CRM; охрана под своей ролью её не видит.
8. `npm run build` проходит (ловит непокрытые `Record<Role,…>`).

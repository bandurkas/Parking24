# СП. Срочные правки: деньги на stage

Статус: **архитектура v1 (22.09.2026)** — ответы пользователя получены (§9), до критики.

Порядок фазы (`docs/TZ_2026-09-21_PLAN.md` §5а): архитектура → критика → код → тесты → ревью (2 раунда) → stage. Источник — `docs/TZ_STATUS_2026-09-22.md` §2 п. 1–3.

## 1. Зачем

Три дыры в деньгах, которые есть на stage сейчас:

1. **Ручное время в «Выехал» снимает ДОЛГ за перестой.** Сервер проверяет только, что время не в будущем (`bookings.ts:133`), а перестой начисляется до даты этого времени (`bookings.ts:142-143`). Администратор ставит выезд датой плана — долга нет. Это обход правила «деньги закрытой брони — только владелец» (Ф2а).
2. **Возврат больше оплаченного проходит молча** (`bookings.ts:268`, `Math.max(0, …)`): платёж пишется на полную сумму, «оплачено» обрезается до нуля. Возврат принимается даже при оплате 0. PLAN §2 п. 9 — записано, не сделано.
3. **Ложный долг после возврата.** Возврат уменьшает «оплачено», но не сумму брони; с Ф2а «К оплате» у клиента учитывает «Выехал» (`clients/[id]/page.tsx:55`). После обычного частичного возврата у клиента висит долг. e2e `crm-pipeline` оставляет бронь ровно так.

## 2. Что входит и что нет

**Входит:** правило даты выезда в перестое (сервер + подсказка в форме); запрет возврата больше оплаченного; возврат уменьшает сумму брони по правилу §3.2; причина возврата обязательна; e2e и юнит-тесты.

**Не входит:**
- ручное время вне перестоя — влияет только на баннер «Стоянка по факту», решение по нему принимает человек; поле убирает Ф9;
- расчёт суммы возврата системой при досрочном выезде, «Оформить возврат», расхождение баннера и действия — Ф10;
- пересчёт старых возвратов: на stage один — демо-бронь №4 (возврат 700 ₽ «досрочный выезд», до правила; PLAN §3 «старые брони не пересчитываются»);
- §2 п. 4 (старые PENDING, правила со скидкой) — шаг 0 Ф4; §2 п. 5 (VPS2) — ответ «не трогать, бой не здесь» → МФ-3б на боевом сервере.

## 3. Решения

### 3.1 Выезд в перестое — по дате нажатия (ответ 2)

1. **Правило.** Если бронь в перестое (`overstayDays(b, today) > 0`: парковка, «Заехал», сегодня по Москве позже даты выезда), дата выезда — только сегодняшняя по Москве. Прошлую дату сервер не принимает: «В перестое выезд отмечается сегодняшним числом. Если машина уехала раньше, а выезд не отметили — „Исправить статус“ с причиной». Время внутри сегодняшнего дня можно указать (до Ф9), на сумму оно не влияет.
2. **Для всех ролей**, включая владельца (выбран вариант без исключений). Забытый выезд — «Исправить статус» → «Выехал» с причиной: без начисления, в ленте «Перестой N сут. не начислен (сумма) · причина» (Ф2а, уже работает). Если надо начислить часть — владелец через «Изменить цену».
3. **Чистая функция** `checkoutDateAllowed(b, outDate, today)` в `src/lib/overstay.ts`: `false`, когда `overstayDays(b, today) > 0 && outDate < today`. В `transition` `today = moscowIso(now)` от того же `now`, что проверка «не в будущем» — одна граница суток на всю транзакцию. Проверка после `lockBooking` и чтения строки (статус и дата выезда — из заблокированной строки).
4. **Все пути ручного времени идут через `transitionAction` → `transition`**: форма `TransitionButtons` (карточка брони, «Сегодня»), `window.prompt` при перетаскивании на доске (`KanbanBoard.tsx:83`), экран охраны (без времени — всегда «сейчас»). Других вызовов `transition` нет (проверено grep). Сервер — единственная проверка.
5. **Подсказка в форме.** `TransitionButtons` получает `overstay?: boolean`; в форме «Фактически выехал» у брони в перестое — строка «Перестой: выезд — сегодняшним числом. Забытый выезд — „Исправить статус“». Атрибут `min` у поля не ставим: браузер заблокировал бы отправку своей подсказкой, и e2e не увидел бы серверную проверку. Карточка брони и «Сегодня» передают `overstay` (у строк «Сегодня» поле уже есть с Ф2а). Доска — только серверная ошибка (по умолчанию в `prompt` сегодняшнее время, прошлую дату надо набрать руками).

### 3.2 Возврат (ответ 1)

6. **Не больше оплаченного.** `refund > paid` → ошибка «Возврат больше оплаченного: оплачено N ₽»; при `paid = 0` — «По брони ничего не оплачено — возвращать нечего». `Math.max(0, …)` уходит: «оплачено» не может стать отрицательным по построению.
7. **Возврат уменьшает сумму брони, сначала гася переплату.** Чистая функция `applyRefund({ amount, paid }, refund)` в новом `src/lib/refund.ts`:
   - `over = max(0, paid − amount)` — переплата;
   - `cut = max(0, refund − over)` — на сколько уменьшается сумма брони;
   - итог `{ amount: amount − cut, paid: paid − refund }`; `null`, если `refund ≤ 0` или `refund > paid`.

   Свойство: «не оплачено» (`max(0, amount − paid)`) возвратом **не меняется**, сумма не уходит в минус (доказательство — три случая: без переплаты; возврат в пределах переплаты; возврат больше переплаты → сумма = новое «оплачено»). Юнит-тест перебором.

   | Случай | Было (сумма / оплачено) | Возврат | Стало |
   |---|---|---|---|
   | Досрочный выезд, оплачено полностью | 1 050 / 1 050 | 350 | 700 / 700 |
   | Лишняя оплата (ошиблись суммой) | 1 050 / 1 400 | 350 | 1 050 / 1 050 |
   | Даты сократили через «Изменить» (сумма уже 700) | 700 / 1 050 | 350 | 700 / 700 |
   | Частичная переплата + уступка | 1 050 / 1 200 | 350 | 850 / 850 |
   | Частичная оплата | 1 050 / 700 | 200 | 850 / 500 (долг 350 остаётся) |
   | Фура «по запросу» | 0 / 5 000 | 5 000 | 0 / 0 |
   | Перестой, долг принят заранее | 700 / 1 050 | 350 | 700 / 700 (показанный ДОЛГ снова 350) |

8. **Причина обязательна** (ТЗ 8.5): примечание к возврату от 3 символов, иначе «Укажите причину возврата».
9. **Права.** Возврат — `OWNER` и `ADMIN` (как сейчас, `addPaymentAction` → `STAFF`), **в том числе после выезда**: единственное исключение из правила «сумму закрытой брони меняет только владелец» (решение пользователя). Ограничено оплаченным, причина обязательна, запись в ленте и журнале; наличный возврат попадёт в кассу смены (Ф11).
10. **Запись.** Одна строка в ленте (тип `PAYMENT`): «Возврат 350 ₽ · <причина> · сумма брони 1 050 → 700 ₽» (хвост — только если сумма изменилась), `meta` += `priceFrom`, `priceTo`. Журнал: `CREATE Payment` как сейчас и `UPDATE Booking { refund, priceFrom, priceTo, reason }`, если сумма изменилась.
11. **«Это полная стоимость» — только для оплаты**: `settle` учитывается при `kind = PAYMENT`, у возврата игнорируется на сервере (сейчас `assertMoneyEditable` сработал бы и для возврата с `settle`).
12. **Форма возврата** (`PaymentPanel`): по умолчанию сумма — переплата, если она есть, иначе всё оплаченное (как сейчас); подпись «не больше N ₽»; поле «Причина возврата (обязательно)»; строка «Сумма брони станет N ₽» (та же `applyRefund`, модуль без сервера); кнопка «Провести» недоступна без причины и при сумме больше оплаченного. Компонент получает сумму брони пропсом `total`.
13. **Что не меняется:** LTV (`recalcLtv` — платежи минус возвраты), «Выручка за месяц» на дашборде (по платежам), автопереход в «Подтверждена» (только при оплате), «К оплате» у клиента (правится источник — сумма брони). Баннер «Стоянка по факту» и возврат согласованы в любом порядке: «по факту» после возврата даёт ту же сумму, возврат после «по факту» гасит переплату.

## 4. Данные

Схема не меняется, миграций нет. Старые возвраты не пересчитываются (на stage — демо №4).

## 6. Критерии приёмки

1. Бронь в перестое: «Выехал» с датой раньше сегодняшней (форма и доска) — отказ с понятным текстом, статус и сумма не меняются; с сегодняшней датой (любое время) — начисление до сегодня, как в Ф2а.
2. Бронь без перестоя: ручное время работает как раньше (до Ф9).
3. «Исправить статус» → «Выехал» в перестое — как раньше: без начисления, причина в ленте.
4. Возврат больше оплаченного и возврат при оплате 0 — ошибка, платёж не записан.
5. Возврат без причины — ошибка на сервере, кнопка недоступна в форме.
6. Возврат 350 из 1 050 после выезда (администратор): сумма 700, оплачено 700, «оплачено», в ленте «сумма брони 1 050 → 700 ₽»; «К оплате» у клиента не растёт.
7. Возврат переплаты сумму брони не меняет.
8. LTV и «Выручка за месяц» — как раньше.

## 7. Тесты

**Юнит (без базы):**
- `applyRefund`: семь случаев таблицы §3.2; `null` при `refund > paid`, `refund ≤ 0`, `paid = 0`; перебор `amount, paid ∈ 0..2000 шаг 50`, `refund ∈ 1..paid`: «не оплачено» не меняется, сумма ≥ 0, оплачено ≥ 0, сумма уменьшается ровно на `refund − переплата`, если это > 0.
- `checkoutDateAllowed`: перестой + вчера → false; перестой + сегодня → true; без перестоя + вчера → true; выезд сегодня (не перестой) + вчера → true; не «Заехал» → true; комната → true.

**E2E** (локально и против stage):
- `crm-pipeline`: после выезда возврат 350 с причиной → «700 ₽», «оплачено», лента «сумма брони 1 050 → 700 ₽»; возврат 800 → «Возврат больше оплаченного»; без причины кнопка «Провести» недоступна.
- `overstay`, бронь А: форма «Выехал» → дата вчера → «сегодняшним числом», статус «Заехал», сумма 700; затем обычный выезд — проверки Ф2а без изменений.
- Остальные сценарии (`site-lead`, `autoconfirm`, `scheduler`) — как есть.

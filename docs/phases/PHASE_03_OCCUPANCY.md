# Ф3. Занятость по ТЗ и потолок 405 в CRM

Дорожка Д2, после Ф9а. Архитектура, код по ней пишет другой агент.
Код на `88c9425`. Разделы ТЗ: 4.1, 4.2, часть 1.1 и 1.3.
Источники решений: `docs/TZ_2026-09-21_PLAN.md` §1 (включая блок 23.09), `docs/TZ_2026-09-21_SOURCE.md` §4, `docs/TZ_STATUS_2026-09-22_night.md` §3 (Ф3) и §4.

## 1. Цель

Сейчас «сколько занято» считается шестью разными способами в шести местах, и ни одно из них не сходится с эталоном ТЗ: панель показывает 1 / 414 / 415 вместо 1 / 404 / 405. Фаза сводит счёт занятости к одному правилу в одном файле и подключает к нему все экраны.

Одновременно в CRM появляется потолок: администратор больше не может руками поставить бронь на дату, где мест уже нет, — ни созданием, ни подтверждением, ни «Исправить статус», ни правкой дат.

## 2. Что входит и что не входит

### Входит

1. **Одно правило занятости.** Одна выборка и одна чистая функция отрезка на все экраны, автоподтверждение и проверки.
2. **«Новая заявка» держит место ограниченное время** — настройка `parking.newLeadHoldHours` (решение 23.09 №2).
3. **Панель занятости по ТЗ 4.2** — пять показателей, эталон 1 / 404 / 405, фуры отдельной строкой.
4. **Окна 24 ч** — один помощник планового момента и одно окно для «Заезды за 24 ч» и «Выезды за 24 ч»; сейчас чисел три и два соответственно.
5. **Категории (ТЗ 4.1)** — остаются как просмотр «занято по типам», без вместимостей 60/30/10/5.
6. **Потолок 405 / 10** в `createBooking`, `transition`, `correctStatus`, `updateBooking`, с порядком блокировок.
7. **Подсказка «свободно N из 405»** в быстрой брони и в «Изменить бронь» — по пулу, а не по категории.
8. **Сверка вместимости при сохранении настроек** — опечатка 45 не закроет приём заявок молча.
9. **Починка `plannedMoment`** и подключение его к окнам.
10. **Дашборд владельца** — «Сейчас на стоянке» из того же правила (сейчас туда попадают комнаты).

### Не входит

| Что | Чья фаза | Граница |
|---|---|---|
| Убрать ручное время, параметр `at` | Ф9а | Ф9а идёт раньше. Я пишу потолок поверх `transition` **без** `at` |
| Предохранитель включения автоподтверждения, таймаут транзакции, дубль заявки под блокировкой | МФ-1 | МФ-1 раньше Ф3 по `createBooking` и `saveCapacityAction`. Я дописываю сверку вместимости **поверх** предохранителя, не переписываю его |
| Уведомления администратору, колокольчик, режимы сканов | Ф2б | Я только вызываю существующий `notify(...)` |
| Табло «Планируют выезд · 24 ч», фильтр в таблице, списки «Прибытие»/«Отправление», предупреждение о раннем заезде | Ф9б | Я отдаю Ф9б помощники окна; **списки на «Сегодня» не трогаю**, кроме формы данных полосы занятости в шапке |
| Деньги при «Исправить статус», забытый заезд, сторно, возвраты | Ф10 | Оба правим `correct.ts`. Ф3 раньше и добавляет туда **только проверку мест** |
| Сообщение «бронь изменена» при смене дат | Ф6 | Ф3 раньше Ф6; Ф3 в `updateBooking` добавляет только потолок |
| Финансовый отчёт, месяц по Москве | Ф12 | Дашборд Ф3 правит только плитку «Сейчас на стоянке» |
| Автопереход «Не приехал» через 48 ч | Ф7 | «Новая» после истечения срока удержания **не меняет статус**, только перестаёт считаться занятой |

## 3. Решения

### 3.1. Одно правило: одна выборка, одна функция отрезка

Правило занятости состоит из трёх частей, и все три живут в одном месте.

1. **Кто вообще держит место** (`holdsSpace`, чистая функция):
   - `CHECKED_IN` — всегда (машина стоит: и ранний заезд, и перестой);
   - `AWAITING_PAYMENT`, `CONFIRMED` — по датам брони (предоплаты нет, место держится — решение №3 от 22.09);
   - `NEW` — по датам, но только пока с `createdAt` прошло меньше `parking.newLeadHoldHours`;
   - остальные — не держат.
2. **На каком отрезке** — существующая `effectiveSpan(b, today)`: «Заехал» начинается с `min(dateFrom, today)` и в перестое тянется до `OPEN_END`. Не трогаем, Ф2а работает.
3. **В каком пуле** — `poolOf(vehicleType)`: `TRUCK` → пул фур, всё остальное, включая `null`, → общий пул (405).

Всё остальное — производные, ни одна из них не ходит в базу сама:

```
parkingSpans(db, from, to, { today, holdSince, excludeBookingId })   ← ЕДИНСТВЕННАЯ выборка
        │
        ├── poolLoad(pool, from, to)        пик, minFree, по дням   → сетка, quoteAction, автоподтверждение
        ├── parkingToday(today)             пул и фуры на сегодня   → панель, полоса, дашборд, страница ёмкости
        ├── byVehicleType(today)            «занято» по категориям  → сетка, полоса
        └── checkFit(...)                   потолок                 → create / transition / correct / update
```

**Почему одна выборка, а не пять.** Сегодня страница занятости делает пять запросов: четыре `occupancy()` по типам плюс `poolLoad`. Все пять читают одно и то же надмножество. Один запрос на `[from, to]` с `vehicleType` в выборке, дальше всё в памяти — это и есть «одно правило в одном месте». Строк заведомо не больше вместимости плюс перестой, выборка дешёвая (обоснование — `PHASE_02_OVERSTAY.md` §4.1 п. 3).

**Отвергнуто:** оставить `occupancy()` по категориям как отдельный путь «потому что он уже есть». Именно он даёт красные строки при свободном пуле и `/5` у фур против 10.

### 3.2. Шесть способов — куда каждый переезжает

| Было | Где | Станет |
|---|---|---|
| `occupancyToday` — `CONFIRMED` + `CHECKED_IN`, ёмкость из `CapacityConfig` | полоса на «Сегодня» и на доске | `parkingToday` + `byVehicleType`: пул и фуры со знаменателями, категории — только «занято» |
| `poolLoad` — `ACTIVE`, ёмкость 405 | сетка, автоподтверждение | остаётся, читает `parkingSpans`, добавлено окно «Новой» |
| `parkingDashboard.held` — все брони парковки против 415 | панель | `parkingToday`: пул против 405, фуры против 10, раздельно |
| `held` на странице ёмкости | `/admin/settings/capacity` | тот же `parkingToday` + пик на 90 дней для сверки |
| дашборд `onSite` — `status: CHECKED_IN` **без** `kind` | `/admin/dashboard` | `parkingToday`, комнаты больше не попадают |
| `occupancy()` по категориям — `ACTIVE`, `CapacityConfig` | сетка, `quoteAction` | категории — из `byVehicleType`; `quoteAction` — на `poolLoad`; `occupancy()`/`occupancySummary`/`capacityFor` остаются **только для комнат** |

### 3.3. «Новая заявка» держит место (решение 23.09 №2)

Ключ `parking.newLeadHoldHours`. Срок считается от `createdAt` брони. `0` — не держит (сегодняшнее поведение).

Реализация — условием в SQL, а не фильтром в памяти, иначе выборка перестанет быть надмножеством:

```ts
// holdSince = holdHours > 0 ? new Date(now - holdHours * 3_600_000) : null
export function occupiesWhere(from: string, to: string, holdSince: Date | null): Prisma.BookingWhereInput {
  const dated = { dateFrom: { lte: toDate(to) }, dateTo: { gte: toDate(from) } };
  const or: Prisma.BookingWhereInput[] = [
    { status: "CHECKED_IN" },
    { status: { in: ["AWAITING_PAYMENT", "CONFIRMED"] }, ...dated },
  ];
  if (holdSince) or.push({ status: "NEW", createdAt: { gte: holdSince }, ...dated });
  return { OR: or };
}
```

**Выключатель.** Правило проекта — новое автоматическое поведение выкатывается выключенным. Поэтому в коде `def = 0`, seed создаёт ключ со значением `0`, поле есть на странице «Ёмкость» с подсказкой «рекомендуется 24». Владелец ставит 24 после приёмки. Это же вынесено вопросом 8 — если пользователь скажет «включай сразу», меняется одна строка в seed.

**«Новая» старше срока статус не меняет** — она просто перестаёт занимать место. Освобождение статусом — Ф7 (автопереход «Не приехал»).

### 3.4. Панель занятости: пять показателей и эталон 1 / 404 / 405

| Показатель ТЗ | Формула |
|---|---|
| Авто на парковке | машины **пула** физически на территории: `CHECKED_IN`, занимающие сегодня |
| Заезды за 24 ч | `AWAITING_PAYMENT` + `CONFIRMED`, плановый момент заезда в `[сейчас, сейчас + 24 ч)`, ещё не заехали |
| Выезды за 24 ч | `CHECKED_IN`, плановый момент выезда раньше `сейчас + 24 ч`; просроченные (перестой) входят |
| Свободно сейчас | `405 − Авто на парковке` |
| Всего мест | `405` — пул; фуры в 405 не входят (решение 22.09, ответ 2) |

Эталон ТЗ сходится: одна машина на стоянке даёт 1 / 404 / 405.

Под плиткой «Свободно сейчас» — подсказка **«занято бронями N»**, где `N` — занятость пула на сегодня со всеми держащими бронями. Формулировка сохранена дословно: её читает `tests/e2e/overstay.mjs:62,90`, тест переписывать не нужно.

Отдельной строкой под плитками:

```
Пул    · на стоянке 1 · занято бронями 312 из 405 · под новые заявки 93
Фуры   · на стоянке 0 · занято бронями 2 из 10   · под новые заявки 8
```

Баннер порога заменяется на честный по решению №3 (порог 395 — пик на датах заявки, не «занято сейчас»):
«Ближайшие 3 недели: K дней заняты на 395 и больше — заявки с сайта на эти даты отклоняются автоматически». `K` считается из уже загруженной сетки, лишнего запроса нет.

**Отвергнуто:** «Свободно сейчас = 405 − занято бронями». Это полезнее для администратора, но не даёт эталон ТЗ (было бы 93, а не 404). Вынесено вопросом 3; оба числа на экране есть в любом случае.

### 3.5. Окна 24 ч и `plannedMoment`

Сегодня «заезды за 24 ч» — это `dateFrom` между двумя календарными датами, то есть окно от 24 до 48 часов, и оно посчитано по-разному в трёх местах.

Вводится один помощник в `src/server/lib/dates.ts`:

```ts
plannedCheckIn(b)   // dateFrom + timeFrom, без времени — 12:00 МСК
plannedCheckOut(b)  // dateTo   + timeTo,   без времени — 12:00 МСК
within24h(moment, now)          // now <= moment < now + 24ч
before24h(moment, now)          // moment < now + 24ч   (просроченные входят)
```

Выборка по календарным датам `[сегодня, завтра]` остаётся надмножеством, точное окно отсекается в памяти.

**Две правки в `plannedMoment`.**

1. `"25:00"` проходит регулярку `^\d{2}:\d{2}$` и даёт **Invalid Date** — проверено запуском. Дальше любое сравнение молча ложно, и бронь исчезает из окна 24 ч. Берём строгую проверку ЧЧ:ММ из шага 0 Ф4 (он раньше по расписанию), при непрохождении — 12:00.
2. Смещение пояса берётся через `toLocaleString` + `new Date(<строка локали>)`. На практике процессный пояс не влияет (проверено под `TZ=Asia/Jakarta` — результат тот же), но разбор строки локали спецификацией не определён. Заменяем на явный расчёт через `formatToParts`:

```ts
export function tzOffsetMs(at: Date, tz = "Europe/Moscow"): number {
  const p = Object.fromEntries(
    new Intl.DateTimeFormat("en-US", { timeZone: tz, hour12: false, year: "numeric", month: "2-digit", day: "2-digit", hour: "2-digit", minute: "2-digit", second: "2-digit" })
      .formatToParts(at).map((x) => [x.type, x.value]),
  );
  return Date.UTC(+p.year, +p.month - 1, +p.day, +p.hour % 24, +p.minute, +p.second) - at.getTime();
}
```

`% 24` — ICU в полночь отдаёт `24`. Существующие тесты `tests/unit/planned-moment.test.ts` должны остаться зелёными без правок.

### 3.6. Категории по ТЗ 4.1

Ответ пользователя 2 от 22.09: общий пул 405 без деления по категориям; фуры отдельно, 10 мест. ТЗ 4.1 просит «сохранить возможность просмотра занятости по каждой категории».

Решение: категории показывают **только «занято»**, без знаменателя и без подсветки перегруза. Знаменатель есть у пула (405) и у фур (10).

Следствия — закрываются три строки сверки разом: у «Груз» больше нет `/5` против 10; строки не краснеют при свободном пуле; плашка «Ёмкость по типам ТС — плейсхолдер» исчезает вместе с ключом `capacityIsPlaceholder` (его перестают читать и писать; строка в базе остаётся — миграции только добавляющие).

`CapacityConfig` для `PARKING` больше не читается. Строки не удаляем, seed перестаёт их создавать для новых баз. Для комнат `CapacityConfig`, `capacityFor`, `occupancy()` и `occupancySummary` работают как работали.

**Отвергнуто:** оставить вместимости категорий и настраивать их на странице ёмкости. Это второе определение вместимости рядом с 405 — ровно то, что фаза убирает.

### 3.7. Потолок в CRM

Потолок — **405 для пула и 10 для фур**, то есть полная вместимость. 395 — это только автоподтверждение заявок с сайта, оно не меняется (решение 23.09 №3).

```ts
export type Fit = { ok: boolean; peak: number; capacity: number; day: string; overstay: number };

export async function checkFit(
  db: Pick<Prisma.TransactionClient, "booking">,
  c: { pool: PoolKind; from: string; to: string; excludeBookingId?: string; today: string; holdSince: Date | null; capacity: number },
): Promise<Fit>;
```

Возвращает самый загруженный день отрезка, занятость на нём и сколько из неё — машины в перестое (для текста ошибки). `ok = peak + 1 <= capacity`.

**Где вызывается** (`kind === "PARKING"`, всегда с исключением самой брони):

| Место | Отрезок | Когда проверяем |
|---|---|---|
| `createBooking` | `[dateFrom, dateTo]` | всегда: любой доступный при создании статус (`NEW`, `AWAITING_PAYMENT`, `CONFIRMED`) держит место |
| `transition` | `[dateFrom, dateTo]` | переход в держащий статус из недержащего: `REJECTED → AWAITING_PAYMENT`, `NEW → AWAITING_PAYMENT/CONFIRMED` |
| `transition → CHECKED_IN` | `[today, dateTo]` | ранний заезд удлиняет отрезок назад. **Не блокируем никогда** — машина уже у шлагбаума: пишем в ленту, в журнал и уведомление |
| `correctStatus` | `[dateFrom, dateTo]` | цель держит место, исходный статус — нет (`Отменена`/`Отклонена`/`Не приехал` → `Ожидает оплаты`/`Подтверждена`) |
| `updateBooking` | новые `[dateFrom, dateTo]` | менялись даты или тип машины (смена типа перекладывает бронь между пулами) |
| `addPayment` → авто `NEW/AWAITING_PAYMENT → CONFIRMED` | `[dateFrom, dateTo]` | **мягкая** проверка: деньги уже приняты, блокировать нечего. Запись в ленту + уведомление |

**Текст отказа** — с цифрами и с подсказкой, что делать:

> На 12 окт мест нет: занято 405 из 405, из них 3 машины в перестое. Освободить место — отметить выезд в «Сегодня»; подтвердить сверх вместимости может владелец.

**Сверх вместимости вручную** (моё предложение, вопрос 2): владельцу можно с явным подтверждением, администратору нельзя.
Технически: серверное действие возвращает `{ ok: false, error, overCapacity: { day, peak, capacity } }`; форма показывает подтверждение; владелец повторяет вызов с `overCapacity: true`. Сервер при этом требует `actor.role === "OWNER"`, пишет `SYSTEM`-строку в ленту брони, `audit(UPDATE, …, { overCapacity: true, day, peak, capacity })` и `notify("CAPACITY_OVER", …)`. Одно подтверждение на одно действие, «запомнить» нет.
Если ответ на вопрос 2 — «жёсткий запрет», весь блок `overCapacity` выбрасывается из действий и форм, `checkFit` и тексты остаются.

### 3.8. Блокировки и их порядок

Правило проекта: деньги и занятость меняются только под блокировкой строки брони. Потолок читает **чужие** брони, поэтому нужна ещё и общая блокировка занятости — она уже есть, `lockOccupancy(tx)` (`pg_advisory_xact_lock`, `autoconfirm.ts`).

**Жёсткий порядок, нарушать нельзя: `lockOccupancy` → `lockBooking`.** Обратный порядок в одной транзакции при прямом в другой даёт взаимную блокировку; `pg_advisory_xact_lock` участвует в детекторе Postgres, то есть это будет не зависание, а случайная ошибка на проде.

Чтобы порядок не зависел от того, что мы прочитали, `lockOccupancy` берётся **безусловно для всех броней парковки** в `createBooking`, `transition`, `correctStatus`, `updateBooking`. Это сериализует записи по парковке — при нагрузке CRM в единицы действий в минуту цена нулевая, а рассуждать не о чем.

`addPayment`, `changePrice`, `decideRecalc`, `waiveOverstay`, `extendStay` общую блокировку **не берут** (занятость не меняют) — значит инверсии порядка с ними не возникает. `extendStay` — бронь в перестое, она и так занимает все будущие дни, проверка мест не нужна (уже отмечено комментарием в коде).

`lockOccupancy` повторно вызывается внутри `decideSiteBooking` — `pg_advisory_xact_lock` в одной сессии реентерабелен, это безопасно.

### 3.9. Вместимость против занятости при сохранении настроек

`saveCapacityAction` сейчас пишет любое число. Опечатка «45» закроет приём заявок и включит автоотклонение на сайте.

Добавляется: считаем пик занятости пула и фур на `[сегодня, +90 дней]`; если новая вместимость меньше пика — отказ с числом («На 3 окт занято 312, вместимость 45 сохранить нельзя»), либо, при `confirm: true` от владельца, сохраняем и пишем в журнал. Поверх предохранителя МФ-1, не вместо него.

Туда же — поле `parking.newLeadHoldHours` (часы, 0–168) и строка «Сейчас занято: пул N из 405, фуры M из 10».

## 4. Изменения схемы

Только добавляющие. Порядок папок миграций при слиянии перенумеровывает оркестратор 1.

1. **Миграция A, новое значение enum, без использования:**
   `NoticeKind` += `CAPACITY_OVER` — уведомление «бронь №N подтверждена сверх вместимости» и «машина заехала при полном пуле».
2. **Миграция B, индексы:**
   `Booking` += `@@index([kind, status, dateFrom])`, `@@index([kind, status, dateTo])`.
   Существующие `@@index([dateFrom])` и `@@index([dateTo])` не покрывают новые запросы «парковка + держащие статусы + диапазон». Индексы добавляющие, данные не трогают.
3. `AuditAction` **не трогаем**: превышение пишется как `UPDATE` с `diff = { overCapacity: true, day, peak, capacity }`. Новое значение enum ради одной записи не окупается.
4. Полей в `Booking` не добавляем: занятость нигде не материализуется, она всегда считается (то же правило, что и у долга за перестой — `PHASE_02_OVERSTAY.md` §4.2 п. 10).

export type PoolKind = "POOL" | "TRUCK";
export const poolOf = (vt: string | null | undefined): PoolKind => (vt === "TRUCK" ? "TRUCK" : "POOL");

// Держит ли бронь место. holdMs = 0 — «Новая» не держит (выключено)
export function holdsSpace(b: { status: string; createdAt: number }, nowMs: number, holdMs: number): boolean {
  if (b.status === "CHECKED_IN" || b.status === "AWAITING_PAYMENT" || b.status === "CONFIRMED") return true;
  return b.status === "NEW" && holdMs > 0 && nowMs - b.createdAt < holdMs;
}

// Перевёрнутый отрезок — мусор на входе, не «везде свободно»: daysRange даёт [], peak 0, и заявка «проходила»
export function fits(spans: Span[], from: string, to: string, limit: number): boolean {
  if (to < from) return false;
  return peakLoad(spans, from, to) + 1 <= limit;
}

## Независимая критика архитектуры

Вердикт: **годится с правками**. Находок: 17.

### [блокер] Потолок в createBooking ломает приём заявок с сайта, как только владелец включит удержание «Новой». Заявка с сайта при выключенном автоподтверждении создаётся в статусе NEW; при holdHours > 0 NEW — держащий статус, значит guardCapacity сработает и бросит CapacityError.

# Ф6. Изменение брони (дорожка Д4, после Ф5)

Документ архитектуры. Код по нему пишет другой агент, вопросов задавать не должен.
Ветка `main`, коммит `88c9425`. Источники решений: `docs/TZ_2026-09-21_SOURCE.md` п. 1.3 и 2, `docs/TZ_2026-09-21_PLAN.md` §1 (включая «Решения пользователя 23.09»), §2 п. 8, §3, `docs/TZ_STATUS_2026-09-22_night.md` §3 «Ф6» и §4, тексты — `docs/MESSAGE_TEMPLATES_2026-09-22.md`.

## 1. Цель

Когда администратор меняет бронь (даты, время, сумму), клиент должен получить сообщение «бронь изменена» с новыми данными, а сообщения, которые ещё лежат в очереди со старыми датами, — перестать быть ложью: подтверждение перерисовывается на новые даты, привязанное к моменту (напоминания, прошлое «изменена») отменяется.
Плюс закрывается путь с сайта: повторная заявка того же телефона на другие даты создаёт новую бронь и уведомление администратору, старую бронь никто не трогает.

## 2. Что входит и что не входит

**Входит:**
1. Триггер `BOOKING_CHANGED` и правило `on_booking_changed` с шаблоном «Бронь изменена» (редакция 3).
2. Единое место решения «писать ли клиенту» — чистая функция плюс один вызов из `updateBooking` и один из `extendStay`.
3. Ключ дедупликации с моментом (`группа:бронь|момент`) в `enqueue` — общий механизм, им же потом пользуется Ф7.
4. Перерисовка висящих сообщений без момента (подтверждение, «заявка принята») на новые данные и отмена висящих сообщений с моментом.
5. Защита от лавины: окно тишины перед отправкой и один ключ на состояние брони.
6. Повторная заявка с сайта: новая бронь (как сейчас) + уведомление администратору «у клиента уже есть бронь на другие даты» (решение 23.09, п. 6).
7. Кнопка на экране результата сайта: вместо «Изменить заявку» — «Забронировать ещё» и строка «изменить эту бронь — позвоните».
8. Дыра из бэклога СП §12: у брони «Заехал» продление в «Изменить бронь» больше не проходит без роста суммы по тарифу.

**Не входит (границы с соседями):**
- Потолок мест при смене дат в `updateBooking` — **Ф3**. Ф6 не считает занятость вообще.
- Сама отправка, каналы, предохранители отправщика, экран результата сайта в части обещаний и «оплаты после подтверждения» — **Ф4** (шаг 0 и дальше), WhatsApp — **Ф14**.
- Тексты отказа, заезда, номера договора, «спасибо + отзыв» — **Ф5**.
- Напоминание за 24 ч, «не приехали», сканы и автопереходы — **Ф7**.
- «Изменить цену», пересчёт по факту, снятие начисления, возвраты — **Ф10**. Эти действия клиенту **не пишут**: иначе правило «пишем об изменении» окажется в двух местах.
- Начисление перестоя при выезде двигает `dateTo` внутри `transition` — сообщение оттуда **не уходит** (явное требование `TZ_STATUS` §3 Ф6).
- Страница «Настройки → Сообщения», где видны выключатели и тексты, — **МФ-2**.
- Колокольчик, `AdminNotice.dedupKey`, режимы сканов — **Ф2б**.
- Ручной ввод времени — **Ф9а**.

## 3. Решения

**Р1. Что считается изменением, о котором пишем клиенту.** Только `dateFrom`, `dateTo`, `timeFrom`, `timeTo`, `amount` и только в `updateBooking` и `extendStay`. Госномер, имя, источник, комментарий, галочка трансфера, тип машины сам по себе — молчим. Тип машины, изменивший сумму, попадает в набор через сумму.
*Отвергнуто:* «писать о любой правке» — клиент получает сообщение из-за исправленной опечатки в номере; «только даты и время, как в ТЗ 1.3» — сумма стоит в брифе фазы, и клиент платит её на въезде (вынесено вопросом 2).

**Р2. Клиенту пишем, только если ему уже что-то отправляли про эту бронь.** Признак — в `Outbox` есть строка со `status = SENT` по этой брони. Если подтверждение ещё висит в очереди (`PENDING`), «бронь изменена» не ставим: подтверждение будет перерисовано и уйдёт сразу с новыми датами, два сообщения подряд клиенту не нужны.
*Отвергнуто:* решать по статусу брони — бронь заведена по телефону, ни одного сообщения не уходило, и первым сообщением человеку приходит «ваша бронь изменена».

**Р3. Возврат к состоянию, о котором клиент уже знает, — не изменение.** Каждая строка очереди помечается `spanKey` — слепок дат и времени брони на момент постановки. Если новый слепок уже встречался среди **отправленных** сообщений, «изменена» не ставим, а висящее «изменена» отменяем. Это закрывает случай «поправили пять раз и вернули как было».

**Р4. Окно тишины.** «Бронь изменена» ставится не «сейчас», а на `сейчас + messages.changeHoldMinutes` (по умолчанию 10 минут). Каждая следующая правка отменяет висящее «изменена» и ставит новое с новым текстом. Пять правок за три минуты дают клиенту одно сообщение с последними данными.
*Отвергнуто:* «слать сразу, а дубли гасить ключом» — ключ включает даты, у каждой правки он свой, значит дублей не будет и уйдут пять сообщений.

**Р5. Ключ дедупликации.** `enqueue` получает необязательный `keyPart`; ключ становится `группа:бронь|момент` (разделитель `|`, в идентификаторе и в группе его нет, в момент — тоже, зато двоеточие есть во времени `12:00`, поэтому по двоеточию ключ не разбирается). Для «изменена» момент — это `spanKey` новой брони, для Ф7 — плановый момент. Строки без `|` — это сообщения «одно на бронь» (подтверждение, «заявка принята»).

**Р6. Висящие сообщения: перерисовываем, а не отменяем всё подряд.** Строка без момента (подтверждение, «заявка принята») перерисовывается по шаблону с новыми данными, ключ и время отправки сохраняются. Строка с моментом отменяется — она была рассчитана на старые даты, Ф7 пересоздаст её сканом. Если шаблон правила недоступен или выключен и перерисовать нечем — строка отменяется, в ленту пишется, какая именно.
*Отвергнуто:* «отменять всё неотправленное» (буквальная формулировка из сверки) — клиент, у которого подтверждение ещё не ушло, не получит его никогда, а именно в нём адрес, маршрут и условия оплаты. Вынесено вопросом 4.

**Р7. Закрытая бронь очередь не трогает.** При статусах `CHECKED_OUT`, `CANCELLED`, `NO_SHOW`, `REJECTED` Ф6 не делает ничего: ни сообщения, ни перерисовки. Это бухгалтерская правка владельца, а у отменённых броней очередь и так погашена (`cancelPendingOutbox`).

**Р8. Выключатели.** `messages.onBookingChanged` (Setting, по умолчанию **false**) — общий рубильник фазы: пока выключен, ни сообщение, ни перерисовка, ни отмена не выполняются, поведение остаётся сегодняшним. `messages.onExtendStay` (Setting, по умолчанию **false**) — писать ли клиенту после «Продлить» (ответ пользователя переключает настройку, код не меняется). `messages.changeHoldMinutes` (Setting, по умолчанию 10) — окно тишины. Текст и включение самого сообщения живут там же, где у остальных шести сообщений, — в `AutomationRule.isActive`; МФ-2 показывает и то и другое на одной странице.

**Р9. Повторная заявка с сайта** (решение 23.09 п. 6, не переспрашиваем): существующая бронь не меняется, создаётся новая, администратор получает уведомление. Десятиминутная защита от дублей (`leads.ts`, те же даты и тот же телефон) остаётся как есть. Новое значение `NoticeKind.CLIENT_HAS_BOOKING`. Если новая заявка сама отклонена «нет мест», второго уведомления не шлём — `BOOKING_REJECTED` уже ушло.

**Р10. Продление брони «Заехал» в «Изменить бронь» (бэклог СП §12).** Если машина на парковке и дата выезда растёт, сумма должна быть не меньше, чем даёт то же правило, что и «Продлить» (`chargeUntil`): своя цена и скидка клиента сохраняются, тариф за добавленные сутки прибавляется. Иначе ошибка с подсказкой «продление считается по тарифу; другая цена — «Изменить цену» с причиной». Смену типа машины у «Заехал» оставляем разрешённой: уменьшить деньги ею нельзя (проверка «сумма не ниже» уже есть), а в перестое она и так запрещена.

## 4. Изменения схемы (только добавляющие)

Две миграции, обе до кода. Номера папок при слиянии перенумеровывает оркестратор.

**Миграция 1 — только значения enum, в этой же миграции не используются:**
```sql
ALTER TYPE "AutomationTrigger" ADD VALUE 'BOOKING_CHANGED';
ALTER TYPE "NoticeKind" ADD VALUE 'CLIENT_HAS_BOOKING';
```

**Миграция 2 — поле и индекс:**
```sql
ALTER TABLE "Outbox" ADD COLUMN "spanKey" TEXT;
CREATE INDEX "Outbox_bookingId_status_idx" ON "Outbox"("bookingId", "status");
```

В `prisma/schema.prisma`: в `enum AutomationTrigger` добавить `BOOKING_CHANGED`, в `enum NoticeKind` — `CLIENT_HAS_BOOKING`, в `model Outbox` — `spanKey String?` и `@@index([bookingId, status])`. Индекс нужен: сегодня `Outbox.bookingId` не проиндексирован, а Ф6 ходит по нему в каждой правке, внутри транзакции под блокировкой строки брони.

Старые строки очереди остаются с `spanKey = null` — для них «клиенту уже сообщали» не сработает, и до первой новой отправки сообщений об изменении по таким броням не будет. Это осознанно, на stage таких строк пять и они гасятся в шаге 0 Ф4.

### 5.1. `src/lib/booking-change.ts` — новый, чистый, без `server-only`

Всё решение — здесь, чтобы покрывалось юнит-тестами без базы.

```ts
export type Span = { dateFrom: string; dateTo: string; timeFrom?: string | null; timeTo?: string | null };
export type ChangeField = "dateFrom" | "dateTo" | "timeFrom" | "timeTo" | "amount";

// «2026-10-01..2026-10-05» или «2026-10-01T09:00..2026-10-05T18:00»
export function spanKey(s: Span): string;

// Изменение, о котором стоит писать клиенту. Пустой массив — молчим.
export function notifiableChange(a: Span & { amount: number }, b: Span & { amount: number }): ChangeField[];

// «группа:бронь» или «группа:бронь|момент»
export function outboxDedupKey(group: string, bookingId: string, keyPart?: string | null): string;
export function isMomentKey(dedupKey: string): boolean; // просто dedupKey.includes("|")

export const CHANGE_OPEN_STATUSES = ["NEW", "AWAITING_PAYMENT", "CONFIRMED", "CHECKED_IN"] as const;

export type ChangePlan = { refresh: boolean; cancelMoment: boolean; notifyAt: Date | null };

export function planChange(i: {
  status: string;         // статус брони после правки
  changed: ChangeField[];
  newSpan: string;
  sentSpans: string[];    // spanKey уже ОТПРАВЛЕННЫХ сообщений по этой брони
  enabled: boolean;       // messages.onBookingChanged
  notifyAllowed: boolean; // правка — всегда true; «Продлить» — messages.onExtendStay
  holdMinutes: number;
  now: Date;
}): ChangePlan;
```

`planChange` по шагам:
1. `!enabled || changed.length === 0 || !CHANGE_OPEN_STATUSES.includes(status)` → `{ refresh: false, cancelMoment: false, notifyAt: null }`;
2. иначе `refresh = true`, `cancelMoment = true`;
3. `notifyAt = null`, если `!notifyAllowed`, или `sentSpans.length === 0` (Р2), или `sentSpans.includes(newSpan)` (Р3);
4. иначе `notifyAt = new Date(now.getTime() + holdMinutes * 60_000)`; при `holdMinutes = 0` это `now`.

### 5.2. `src/server/automations/dispatcher.ts` — правки в `enqueue`, новые функции в конец файла

В `enqueue` меняются две строки: ключ и новое поле.


Новое (добавлять в конец файла — файл общий с Ф4, Ф5, Ф7):

```ts
// Правка брони: что делаем с очередью и пишем ли клиенту. Одна точка на updateBooking и extendStay.
export async function onBookingChanged(
  before: Booking, after: Booking, tx: Tx, opts: { source: "edit" | "extend" },
): Promise<{ refreshed: number; cancelled: number; notifyAt: Date | null; stuck: string[] }> {
  const changed = notifiableChange(before, after);
  if (!changed.length) return EMPTY;
  const s = await messageSettings(tx);
  const sent = await tx.outbox.findMany({
    where: { bookingId: after.id, status: "SENT", spanKey: { not: null } },
    select: { spanKey: true },
  });
  const plan = planChange({
    status: after.status, changed, newSpan: spanKey(spanOf(after)),
    sentSpans: sent.map((r) => r.spanKey!), enabled: s.onBookingChanged,
    notifyAllowed: opts.source === "edit" ? true : s.onExtendStay,
    holdMinutes: s.changeHoldMinutes, now: new Date(),
  });
  if (!plan.refresh && !plan.cancelMoment && !plan.notifyAt) return EMPTY;
  const { refreshed, cancelled, stuck } = await refreshPending(after, tx); // внутри: с моментом — отменить, без — перерисовать
  if (!plan.notifyAt) return { refreshed, cancelled, notifyAt: null, stuck };
  const rules = await tx.automationRule.findMany({
    where: { isActive: true, trigger: "BOOKING_CHANGED", OR: [{ kind: null }, { kind: after.kind }] },
    include: { template: true },
  });
  for (const rule of rules) {
    if (!rule.template?.isActive) continue;
    await enqueue(after, rule.id, rule.code, rule.template.body, tx, plan.notifyAt, undefined, spanKey(spanOf(after)));
  }
  return { refreshed, cancelled, notifyAt: plan.notifyAt, stuck };
}
```

`refreshPending(b, tx)`: берёт `PENDING` по брони вместе с `rule.template`, и для каждой строки —
- `isMomentKey(dedupKey)` → `status: "CANCELLED"` (Ф7 пересоздаст сканом по новым датам);
- иначе есть активный шаблон → `renderedText` пересобирается `renderTemplate(body, { booking: b, client }, extras)` и обновляется `spanKey`; `dedupKey` и `scheduledAt` не трогаем;
- шаблона нет или выключен → `CANCELLED`, код шаблона попадает в `stuck`.

Порядок важен: сначала гасим строки с моментом, потом ставим новое «изменена» — иначе погасили бы только что созданное. Клиент и `extras` (`siteLinks(tx)`, `checkedInAt`) читаются один раз на вызов; общий кусок с `enqueue` вынести в приватную `renderFor(booking, client, extras)`.

## 7. Критерии приёмки (что смотрит человек)

Выключатель `messages.onBookingChanged` включается в настройках (до МФ-2 — строкой в `Setting`).

1. Выключатель выключен (состояние stage по умолчанию): правка брони работает ровно как сегодня, новых записей в «Сообщения клиенту» нет.
2. Включили. Бронь с висящим подтверждением, меняем дату выезда → в блоке «Сообщения клиенту» текст подтверждения содержит **новую** дату, статус остался «запланировано», нового сообщения «изменена» не появилось; в ленте строка «Изменено: даты» и строка «Сообщения клиенту: обновлено 1 · «бронь изменена» не отправляем — клиенту ещё ничего не уходило».
3. Меняем только госномер → в ленте «Изменено: номер …», блок сообщений не изменился.
4. Машина «Заехал», в «Изменить бронь» растянули дату выезда, сумму оставили прежней → ошибка «Продление считается по тарифу: не меньше 1 400 ₽…»; с суммой по тарифу правка проходит.
5. Бронь в перестое: «Изменить бронь» по-прежнему не даёт менять даты, сумму и тип (поведение СП не сломано).
6. Заявка с сайта с телефона, у которого уже есть активная бронь на другие даты → появилась **новая** бронь с новым номером, старая не изменилась, в колокольчике «Заявка №N …: у клиента уже есть бронь №M на 1–5 окт…».
7. Экран сайта после заявки: кнопка «Забронировать ещё» и строка «Изменить эту бронь — позвоните: +7 905 525-06-60».
8. Сообщение клиенту строгое, без эмодзи, ровно как в `MESSAGE_TEMPLATES_2026-09-22.md`.

**После Ф4 (реальная отправка), тем же списком:**
9. Подтверждение ушло (`SENT`) → меняем дату → через 10 минут клиент получает одно «бронь изменена» с новыми датами.
10. Пять правок за три минуты → клиенту одно сообщение с последними данными, в карточке одна строка «запланировано», остальные `CANCELLED`.
11. Вернули даты как были → новое сообщение не появилось, висящее отменено.
12. «Продлить» из плашки перестоя: при `messages.onExtendStay = false` сообщения нет, при `true` — есть (ответ на вопрос 1 меняет только настройку).

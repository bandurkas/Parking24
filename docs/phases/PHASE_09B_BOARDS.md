# Ф9б. Табло «Планируют выезд», фильтры, московское время, мелочи

Дорожка Д2, после Ф9а и Ф3. Код на `88c9425`. Разделы ТЗ: 3.1, 3.2, 3.3 треб. 1.

## 1. Цель

Администратор и охрана должны заранее видеть, кто уезжает в ближайшие сутки, и находить такие брони фильтром в таблице. Плюс убрать три места, где время показано не по Москве, и закрыть мелкие ошибки экранов, найденные сверкой 22.09.

## 3. Решения

### 3.1. Одно правило окна 24 часов

ТЗ п. 3.1 («табло … в ближайшие 24 часа») и п. 4.2 («планируемые выезды … за ближайшие 24 часа») — это **один и тот же показатель**. Сверка §3 нашла три разных числа (`boards/[kind]/page.tsx:36`, `today/page.tsx:27`, `occupancy.ts:131`), потому что каждое место считало по своим календарным датам.

**Решено.** Окно считается **от текущего момента**, а не по календарным суткам, одной чистой функцией:

```ts
// src/lib/occupancy-math.ts — кладёт Ф3, см. §4
export const DUE_WINDOW_H = 24;
export type Due = "soon" | "late" | null;

// «Ближайшие 24 часа» (ТЗ 3.1 и 4.2) — от момента, а не по календарным суткам.
// "late" — плановый момент уже прошёл: строка остаётся в списке, пока машина не выехала.
export function dueState(plannedAt: Date, now: Date, windowH = DUE_WINDOW_H): Due {
  const diff = plannedAt.getTime() - now.getTime();
  if (diff < 0) return "late";
  return diff <= windowH * 3_600_000 ? "soon" : null;
}
```

Показатель «Выезды за 24 ч» везде равен числу броней с `dueState(...) !== null`: и на панели `/admin/occupancy` (Ф3), и в заголовке табло на `/admin/today`, и на полосе доски, и во вкладке охраны. **Просроченные не выносятся в отдельный набор — это признак строки, а не другой список.** Машина, которая должна была уехать вчера, всё ещё «планирует выезд».

*Отвергнуто:* считать окно как «сегодня и завтра» по датам — именно так получились три разных числа; и «отдельно soon, отдельно late» — тогда числа опять разойдутся.

### 3.2. Плановый момент выезда

Плановый момент = `plannedMoment(dateTo, timeTo)` (дата брони + время по Москве, без времени — 12:00). Это уже есть в `dates.ts:81-88` и покрыто `tests/unit/planned-moment.test.ts`; Ф3 чинит его независимость от пояса процесса.

### 3.3. «Просрочен» — это перестой, а не прошедший плановый момент

У большинства броней `timeTo` не заполнено, и плановый момент — полдень. Если красить красным всё, у чего `dueState === "late"`, после 12:00 покраснеет половина табло, хотя день выезда ещё идёт и денег никто не должен.

**Решено.** Красная пометка на табло — существующее правило перестоя (`overstayOf`, `lib/overstay.ts`), как сейчас. Нейтральная серая подпись «плановое время прошло» показывается только когда `due === "late"` **и** `timeTo` у брони заполнено (то есть время действительно обещано клиентом). Двух правил «просрочки» в системе не заводим.

### 3.4. Блок «Отправление» заменяется блоком «Планируют выезд · 24 ч»

Сейчас на `/admin/today` два блока и список: «Прибытие», «Отправление» (`CHECKED_IN` с `dateTo ≤ сегодня`) и «Сейчас на стоянке» (`CHECKED_IN` с `dateTo > сегодня`).

**Решено.** «Отправление» становится «Планируют выезд · 24 ч» по правилу §3.1; «Сейчас на стоянке» переименовывается в «Ещё на стоянке» и показывает `CHECKED_IN` с `due === null`. Сумма двух множеств — по-прежнему все машины на парковке, счётчик «на стоянке» в шапке не меняет смысла.

*Отвергнуто:* добавить третий блок рядом с «Отправлением». Два пересекающихся списка выездов на одном экране — ровно то, что сверка назвала «три разных числа». Вынесено вопросом 3: экран заказчик видит каждый день.

### 3.5. «Прибытие» — рабочий список, а не показатель ТЗ

ТЗ называет показатель «Заезды за 24 ч» только на панели занятости (4.2) и определяет его как «подтверждённые автомобили». Список на `/admin/today` — рабочий: в нём нужны и «Новая заявка», и опоздавшие.

**Решено.**
- Список строится по `ARRIVAL_STATUSES` из Ф3 (см. §4) — если Ф3 включит туда `NEW`, числа совпадут сами.
- Показывается `dueState !== null`; опоздание глубже `ARRIVAL_LATE_H = 48` не показывается — столько же, сколько порог автоперехода в «Не приехал» (PLAN §1, `CancellationPolicy.autoNoShowAfterHours`). После Ф7 ограничение станет лишним: бронь сама уйдёт в `NO_SHOW` и выпадет из статусов.
- Заголовок блока подписан «Ожидаем», а не «Заезды за 24 ч», и его число не обязано совпадать с плиткой. Оба числа при этом на одном экране: в шапку `/admin/today` выводятся плитки «Заезды за 24 ч» и «Выезды за 24 ч» из `parkingDashboard` (Ф3).

### 3.6. Экран охраны: окно по умолчанию, поиск по всем

Вкладка «Выезд» сейчас — все `CHECKED_IN` (`GuardScreen.tsx:24-25`). Охрана обязана выпустить любую машину, в том числе уезжающую на три дня раньше.

**Решено.** Вкладка «Выезд» по умолчанию показывает окно 24 ч и просроченных; ниже строка «Ещё на стоянке: N · показать всех». Как только охранник набирает госномер, телефон или номер брони, **поиск идёт по всем** `CHECKED_IN`, без окна. Ни один сценарий выпуска не закрывается. Вынесено вопросом 3.

### 3.7. Кнопка у охраны — по таблице переходов

`GuardScreen.tsx:82` разрешает «Заехал» для `NEW`, а `TRANSITIONS.NEW` (`labels.ts:55`) такого перехода не содержит: кнопка нажимается, сервер отказывает. **Решено:** `can = TRANSITIONS[r.status].includes(to) && GUARD_TRANSITIONS.includes(to)` — одно правило, то же, что у `TransitionButtons`. Под неактивной кнопкой — подсказка «Сначала администратор подтвердит место».

### 3.8. Подписи `CONFIRMED` против решения 3

Решение 3 (PLAN §1): «Предоплаты нет. „Ожидает оплаты“ держит место, клиент платит на въезде. Окончательно подтверждённой бронь становится после оплаты („Подтверждена“)». Сейчас интерфейс этому противоречит: короткая подпись `CONFIRMED` — «Оплачена» (`labels.ts:17`) даже при нуле оплаты; главная кнопка «Подтвердить» ведёт в `CONFIRMED` без денег (`labels.ts:69`, `TransitionButtons.tsx:11`); «Сразу подтвердить» в быстрой брони создаёт `CONFIRMED` (`QuickBookingDrawer.tsx:285,318`).

**Решено в этой фазе (только подписи, поведение не меняется):** `STATUS_SHORT.CONFIRMED` = «Подтверждена». Оплату и без того видно отдельно: `paidAmount < amount` рисует «не оплачено» и «оплачено N».

**Отдано вопросом 2** (это изменение поведения, а не подписи): убирать ли ручной переход в `CONFIRMED` из главных кнопок и что должна ставить «Сразу подтвердить» в быстрой брони. Пока ответа нет — ни `TRANSITIONS`, ни `PRIMARY`, ни `status` в быстрой брони не трогаем.

### 3.9. Часы шапки: время с сервера, тик на клиенте

Правило проекта — форматировать время на сервере и отдавать в клиент готовые строки. Часы обязаны тикать, поэтому:

- `AdminShell` (сервер) вызывает чистый `clockNow()` и отдаёт готовые строки в `Topbar` → `Clock`.
- `Clock` берёт их начальным состоянием (`useState(initial)`) — первая отрисовка сервера и клиента совпадают, гидратация чистая, `setState` в теле эффекта исчезает вместе с ошибкой линтера.
- Форматирование — `Intl` с `timeZone: "Europe/Moscow"`: браузер администратора может стоять в любом поясе.
- Часы браузера могут врать. При гидратации один раз считаем расхождение с серверным моментом и дальше тикаем от него.
- Рядом со временем — подпись «МСК».

*Отвергнуто:* `useSyncExternalStore` — для часов это втрое больше кода при том же результате; `setTimeout(…, 0)` вокруг `setNow` — обход правила линтера, а не его исполнение.

### 3.10. Даты по умолчанию в быстрой брони

`iso(offset)` (`QuickBookingDrawer.tsx:28-32`) смешивает локальный `getDate()` с `toISOString()`. У администратора в Москве после 21:00 UTC (00:00 МСК) подставляется вчерашняя дата.

**Решено.** Чистый помощник `moscowDatePlus(n)` в новом `src/lib/moscow.ts`, туда же переезжает тело `moscowIso` из `dates.ts` (`dates.ts` его реэкспортирует — второй копии правила не появляется). Вызывается он в `reset()`, то есть при каждом открытии ящика: даты всегда свежие.

### 3.11. Фильтр в таблице

`KanbanItem` получает три поля, все считаются на сервере в `boards/[kind]/page.tsx`: `timeTo`, `due: Due`, `dueAt: string | null` (готовая строка «сегодня 12:00»). `due` считается **только для выездов** (`CHECKED_IN`) — ТЗ 3.2 просит один фильтр, и двусмысленности «заезд или выезд» не возникает.

Фильтр — один чип «Планируют выезд · 24 ч» рядом с чипами статусов, `due !== null`. Симметричный чип для заездов ТЗ не просит и мы его не добавляем.

Там же в `boards/[kind]/page.tsx` исчезают два `prisma.booking.count` (`:36`, `:38`): счётчики полосы считаются из уже загруженных строк тем же `dueState`.

### 3.12. Ширина канбана

Семь колонок по 272 px не помещаются в 1440 px ни при какой вёрстке. **Решено:** колонки сужаются до 228 px (`2xl` — прежние 272), а две терминальные («Отклонена» и «Отменена/No-show») по умолчанию свёрнуты в вертикальные полосы 56 px. Они остаются `useDroppable`, то есть перетащить в них карточку по-прежнему можно. Разворот — ссылкой `?cols=all`, как уже сделан переключатель `?view=table`: никакого состояния, никакого `localStorage`, ничего не ломается при гидратации. Пять рабочих колонок при 1440 px видны без горизонтальной прокрутки.

### 3.13. Клавиатура охраны

Сейчас из букв только «А» (`GuardScreen.tsx:42`). В российских номерах 12 букв. **Решено:** две группы клавиш — цифры `1…0` плюс `⌫` и ряд букв `А В Е К М Н О Р С Т У Х`. `normalizePlate` уже переводит латиницу в кириллицу (`phone.ts:25-30`), так что физическая клавиатура планшета тоже работает.

### 3.14. Ранний заезд — предупреждение в интерфейсе

Сервер разрешает ранний заезд осознанно (Ф2а: ранний заезд держит место). Запрет ломал бы реальную работу. **Решено:** `window.confirm` перед «Заехал», если `dateFrom` больше сегодняшней московской даты: «Заезд раньше брони (с 26 сен). Отметить заезд?». Правило — чистая функция, вызывается из `GuardScreen` и из `TransitionButtons` (необязательный проп; там, где проп не передан, подтверждения нет — карточка брони остаётся без изменений и не конфликтует с Ф4/Ф10).

### 3.15. Схема и выключатели

**Изменений схемы нет.** Ни таблиц, ни полей, ни новых значений enum.

**Выключателей в `Setting` не заводим:** фаза не добавляет ни одного автоматического поведения. Табло, фильтр, формат времени и подписи — представление уже существующих данных; ничего не отправляется, не переводится и не начисляется. Единственное новое умолчание (свёрнутые терминальные колонки) переключается ссылкой в адресе.

```ts
// «22 сен 2026, 14:05» по Москве — журнал действий и другие точные моменты
export function fmtDateTimeFull(d: Date): string {
  return new Intl.DateTimeFormat("ru-RU", { timeZone: "Europe/Moscow", day: "2-digit", month: "short", year: "numeric", hour: "2-digit", minute: "2-digit" }).format(d);
}

// «сегодня 12:00» · «завтра 09:00» · «вчера 12:00» · «26 сен, 12:00» — плановый момент на табло.
// today — сегодняшняя дата по Москве; день момента тоже берётся по Москве, иначе 00:30 МСК уедет во вчера.
export function fmtDueAt(plannedAt: Date, today: string): string {
  const day = moscowIso(plannedAt);
  const hhmm = new Intl.DateTimeFormat("ru-RU", { timeZone: "Europe/Moscow", hour: "2-digit", minute: "2-digit" }).format(plannedAt);
  if (day === today) return `сегодня ${hhmm}`;
  if (day === addDays(today, 1)) return `завтра ${hhmm}`;
  if (day === addDays(today, -1)) return `вчера ${hhmm}`;
  return `${fmtDate(day, { day: "numeric", month: "short" })}, ${hhmm}`;
}
```

`fmtDate(day, …)` получает строку даты, а не момент: `fmtDate` форматирует в UTC, и только со строкой это верно в любом поясе.

# Ф10. Возвраты, пересчёт и «Исправить статус»

Дорожка **Д5 (деньги)**, первая фаза. Источники: `docs/TZ_STATUS_2026-09-22_night.md` §3 (блок Ф10), §4 (зависимости), §5 (вопросы); `docs/TZ_2026-09-21_PLAN.md` §1 (решения 22.09 и 23.09); `docs/TZ_2026-09-21_SOURCE.md` 5.3 и 8.5; `docs/phases/PHASE_SP_URGENT_FIXES.md` (что уже сделано и что легло в бэклог Ф10).

Код читался на `19cc5f2` (после разреза `bookings.ts` на модули). Порядок фазы по PLAN §5а: архитектура → критика → код → тесты → ревью (2 раунда) → stage.

**Зависимости и порядок слияния.** Ф10 идёт **после Ф9а** (убрано ручное время: `transition` больше не принимает `at`) и **после Ф3** (потолок мест в `correctStatus` и `transition`). Все три фазы правят `transition.ts` и `correct.ts`, но разные куски; Ф10 сливается последней из трёх.

---

## 1. Зачем

Сейчас система умеет принимать возврат, но не умеет **посчитать его сама**: баннер «Стоянка по факту» и кнопка «Пересчитать по факту» считают сумму двумя разными формулами, при ручной цене пересчёт по тарифу стирает договорённость, а поздний заезд показывает несуществующую переплату. Ф10 делает расчёт одним правилом в одном месте, доводит возврат до вида из ТЗ 5.3 (номер брони, сумма, причина, способ, сотрудник, дата и время), закрывает дыры в «Исправить статус» (забытый заезд и выезд датой без времени, открытие закрытой брони) и закладывает в модель `Payment` то, что через фазу понадобится кассе — способ оплаты, причину, автора и сторно.

---

## 2. Что входит и что не входит

### Входит

1. **Одна формула пересчёта после выезда** для баннера и для действия, с корректными оплачиваемыми сутками (поздний заезд не даёт переплаты).
2. **Пересчёт при ручной цене и скидке** — пропорционально, а не по тарифу.
3. **«Оформить возврат» с готовой суммой** из блока «Оплата», видимая строка «переплата N ₽».
4. **`Payment.reason`** — отдельное поле причины (возврат, сторно) вместо примечания.
5. **Сторно ошибочной оплаты** (`PaymentStatus.VOID`, автор, причина, время) — владелец.
6. **«Исправить статус» датой без времени** для забытого заезда и выезда (решение 23.09 п. 5), с расчётом фактических суток и без начисления за перестой.
7. **Права на «Исправить статус»**: закрытую бронь открывает владелец.
8. **Мелкие дыры Ф10 из сверки:** полный возврат до заезда и статус брони; фура с ценой 0 не становится «Подтверждена» от любой оплаты; отметки отклонения больше не стираются; время платежа по Москве; автор платежа в карточке; «Отменена» из перестоя пишет «перестой не начислен»; снятие начисления за перестой при открытом баннере.

### Не входит (границы по §4 сверки)

| Не делаем | Чья фаза | Почему |
|---|---|---|
| Ручной ввод времени заезда и выезда (поле `datetime-local`, `window.prompt`, параметр `at`) | **Ф9а** | Ф10 не трогает `TransitionButtons`, `KanbanBoard`, `transitionAction`. Код Ф10 в `transition` пишется так, чтобы работать и с `at`, и без него |
| Проверка мест при «Исправить статус» и при переходах | **Ф3** | Ф10 добавляет в `correctStatus` параметр дат, Ф3 — проверку мест в ту же функцию. Ф10 сливается после Ф3 |
| Смены, инкассация, привязка платежа к смене, `cash.requireShift`, снимок смены, индекс `Payment(kind,status,paidAt)`, `onDelete: Restrict` | **Ф11** | Ф10 только готовит модель `Payment` (§9) |
| Финансовый отчёт, строка возвратов, список смен, границы периода по Москве | **Ф12** | Ф10 лишь перестаёт стирать историю отклонений, чтобы отчёт не менялся задним числом |
| Сообщения клиенту о возврате, пересчёте, исправлении статуса; номер договора после «Исправить статус» | **Ф5, Ф6** | Ф10 не ставит ничего в Outbox и не заводит шаблонов. Отмена запланированных сообщений при исправлении статуса уже есть и остаётся |
| Уведомление администратору (колокольчик) о сторно и расхождениях | **Ф2б, Ф11** | `NoticeKind` и `notify(tx, key)` — фаза Ф2б; Ф10 пишет только в ленту брони и в журнал |
| Страница «Отмена и возвраты» в настройках, редактирование шаблонов | **МФ-2** | Ф10 добавляет один выключатель прямо на `/admin/settings` (дописывание в конец файла разрешено шагом 0 оркестратора) |
| Комнаты: правило «не раньше планового заезда» | — | Комнаты считаются 24-часовыми периодами от фактических времён; формула для них не меняется |

## 3. Решения

### Р1. Оплачиваемые сутки: с плановой даты заезда или с фактической — что раньше

**Выбрано.** Фактические сутки (`Booking.actualDays`) считаются от **`min(дата фактического заезда, dateFrom)`** до даты фактического выезда (с уже действующим льготным часом после плановой даты выезда).

**Почему.** Сейчас счёт идёт от фактического заезда, поэтому поздний заезд (клиент приехал на два дня позже) даёт `actualDays < days`, открывается баннер и предлагается **вернуть деньги за место, которое мы держали**. Это прямо противоречит решению «место держится с плановой даты» (PLAN §1, 1.1 и ответ 3). Досрочный выезд при этом считается по-прежнему, ранний заезд по-прежнему добавляет сутки (место занято по факту).

**Отвергли.** «Считать от `dateFrom` всегда» — потеряли бы ранний заезд, за который сейчас справедливо берут доплату. «Оставить как есть и просто не показывать баннер при позднем заезде» — расчёт остался бы неверным внутри `decideRecalc`.

```ts
// src/lib/recalc.ts — чистая функция, одинаково в транзакции, в исправлении статуса и в тестах
export function billableParkingDays(a: { dateFrom: string; inDate: string; outDate: string }): number {
  const start = a.inDate && a.inDate < a.dateFrom ? a.inDate : a.dateFrom;
  return Math.max(1, parkingDays(start, a.outDate));
}
```

`actualParkingDays` в `src/server/lib/dates.ts` получает четвёртый аргумент `plannedFrom` и делегирует сюда; поведение без этого аргумента не меняется (старые юнит-тесты остаются зелёными).

### Р2. Одна формула пересчёта для баннера и для действия

**Выбрано.** Баннер больше ничего не считает: сумму, разницу и цену суток он получает готовыми с сервера. Источник — `recalcPlanOf(booking)` в новом `src/server/services/recalc.ts`, её же вызывает `decideRecalc`.

**Почему.** Сейчас баннер показывает `actualDays × perDay(1 сутки)` (`PriceTools.tsx:13`), а действие считает `quote(kind, actualDays)`. Ступень тарифа выбирается по суткам, поэтому от 30 суток (легковая 250 ₽ вместо 350 ₽) человек видит одну сумму, а нажимает другую. Правило проекта «одно правило в одном месте» требует единой функции.

**Отвергли.** «Передавать в баннер правильный `perDay` и оставить умножение на клиенте» — формула всё равно осталась бы в двух местах и разошлась бы при первой же правке (например, при пропорциональном пересчёте из Р3).

### Р3. Ручная цена и скидка — пропорционально, а не по тарифу

**Выбрано.** Признак ручной цены — расхождение суммы брони с тарифной ценой на плановые сутки (никакого нового поля не нужно). Дальше три режима:

| Режим | Когда | Новая сумма |
|---|---|---|
| `tariff` | цена совпадает с тарифом на плановые сутки | `actualDays × цена суток по тарифу для actualDays` |
| `manual` | цена задана вручную (скидка, договорённость), начисления за перестой нет | `round(amount × actualDays / days)` |
| `none` | тариф не задан (фура «по запросу») **или** ручная цена вместе с начислением за перестой | не пересчитываем: только «Оставить по плану», в баннере подсказка «поправьте сумму через „Изменить цену“ с причиной» |

**Почему.** ТЗ 8.5 в редакции заказчика: «возврат считается посуточно по тому же правилу, что и цена». У брони с ручной ценой цена суток — это её собственная цена, делённая на сутки, а не тариф. Режим `none` нужен, чтобы не изобретать правило там, где сумма — это смесь ручной цены и начисленного перестоя: таких броней единицы, и решение принимает человек (пользователь: «перестой бывает редко — решения держим простыми»).

**Отвергли.** Новое поле `Booking.priceManualAt` — лишняя миграция и пять мест записи, при том что сравнение с тарифом даёт тот же ответ. Если тариф изменят задним числом, сравнение объявит старую бронь «ручной» и посчитает пропорционально — то есть сохранит цену, по которой клиенту обещали, а это как раз желаемое поведение.

```ts
// src/lib/recalc.ts
export type RecalcMode = "tariff" | "manual" | "none";
export type RecalcPlan = { days: number; actualDays: number; amount: number; delta: number; perDay: number; mode: RecalcMode; hint: string };

export function recalcFrom(
  b: { days: number; actualDays: number; amount: number; overstayCharge: number | null },
  t: { plannedAmount: number; actualAmount: number; actualPerDay: number },
): RecalcPlan {
  const manual = t.plannedAmount > 0 && t.plannedAmount !== b.amount;
  if (t.actualPerDay <= 0) return plan(b, b.amount, 0, "none", "цена по запросу — поправьте сумму через «Изменить цену»");
  if (manual && b.overstayCharge) return plan(b, b.amount, t.actualPerDay, "none", "сумма задана вручную и есть начисление за перестой — решает «Изменить цену» с причиной");
  if (manual) return plan(b, Math.round((b.amount * b.actualDays) / b.days), t.actualPerDay, "manual", "сумма брони задана вручную — считаем пропорционально суткам");
  return plan(b, t.actualAmount, t.actualPerDay, "tariff", "");
}
```

Цена по тарифу считается общей чистой функцией `priceFor(tariffs, kind, days, opts)`, вынесенной из `quote()`; `quote()` становится тонкой обёрткой над ней. Так тарифная ступень у заявки, у пересчёта и у долга за перестой выбирается одним кодом.

### Р4. «Оформить возврат» с готовой суммой и видимая переплата

**Выбрано.**
- В блоке «Оплата» карточки появляется строка **«переплата N ₽»** (сейчас переплата вообще не видна: при `unpaid = 0` пишется «оплачено»).
- Кнопка возврата получает подпись **«Оформить возврат N ₽»**, когда есть переплата и бронь не в перестое; сумма и способ «Наличные» подставляются как сейчас (правило СП §3.3 п. 18 не меняется).
- Если после возврата остался остаток переплаты, кнопка снова показывает остаток — деньги не «теряются» из виду.

**Почему.** ТЗ 5.3 требует «дать расчёт» и оформить возврат готовой суммой; сверка отмечает, что остаток переплаты сейчас молча висит на брони.

**Отвергли.** Отдельную кнопку «Оформить возврат» внутри баннера пересчёта — баннер исчезает сразу после решения, и кнопка пропала бы вместе с ним; возврат нужен и тогда, когда баннера не было (решение «Оставить по плану», ошибочная оплата).

### Р5. Статус после полного возврата до заезда — под выключателем

**Выбрано.** Новый ключ `money.demoteOnFullRefund` (по умолчанию **выключено**, на stage выкатывается выключенным). Когда включён: если бронь в статусе «Подтверждена», заезда не было и после возврата `paidAmount = 0`, бронь возвращается в «Ожидает оплаты». Запись в ленте «Подтверждена → Ожидает оплаты (оплата возвращена полностью)», автоматизации **не запускаются** (это исправление учёта, а не событие для клиента), автор — тот, кто провёл возврат.

**Почему.** По решению 3 «Подтверждена» значит «оплачена»; после полного возврата это неправда, а место бронь держит. Правило проекта требует выключатель для каждого нового автоматического поведения.

**Отвергли.** Откат при любом частичном возврате — неоплаченная наполовину бронь и сейчас остаётся «Подтверждена», менять это без запроса заказчика нельзя. Открытый вопрос **В1**.

### Р6. Фура с ценой 0 не становится «Подтверждена» от любой оплаты

**Выбрано.** Условие автоперехода в `addPayment` дополняется `b.amount > 0`.

**Почему.** Сейчас у брони с ценой 0 («по запросу» у фур) любая оплата в 1 ₽ делает её «Подтверждена». Администратор сначала ставит цену («Изменить цену» с причиной), потом принимает оплату.

**Отвергли.** Считать бронь с ценой 0 оплаченной сразу — тогда фура попадала бы в «оплаченные» в отчёте Ф12.

### Р7. «Исправить статус»: забытый заезд и выезд — датой без времени

**Выбрано** (решение пользователя 23.09 п. 5).
- `correctStatus` получает необязательные `inDate` и `outDate` (`YYYY-MM-DD`).
- Дата заезда обязательна при переходе в «Заехал» и при переходе в «Выехал», если `checkedInAt` пуст (закрывает дыру «исправление сразу в „Выехал“ оставляет `checkedInAt = null`»).
- Дата выезда обязательна при переходе в «Выехал».
- Дата не может быть в будущем (по Москве), выезд не раньше заезда.
- Хранится момент **12:00 по Москве** этой даты (`plannedMoment(date)`), плюс признаки `checkedInDateOnly` / `checkedOutDateOnly`. В карточке при поднятом признаке печатается только дата, без времени и без «по факту 3 ч 20 мин» — система не выдумывает время, которого не знает.
- `actualDays` считается по правилу Р1 из дат; если он разошёлся с планом — остаётся открытым баннер «Стоянка по факту», и администратор решает деньги явно.
- Начисление за перестой по-прежнему **не производится** (это путь для забытого выезда), но строка «Перестой N сут. не начислен (сумма) · причина» теперь пишется и при исправлении из «Заехал» в «Отменена» и «Не приехал», а не только в «Выехал» (бэклог СП).

**Почему.** Ручной ввод времени убирает Ф9а; ставить «время нажатия кнопки» для события трёхдневной давности — та самая ошибка, из-за которой ТЗ 3.3 требует автоматической фиксации. Полдень выбран, чтобы дата не «переезжала» в соседние сутки ни в одном представлении.

**Отвергли.** 00:00 по Москве — визуально неотличимо от настоящего выезда в полночь и опасно рядом с льготным часом (01:00). Хранить время исправления — прямо противоречит решению 23.09 п. 5. Открытый вопрос **В6**.

### Р8. Закрытую бронь открывает владелец

**Выбрано.** `correctStatus` **из** статусов «Выехал», «Отменена», «Не приехал» разрешён только владельцу: «Закрытую бронь открывает только владелец: деньги по ней уже посчитаны». Администратор по-прежнему свободно исправляет статусы среди открытых и **в** закрытые (отметить выезд, отменить).

Кроме того, при выходе из «Выехал» сбрасываются `actualDays` и `recalcDecidedAt` (иначе повторный выезд не покажет баннер), а сумма и начисление за перестой **не трогаются**; в ленту пишется: «Бронь открыта заново: сумма 1 750 ₽ и начисление за перестой 700 ₽ остаются — при повторном выезде начислятся только новые сутки».

**Почему.** Сейчас «Выехал» → «Заехал» обходит `assertMoneyEditable` («после выезда цену меняет только владелец»): администратор открывает бронь, правит деньги и закрывает обратно. Это та же дыра, что закрывала СП, только через другую дверь.

**Отвергли.** Автоматический откат суммы и начисления при открытии — уже проведённые платежи и возвраты сделали бы такой откат неверным; лучше явная запись в ленте. Открытый вопрос **В2**.

### Р9. Сторно ошибочной оплаты

**Выбрано.**
- Новое значение `PaymentStatus.VOID` (отдельной миграцией, без использования в ней же) и поля `Payment.voidedAt`, `voidedById`, `voidReason`.
- Действие `voidPayment(paymentId, reason, actor)` — **только владелец**, только `kind = PAYMENT` и `status = SUCCEEDED`, причина от 3 символов, всё под `lockBooking`.
- Сторно **не меняет сумму брони**; в форме подтверждения написано: «Сторно отменит только учёт оплаты. Если этой оплатой меняли сумму брони („Это полная стоимость“), поправьте сумму отдельно».
- `paidAmount` после сторно **пересчитывается из платежей** (`SUCCEEDED PAYMENT − SUCCEEDED REFUND`), а не правится дельтой.
- В карточке строка платежа зачёркнута, с пометкой «сторно · причина · кто · когда». В ленте — запись `PAYMENT`: «Сторно оплаты 1 050 ₽ от 22 сент · причина». В журнале — `UPDATE Payment`.

**Почему `VOID`, а не удаление и не встречная запись.** Выручка на дашборде, LTV клиента, будущий снимок кассовой смены и отчёт Ф12 уже фильтруют платежи по `status = SUCCEEDED` — сторнированный платёж выпадает из всех сумм сам, без правки этих мест. Удаление уничтожило бы историю (и упирается в `onDelete`), а встречная запись «минус 1 050» раздула бы обороты смены вдвое: в кассе появилось бы движение денег, которого не было.

**Почему только оплаты.** Ошибочный возврат — это уже выданные из кассы деньги; его гасят новой оплатой, а не «отменой».

**Контракт для Ф11:** сторно допустимо, **пока смена платежа не закрыта**; после закрытия смены ошибка исправляется возвратом. Проверку добавит Ф11 в ту же функцию — место под неё помечено комментарием. Открытый вопрос **В3**.

### Р10. `Payment.reason` — отдельное поле причины

**Выбрано.** Добавляем `Payment.reason String?`. Причина возврата и причина сторно пишутся туда; `note` остаётся свободным примечанием к оплате. В карточке показывается `reason ?? note` (старые возвраты, у которых причина лежит в `note`, отображаются как раньше — миграция ничего не пересчитывает).

**Почему.** ТЗ 5.3 требует причину как отдельный реквизит операции; касса и отчёт будут её печатать, и вынимать её из свободного примечания нельзя.

### Р11. Снятие начисления за перестой при открытом баннере

**Выбрано** (бэклог СП §13): `waiveOverstay` отказывает, пока не решён баннер «Стоянка по факту»: «Сначала решите „Стоянка по факту“».

**Почему.** Иначе «Пересчитать по факту» после снятия возвращает снятые сутки обратно — начисление всплывает второй раз.

**Отвергли.** «Снятие само закрывает баннер» — человек теряет видимый расчёт досрочного выезда, а это как раз то, что просил заказчик показывать. Открытый вопрос **В7**.

### Р12. Отметки отклонения больше не стираются

**Выбрано.** `transition` и `correctStatus` перестают обнулять `rejectedAt`, `rejectKind`, `rejectReason` при выходе из «Отклонена». Вместо обнуления — запись в ленте: «Отклонение снято (нет мест) → Ожидает оплаты · причина». Отметки `cancelledAt` и `noShowAt` продолжают сбрасываться как сейчас (они привязаны к статусу, а не к отчёту). В карточке шаг «Отклонена / Отменена / Не приехал» берёт время из отметки, **соответствующей текущему статусу**, а не первой непустой.

**Почему.** Отчёт Ф12 считает отклонённые заявки за период, сегмент «не смогли попасть» (Ф8) ищет `rejectKind = NO_SPACE`. Если подтверждение из резерва стирает отметку, отчёт за прошлый месяц меняется задним числом. По §4 сверки отметки отклонения меняет **только Ф10**.

### Р13. Время платежа по Москве и автор операции

**Выбрано.** Дата и время платежа форматируются **на сервере** (`fmtDateTime`, зона Europe/Moscow) и приходят в `PaymentPanel` готовой строкой; в строку добавляется имя сотрудника (`payments.createdBy.name`, для сторно — `voidedBy.name`). В `bookingInclude.payments` добавляется `createdBy: { select: { name: true } }` и `voidedBy: { select: { name: true } }`.

**Почему.** Сейчас строка рисуется `new Date(p.paidAt).toLocaleDateString("ru-RU", …)` в браузере — без зоны и без времени; ТЗ 3.3 требует московское время, ТЗ 5.3 — сотрудника, оформившего операцию.

### Р14. Что не меняется

LTV (`recalcLtv` уже фильтрует по `SUCCEEDED`), «Выручка за месяц» на дашборде, правила возврата из СП (`applyRefund`, `refundLimit`, «не больше оплаченного», причина обязательна, администратор после выезда возвращает только переплату), начисление и льготный час перестоя, отмена запланированных сообщений при исправлении статуса. Системные действия по-прежнему пишутся с `userId = null` — в Ф10 системных действий нет, все операции инициирует человек.

```ts
export async function voidPayment(paymentId: string, reason: string, actor: SessionUser) {
  if (actor.role !== "OWNER") throw new BookingError("Сторно оформляет владелец");
  const why = reason.trim();
  if (why.length < 3) throw new BookingError("Укажите причину сторно");
  return prisma.$transaction(async (tx) => {
    const head = await tx.payment.findUniqueOrThrow({ where: { id: paymentId }, select: { bookingId: true } });
    await lockBooking(tx, head.bookingId);                       // деньги брони меняем только под блокировкой строки
    const p = await tx.payment.findUniqueOrThrow({ where: { id: paymentId } });
    if (p.kind !== "PAYMENT") throw new BookingError("Сторнируется только оплата: ошибочный возврат гасится новой оплатой");
    if (p.status !== "SUCCEEDED") throw new BookingError("Платёж уже сторнирован");
    // Ф11: здесь же — «смена этого платежа ещё открыта», после закрытия смены ошибка исправляется возвратом
    await tx.payment.update({ where: { id: p.id }, data: { status: "VOID", voidedAt: new Date(), voidedById: actor.id, voidReason: why } });
    const paid = await paidFromPayments(tx, p.bookingId);        // SUCCEEDED PAYMENT − SUCCEEDED REFUND
    const b = await tx.booking.update({ where: { id: p.bookingId }, data: { paidAmount: paid } });
    // лента PAYMENT: «Сторно оплаты 1 050 ₽ от 22 сент · <причина> · оплачено 1 050 → 0 ₽»
    // журнал: UPDATE Payment { void: true, amount, reason }
    if (b.clientId) await recalcLtv(b.clientId, tx);
    return b;
  });
}
```

## 6. Риски

| Риск | Что делаем |
|---|---|
| Новая формула суток меняет деньги задним числом у уже закрытых броней | Старые строки не пересчитываются; формула работает только при новом выезде или новом исправлении статуса. Деньги не двигаются автоматически: сумму меняет человек кнопкой в баннере |
| Признак «ручная цена» ловит бронь, у которой просто поменяли тариф | Пропорциональный пересчёт сохраняет обещанную клиенту цену — это безопаснее тарифного. В ленте пишется, в каком режиме считали |
| Пропорция даёт копеечную разницу при делении | `round(amount × actualDays / days)` — одно округление; при `actualDays = days` даёт ровно прежнюю сумму, и такой случай вообще не открывает баннер |
| Сторно платежа, которым меняли сумму брони («Это полная стоимость») | Сумма не откатывается; предупреждение в форме, запись в ленте, владелец правит «Изменить цену» |
| Сторно платежа из закрытой смены (после Ф11) испортит закрытый отчёт | Контракт §9: сторно только внутри открытой смены; место под проверку помечено в `voidPayment` |
| Полдень как время забытого заезда выглядит настоящим | Признаки `checkedInDateOnly`/`checkedOutDateOnly`: в карточке печатается только дата и подпись «время не указано», длительность стоянки не показывается |
| Откат статуса после полного возврата разбудит сообщения клиенту | Автоматизации при откате не вызываются; сам откат под выключателем, на stage выключен |
| Открытие закрытой брони владельцем оставит завышенную сумму и начисление за перестой | Явная запись в ленте, что именно осталось; сумму владелец правит «Изменить цену» |
| Ф3 и Ф9а правят те же `transition.ts` и `correct.ts` | Порядок слияния Ф9а → Ф3 → Ф10 зафиксирован в §4 сверки; Ф10 добавляет параметр `dates` в `correctStatus`, Ф3 — проверку мест в ту же функцию; конфликт разводится по строкам |
| Отметки отклонения перестали стираться — где-то посчитаются дважды | В коде их читают только карточка брони (шаг конвейера) и будущие Ф8/Ф12; карточка переводится на «отметку текущего статуса», в Ф12 правило описано в §9 |

## 7. Критерии приёмки (что проверяет человек глазами)

1. **Досрочный выезд.** Бронь 3 суток за 1 050 ₽, выезд в первый день. Баннер: «Стоянка по факту: 1 сут. (по плану 3) · переплата 700 ₽ · итого 350 ₽ вместо 1 050 ₽». «Пересчитать по факту» → сумма 350 ₽, в блоке «Оплата» появляется строка «переплата 700 ₽» и кнопка «Оформить возврат 700 ₽».
2. **Возврат.** Кнопка открывает форму с суммой 700 ₽ и способом «Наличные»; без причины «Провести» недоступна; после проведения — «оплачено», переплаты нет, в списке платежей строка «22 сент, 14:05 · Наличные · Иванов · досрочный выезд · −700 ₽».
3. **Частичный возврат.** Вернули 400 из 700 — на карточке остаётся «переплата 300 ₽» и кнопка «Оформить возврат 300 ₽».
4. **Длинная бронь.** У брони от 30 суток сумма в баннере и сумма после нажатия совпадают.
5. **Ручная цена.** У брони со скидкой (цена изменена вручную) баннер пишет «сумма брони задана вручную — считаем пропорционально суткам» и предлагает пропорциональную сумму, а не тарифную.
6. **Фура «по запросу».** У брони с ценой 0 кнопки «Пересчитать по факту» нет, есть подсказка про «Изменить цену»; оплата в 1 ₽ не делает бронь «Подтверждена».
7. **Поздний заезд.** Заезд отмечен на два дня позже планового, выезд — в плановую дату: баннер не появляется, переплаты нет.
8. **Забытый заезд и выезд.** «Исправить статус» → «Выехал» требует дату выезда (и дату заезда, если заезд не отмечен), будущие даты не принимает; после сохранения в карточке «Заехал: 18 сент», «Выехал: 20 сент» без времени, «по факту 3 сут.», в ленте — причина, а при перестое ещё и «Перестой 2 сут. не начислен (700 ₽)».
9. **Закрытая бронь.** Администратор в «Выехал» жмёт «Исправить статус» → «Заехал» и получает отказ «Закрытую бронь открывает только владелец»; владелец проходит, и в ленте видно, что сумма и начисление за перестой остались.
10. **Отмена из перестоя.** «Исправить статус» → «Отменена» у машины в перестое пишет в ленту «Перестой N сут. не начислен».
11. **Сторно.** У владельца в списке платежей есть «Сторно»; после сторно строка зачёркнута с пометкой «сторно · причина · кто», «оплачено» уменьшилось, сумма брони та же; повторное сторно того же платежа — отказ; у администратора кнопки нет.
12. **Снятие начисления.** Пока открыт баннер «Стоянка по факту», «Снять начисление за перестой» отказывает: «Сначала решите „Стоянка по факту“».
13. **Отклонение.** «Отклонена (нет мест)» → «Ожидает оплаты»: в ленте «Отклонение снято (нет мест)», карточка показывает новый статус.
14. **Время.** Время платежа в карточке — московское, одинаковое на компьютере администратора и на телефоне в другом часовом поясе.
15. **Выключатель.** На `/admin/settings` есть блок «Деньги» с выключателем «После полного возврата возвращать бронь в „Ожидает оплаты“»; на stage он **выключен**, и полный возврат до заезда оставляет статус «Подтверждена» с надписью «не оплачено».

## 9. Что Ф10 оставляет кассе (Ф11) — не проектируя кассу

| Что уже будет в модели | Как кассе этим пользоваться |
|---|---|
| `Payment.method` — четыре способа (наличные, карта, перевод, онлайн) | Снимок смены разносит суммы по способам без доработок Ф10 |
| `Payment.status` — `SUCCEEDED` / `VOID` | Итоги смены и отчёт считают только `SUCCEEDED`; сторнированный платёж выпадает из сумм сам |
| `Payment.reason` — обязательная причина возврата и сторно | Печатается в отчёте смены и в финансовом отчёте |
| `Payment.createdById`, `voidedById`, `paidAt`, `voidedAt` | «Сотрудник, оформивший операцию» и «дата и время операции» из ТЗ 5.3 |
| `paidFromPayments(tx, bookingId)` — пересчёт оплаченного из платежей | Ф11 пользуется ею же после любых операций смены |
| Пометка места в `voidPayment` | Ф11 добавляет туда правило: **сторно только пока смена платежа открыта**; после закрытия смены ошибка исправляется возвратом (иначе закрытый отчёт смены менялся бы задним числом) |
| Возврат по умолчанию — наличными | ТЗ 5.3: «возврат уменьшает остаток наличных в кассе» — Ф11 вычитает возвраты наличными из расчётного остатка |

**Что Ф11 добавляет сама:** `Payment.cashShiftId`, индекс `(kind, status, paidAt)`, замену `onDelete: Cascade` на `Restrict`, `cash.requireShift`, модели `CashShift` и `CashCollection`.

## 10. Открытые вопросы пользователю

Агенты спросить не могут, ответы собираются разом. До ответа код пишется по рекомендации — она уже заложена в решениях выше.

**В1. После полного возврата до заезда возвращать бронь в «Ожидает оплаты»?**
Варианты: оставить «Подтверждена» (видно только «не оплачено»); откатывать при полном возврате; откатывать при любом возврате, после которого оплата меньше суммы.
Рекомендация: **откатывать при полном возврате, под выключателем `money.demoteOnFullRefund`, на stage выключенным**. По решению 3 «Подтверждена» означает «оплачена», а после полного возврата это неправда; выключатель — требование правил проекта к любому новому автоматическому поведению.

**В2. «Исправить статус» из закрытой брони — только владелец?**
Варианты: только владелец для всех закрытых («Выехал», «Отменена», «Не приехал»); только для «Выехал», а «Отменена» и «Не приехал» — и администратору; как сейчас (любой администратор).
Рекомендация: **только владелец для всех закрытых**. Сейчас «Выехал» → «Заехал» обходит правило «после выезда деньги меняет только владелец»; одно правило на все закрытые статусы проще объяснить администратору, чем три исключения.

**В3. Сторно ошибочного платежа: кто делает и что именно можно сторнировать?**
Варианты: владелец, только оплаты, сумма брони не меняется; владелец и администратор в пределах своей смены; сторно не делаем вовсе — только возврат.
Рекомендация: **владелец, только оплаты**, сумма брони не меняется, в кассе сторнированный платёж просто выпадает из итогов открытой смены, а после закрытия смены сторно запрещено (ошибку исправляем возвратом). Ошибочный возврат — это выданные деньги, его гасят новой оплатой.

**В4. Что делать с остатком переплаты, если вернули меньше, чем переплатили?**
Варианты: показывать «переплата N ₽» и кнопку «Оформить возврат остатка», ничего не делая автоматически; не давать закрыть бронь, пока переплата не нулевая; разрешить владельцу зачесть остаток в сумму брони.
Рекомендация: **первый вариант**. Остаток — это чужие деньги, их нельзя ни списать автоматически, ни спрятать; достаточно, чтобы он был виден в карточке и попал в отчёт Ф12 отдельной строкой.

**В5. Как пересчитывать досрочный выезд у брони с ручной ценой или скидкой?**
Варианты: пропорционально фактическим суткам от цены самой брони; по тарифу (как сейчас); не пересчитывать автоматически, оставить владельцу «Изменить цену».
Рекомендация: **пропорционально**, а если к ручной цене добавилось начисление за перестой — не предлагать пересчёт вовсе. По ТЗ 8.5 возврат считается «по тому же правилу, что и цена»; у брони со скидкой её собственная цена суток и есть это правило, а тариф стёр бы договорённость с клиентом.

**В6. Забытый заезд или выезд отмечается датой без времени — что хранить в базе и что показывать?**
Варианты: 12:00 по Москве и признак «время не указано» (в карточке — только дата); 00:00 по Москве; время нажатия кнопки, как сейчас.
Рекомендация: **12:00 и признак**. Полдень не «переезжает» в соседние сутки ни в одном представлении и не путается с льготным часом перестоя (01:00), а признак не даёт системе показывать выдуманное время.

**В7. Снятие начисления за перестой, когда открыт баннер «Стоянка по факту».**
Варианты: не давать снять, пока баннер не решён; снятие само закрывает баннер; оставить как сейчас (оба действия независимы).
Рекомендация: **первый вариант** — так записал ревьюер СП (§13): иначе «Пересчитать по факту» после снятия вернёт снятые сутки обратно. Второй вариант прячет от администратора расчёт досрочного выезда, который заказчик просил показывать.

- **Роли:** `assertMoneyActor` (владелец/администратор) — второй рубеж в `addPayment`, `changePrice`, `decideRecalc`, `waiveOverstay`; сторно — `requireActor(OWNER)` + проверка в сервисе. DRIVER/PARKER/GUARD до денег не доходят.

### Отступления от тела документа

1. **Сторно — отдельная запись, не `PaymentStatus.VOID`.** Контракт оркестратора для Ф11 («сторно — ОТДЕЛЬНОЙ записью Payment, не правкой/удалением; реальные деньги — SUCCEEDED») и Ф12 («`reversalOfId` или статус») выполнен буквально: `Payment { kind: REFUND, reversalOfId: <id оплаты> @unique, method и amount — как у исходной, status: SUCCEEDED, reason, createdById, paidAt }`, исходная оплата не меняется. Новых статусов нет (миграции enum нет). Все нетто-суммы (`paidAmount`, LTV, «Выручка за месяц») учитывают сторно сами как возврат; валовые «получено/возвращено» отделяют пары по `reversalOfId` (запросы — ниже). Самоссылка `ON DELETE NO ACTION` — исходную оплату нельзя удалить отдельно от сторно; каскад брони и `cleanup` удаляют обе записи одним оператором.
2. Одна миграция `20260924090637_money_reason_reversal` (только добавляющие поля и индекс): `Payment.reason`, `Payment.reversalOfId` (+ unique, FK), `Booking.rejectClearedAt`. `checkedIn/OutDateOnly` уже были (Ф9а). `voidedAt/voidedById/voidReason` не нужны — у записи сторно свои `paidAt/createdById/reason`.
3. `src/server/lib/dates.ts` **не тронут** (общий файл 6 фаз): `actualParkingDays` прежний, `noonMoscow` не заведён — Ф9а уже хранит дату как `plannedMoment(date)` (12:00 МСК). `tests/unit/dates.test.ts` не менялся.

### Контракты соседям (точные имена)

- **Ф11:** `Payment.reason String?`; сторно — `Payment.reversalOfId String? @unique` (связи `reversalOf` / `reversal`), запись `kind = REFUND`, `status = SUCCEEDED`, `method` исходной оплаты. Единственный `tx.payment.create` — в `addPayment(input: PaymentInput, actor)` (`src/server/services/bookings/payments.ts`): оплата, возврат и сторно (`input.reversalOf`) идут через него, `reversePayment(paymentId, reason, actor)` — обёртка. `shiftForPayment(tx, { kind, method })` ставится прямо перед `tx.payment.create`. В снимке смены сторно наличной оплаты — это `REFUND CASH` с `reversalOfId != null`: показывать строкой «сторно», не «возврат наличными». **Решить в Ф11:** сторно оплаты из уже закрытой смены — запрещать или разрешать (сторно в новой смене уменьшит её расчётный остаток, хотя наличные в ящике не менялись). Путей удаления `Payment` нет.
- **Ф12:** сторно учитывается **в периоде самого сторно** (по `paidAt` записи сторно), чтобы закрытый период не менялся задним числом: «Получено» — все `kind: "PAYMENT", status: "SUCCEEDED"` за период (и те, что позже сторнированы); «Сторно» — `kind: "REFUND", status: "SUCCEEDED", reversalOfId: { not: null }` за период, вычитается из «Получено» (или строкой); «Возвращено» — `kind: "REFUND", status: "SUCCEEDED", reversalOfId: null`. Причина — `reason ?? note`. Отказы за период — по `rejectedAt` (при выходе из «Отклонена» не стирается); `rejectClearedAt` — когда бронь вышла из «Отклонена». **Повторное отклонение перезаписывает `rejectedAt/rejectKind`** (редкий случай: отказ → резерв → снова отказ).
- **Ф8:** «не смогли попасть и сейчас не у нас» — `rejectKind = NO_SPACE AND rejectClearedAt IS NULL`. «Когда-либо NO_SPACE» по текущей схеме **не надёжно**: повторное отклонение (сейчас ручное — всегда `OTHER`, после Ф5 — по выбору администратора) перезаписывает `rejectKind`. Если сегменту это нужно, неизменяемый признак (например, `Booking.noSpaceAt`, ставится при каждой записи `NO_SPACE`, не снимается) заводит фаза, добавляющая второй источник `NO_SPACE` (Ф5), вместе с `create.ts` (МФ-1) — в файлах Ф10 его ставить некуда.
- **Ф3:** в `correctStatus` проверки Ф10 стоят после `lockBooking` — `lockOccupancy` Ф3 ставит перед ним; в `addPayment` ветка автоподъёма получила только условие `b.amount > 0`.
- **Ф5/Ф6:** `changePrice`, `decideRecalc`, `waiveOverstay`, откат статуса после возврата/сторно автоматизации не вызывают.

### Вопросы пользователю (деньги, по PLAN §1/DECISIONS не решаются)

- **В8. Ступень тарифа при досрочном выезде.** Бронь от 30 суток дешевле за сутки (250 ₽ против 350 ₽). Если клиент уехал раньше и суток стало меньше 30, «посуточно по тарифу» выходит **дороже плана** (31 → 29 сут.: 10 150 ₽ вместо 7 750 ₽). Сейчас сделано: досрочный выезд не дороже плана (возврата нет, доплаты нет), ранний заезд не делает стоянку дешевле плана. Альтернатива — считать остаток по цене суток брони (250 ₽): 29 × 250 = 7 250 ₽, возврат 500 ₽. Рекомендация: оставить сделанное (клиенту не выставляется доплата за то, что уехал раньше), либо пропорционально, если заказчик хочет возврат и в этом случае.

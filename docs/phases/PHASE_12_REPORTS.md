# Ф12. Финансовый отчёт — архитектура

Дорожка Д5, после Ф11. Раздел ТЗ 5.1–5.2 (`docs/TZ_2026-09-21_SOURCE.md`), состав — `docs/TZ_STATUS_2026-09-22_night.md` §3 «Ф12». Решение пользователя 23.09 (PLAN §1, п. 7): **отчёт только по парковке, комнаты в него не входят**.

Документ пишется под код: другой агент должен собрать фазу, не задавая вопросов. Всё, чего нет ни в PLAN §1, ни в ТЗ, вынесено в §10 «Открытые вопросы».

## 1. Зачем

Владельцу нужен один экран, где за любой период видно: сколько машин заехало, сколько денег пришло и какими способами, сколько вернули и сколько за нами долга. Сейчас такого экрана нет вообще — есть только дашборд с одной плиткой «Выручка за месяц», которая считает месяц по UTC и молча складывает парковку с комнатами.

## 2. Что входит и что не входит

**Входит:**
- новый раздел `/admin/reports`: выбор периода, показатели, печать, выгрузка в CSV;
- сервис расчёта `src/server/services/reports.ts` — единственное место, где считаются деньги отчёта;
- помощник московских суток в `src/server/lib/dates.ts` (границы периода по Москве, а не по UTC);
- три добавляющих индекса в схеме;
- перевод денежных плиток дашборда на этот же сервис и этот же помощник (по §4 сверки `dashboard/page` — зона Ф12);
- пункт «Отчёты» в меню владельца;
- запись `EXPORT` в журнал при каждой выгрузке.

**Не входит (границы с соседями):**
- **Комнаты** — решение 23.09 п. 7. В отчёте остаётся одна сноска-сверка (см. §4.8), никакого раздела комнат.
- **Касса** (открытие, закрытие, инкассация, расхождение, формула) — Ф11. Отчёт только **читает** смены и показывает их списком.
- **Механика возвратов, сторно, причины, «Исправить статус»** — Ф10. Отчёт их только показывает.
- **Ручное время заезда и выезда** — Ф9а. Отчёт опирается на `checkedInAt`/`checkedOutAt` и верит им ровно настолько, насколько их починит Ф9а.
- **Табель и зарплата** — Ф13.
- **Ограничение CSV броней на доске (`BookingsTable`) и журнал по нему** — МФ-3б; свой CSV делаем здесь и сразу правильно, чужой не трогаем.
- **Графики и диаграммы** — нет. Плитки и таблицы: так отчёт печатается и читается с телефона.
- **PDF-генерация** — нет, печать средствами браузера (см. вопрос 7).
- **«Повторные клиенты»** из хвоста «дашборд §11» — нет: определения «повторный» нет ни в ТЗ, ни в решениях (см. вопрос 8). Конверсия по источникам и средний чек — входят, они считаются тем же запросом.

## 3. Определения (важно: эти слова потом стоят на экране)

| Слово на экране | Что это по коду | Чем не является |
|---|---|---|
| **Получено** | Σ `Payment.amount`, `kind = PAYMENT`, `status = SUCCEEDED`, `paidAt` в периоде, бронь `kind = PARKING` | Не стоимость услуг периода: сюда входит оплата броней прошлых месяцев |
| **Возвращено** | То же, `kind = REFUND` | — |
| **Чисто в кассу** | Получено − Возвращено | — |
| **Начислено** | Σ `Booking.amount` по броням парковки с `checkedInAt` в периоде | Не деньги: часть может быть не оплачена, часть оплачена в другом месяце |
| **Оплачено по этим броням** | Σ `Booking.paidAmount` по тем же броням | — |
| **Не оплачено (долг)** | Σ max(0, `amount` − `paidAmount`) по тем же броням | — |
| **Переплата** | Σ max(0, `paidAmount` − `amount`) по тем же броням | — |
| **Заехало машин** | Число броней парковки с `checkedInAt` в периоде | Не число уникальных машин: два заезда одной машины — это два заезда |
| **Всего заявок** | Число броней парковки с `createdAt` в периоде | — |
| **Отклонено** | Число броней парковки с `rejectedAt` в периоде | — |

Период задаётся **московскими календарными датами включительно**: «01.09 — 30.09» значит от 00:00 1 сентября по Москве до 00:00 1 октября по Москве.

## 4. Решения

### 4.1 Границы периода — по Москве, помощником, не по UTC

`paidAt`, `checkedInAt`, `checkedOutAt`, `createdAt`, `rejectedAt` — это моменты (UTC). Даты периода — московские сутки. Сравнивать их напрямую нельзя: 30 сентября 23:40 по Москве — это 30 сентября 20:40 UTC, а 1 октября 01:00 по Москве — уже 30 сентября 22:00 UTC. Фильтр по UTC-полуночи теряет вечер последнего дня и прихватывает ночь следующего.

Добавляем в `src/server/lib/dates.ts`:

```ts
// Смещение пояса на данный момент, в мс. Берём у Intl, а не у процесса: контейнер сейчас в UTC,
// TZ=Europe/Moscow появится только в МФ-3б, и отчёт не должен от этого зависеть.
function tzOffsetMs(at: Date, tz: string): number {
  const name = new Intl.DateTimeFormat("en-US", { timeZone: tz, timeZoneName: "longOffset" })
    .formatToParts(at).find((p) => p.type === "timeZoneName")?.value ?? "GMT";
  const m = /GMT([+-])(\d{2}):(\d{2})/.exec(name);
  return m ? (m[1] === "-" ? -1 : 1) * (+m[2] * 60 + +m[3]) * 60_000 : 0;
}

// Начало московских суток как момент UTC: "2026-09-01" → 2026-08-31T21:00:00.000Z
export function moscowDayStart(iso: string, tz = "Europe/Moscow"): Date {
  const guess = toDate(iso);
  const first = guess.getTime() - tzOffsetMs(guess, tz);
  // второй проход — страховка от пояса с переводом часов; в Москве перевода нет, значение не меняется
  return new Date(guess.getTime() - tzOffsetMs(new Date(first), tz));
}

// Полуинтервал для выборок по моменту: [начало from, начало дня после to)
export function moscowRange(fromIso: string, toIso: string): { gte: Date; lt: Date } {
  return { gte: moscowDayStart(fromIso), lt: moscowDayStart(addDays(toIso, 1)) };
}

// Первое число текущего месяца по Москве — период отчёта по умолчанию (ТЗ 5.1)
export function monthStartIso(today: string = todayIso()): string {
  return today.slice(0, 8) + "01";
}
```

**Почему так, а не иначе.** Отвергли: (а) вычитание фиксированных трёх часов — в коде уже принято не зашивать смещение числом (`plannedMoment`, комментарий `dates.ts:80`); (б) переиспользование `plannedMoment(date, "00:00")` — она в зоне Ф3 (сверка §3 «Ф3»: «`plannedMoment` зависит от пояса процесса»), и брать зависимость от чужой правки ради полуночи незачем; (в) `TZ=Europe/Moscow` в контейнере — это МФ-3б, последняя фаза, отчёт не может её ждать, и отчёт обязан считать одинаково при любом поясе процесса.

`dates.ts` общий с Ф3, но Ф3 правит `plannedMoment`, а мы **только дописываем три новые функции в конец файла**. Слияние механическое.

### 4.2 Две «выручки» показываем обе и называем разными словами

Заказчику нужны оба числа, и путать их нельзя. Решение: два отдельных блока с заголовками и одной строкой пояснения под каждым.

- **Блок «Деньги в кассу»** (по датам платежей) — Получено / Возвращено / Чисто. Подпись: «Деньги, пришедшие и ушедшие в этот период, включая оплату броней прошлых месяцев».
- **Блок «Начислено по заехавшим»** (по дате заезда) — Начислено / Оплачено / Не оплачено / Переплата / Средний чек. Подпись: «Стоимость стоянки машин, заехавших в этот период, включая ещё не оплаченное».

Слово «выручка» на экране не используем нигде — оно и есть источник путаницы.

**Якорь «начислено» — дата заезда (`checkedInAt`), а не выезда.** Так совпадают две строки отчёта: «заехало N машин» и «начислено по ним X ₽», и «средний чек» = X / N честный. Отвергли якорь по `checkedOutAt`: число заехавших ТЗ требует по заезду (5.2 п. 1), и два разных якоря в соседних строках читаются как ошибка. Отвергли якорь по `dateFrom` (плановая дата): бронь могла не состояться.

Следствие, которое пишем прямо на экране: у машин, которые ещё стоят, сумма может вырасти (перестой), поэтому **отчёт всегда «на момент формирования»** — время формирования по Москве печатается в шапке.

### 4.3 Долги и переплаты — два разных среза, подписаны по-разному

1. **За период** — по броням, заехавшим в периоде (в блоке «Начислено»), плюс список этих броней с долгом: № брони (ссылка), госномер, дата заезда, статус, сумма, оплачено, долг. Показываем до 50 строк, остальное — в выгрузке.
2. **На сегодня** — отдельный блок «Срез на сейчас, период не влияет»: сколько всего броней парковки в статусах «Заехал» и «Выехал» с `paidAmount < amount` и на какую сумму; отдельно — переплаты. Это ответ на вопрос «сколько нам должны прямо сейчас», который в отчёте за период не виден.

Долг и переплата считаются **построчно**, а не как разность двух сумм: иначе одна переплата гасит чужой долг и оба числа становятся ложью.

Чтобы не тащить тысячи строк, выбираем только неравные брони через сравнение полей одной модели (Prisma 6 это умеет, проверено на `@prisma/client` 6.19.3):

```ts
const debt = await prisma.booking.findMany({
  where: { kind: "PARKING", checkedInAt: at, paidAmount: { lt: prisma.booking.fields.amount } },
  select: { id: true, number: true, plate: true, status: true, checkedInAt: true, amount: true, paidAmount: true },
  orderBy: { checkedInAt: "asc" },
});
```

Сложение — чистой функцией из `src/lib/report-math.ts`, чтобы проверялось юнит-тестом без базы.

### 4.4 Способы оплаты — четыре строки и обязательная сверка

Таблица: строка на каждый способ (`CASH`, `CARD_TERMINAL`, `TRANSFER`, `ONLINE`, подписи из `METHOD_LABEL`), колонки «Получено», «Возвращено», «Чисто». Отсутствующие способы показываем нулями, а не прячем — пустая строка «Онлайн 0 ₽» честнее исчезнувшей.

Строка «Итого» обязана совпадать с плитками блока «Деньги в кассу» — это и есть требование ТЗ 5.2 «распределение оплат по способам». Числа берутся из одного `groupBy`, поэтому совпадают по построению; в тестах это всё равно проверяем.

Один запрос на всё:

```ts
prisma.payment.groupBy({
  by: ["kind", "method"],
  where: { status: "SUCCEEDED", paidAt: at, booking: { kind: "PARKING" } },
  _sum: { amount: true },
})
```

### 4.5 Заявки: всего, отклонённые, конверсия, источники

- **Всего заявок** — `createdAt` в периоде, `kind = PARKING`.
- **Отклонено** — `rejectedAt` в периоде; отдельной строкой «из них: нет мест» (`rejectKind = NO_SPACE`).
- **Отменено** — `cancelledAt` в периоде; **не приехал** — `noShowAt` в периоде.
- **Дошли до заезда** — из заявок периода те, у кого `checkedInAt != null` (когорта по созданию, а не по заезду — иначе процент считается от разных множеств).
- **Источники** — `groupBy(["source"])` по заявкам периода: заявок, доля, из них дошли до заезда, начислено.

**Честное предупреждение про отклонённые.** Сейчас подтверждение заявки из резерва стирает `rejectedAt` (`bookings/transition.ts:72-76`, `bookings/correct.ts:28`), поэтому отчёт за сентябрь, открытый в октябре, может показать меньше отклонённых, чем показывал вчера. Чинит это Ф10 (см. §8). Пока не починено — под числом стоит сноска «считается по текущим отметкам; заявка, подтверждённая позже из резерва, из числа уходит».

### 4.6 Смены за период — читаем у Ф11, делаем последним шагом

Блок «Смены за период»: таблица — администратор, открыта, закрыта, наличные за смену, расчётный остаток, фактический, расхождение, инкассации. Плюс строка сверки: **«Наличные по отчёту X ₽ · по снимкам смен Y ₽ · расхождение Z ₽»** — это то, ради чего заказчик вообще открывает отчёт после закрытия месяца.

Смена относится к периоду **по моменту открытия** (`openedAt`) в московских сутках — ночная смена целиком попадает в дату, когда её открыли (см. вопрос 6; это тот же вопрос 8 из §5 сверки, ответ нужен одинаковый Ф11, Ф12 и Ф13).

Блок пишется **отдельным, последним коммитом фазы**. Если на момент кода Ф11 ещё не в `main`, фаза сдаётся без него, а на месте блока стоит строка «Появится после кассы (Ф11)». Так Ф12 не блокируется чужим сроком.

### 4.7 Фуры

По ТЗ явного требования нет. Предлагаемое (вопрос 1): в блоке «Заехало машин» и в блоке «Начислено» — подстрока «в том числе фуры: N · X ₽». Разбивка берётся тем же `groupBy(["vehicleType"])`, лишних запросов нет. Деньги по способам по фурам отдельно не режем: у фуры цена «по запросу», отдельная колонка была бы почти всегда пустой.

### 4.8 Комнаты: не раздел, а одна сноска

Решение 23.09: комнаты в отчёт не входят. Но если из отчёта просто вычеркнуть комнаты, «наличные по отчёту» перестанут сходиться с кассой, где деньги общие. Поэтому внизу страницы — одна строка мелким шрифтом: «Комнаты в отчёт не входят. За период по комнатам получено X ₽, возвращено Y ₽». Ни таблиц, ни разбивок (вопрос 5).

### 4.9 Выгрузка и печать

**Выгрузка — серверная, не браузерная.** Отдельный обработчик `GET /admin/reports/export`, потому что: (а) числа считает тот же сервис, что и страница, второй реализации нет; (б) проверка роли на сервере; (в) каждую выгрузку пишем в журнал.

Три вида (`?kind=`):
- `summary` — свод: «Показатель;Значение», ровно то, что на экране;
- `payments` — платежи построчно: дата и время по Москве, вид (оплата/возврат), способ, сумма, № брони, кто провёл, причина (после Ф10 — из `Payment.reason`, до неё — из `note`);
- `debts` — брони периода с долгом и переплатой.

**Персональных данных в выгрузке нет**: ни телефонов, ни имён, ни госномеров в `payments`; идентификация — номер брони. В `debts` госномер оставляем (без него строка бесполезна для поиска машины), телефон — нет. Это снижает цену утечки файла и снимает половину разговора с юристом по 152-ФЗ.

Формат CSV — как в существующем экспорте броней (`BookingsTable.tsx:34-42`): разделитель `;`, BOM в начале, кавычки удваиваются. Деньги — целыми числами без пробелов-разделителей, иначе Excel читает их как текст.

**Печать** — средствами браузера: кнопка «Печать» (единственный клиентский компонент на странице) и блок `@media print` в конце `globals.css`, прячущий боковое меню, шапку и элементы с классом `no-print`.

### 4.10 Права

Страница — **только владелец** (`requireUser(["OWNER"])`), выгрузка — **только владелец** (`requireActor(OWNER)` + `audit(EXPORT)`). Охрана в группу `(app)` вообще не попадает (`layout.tsx` пускает `OWNER` и `ADMIN`), администратору отчёт за период не нужен: его отчёт — закрытие своей смены (ТЗ 7.5, Ф11). Вопрос 2 — на подтверждение.

### 4.11 Чего в фазе нет по правилам проекта

- **Выключателя в `Setting` нет и не нужно**: фаза не добавляет ни одного автоматического поведения — отчёт ничего не делает сам, только читает. Пункт меню и страница появляются сразу; выкатывать «выключенным» тут нечего. Это осознанное исключение, ревьюеру — сюда.
- **`lockBooking` не нужен**: фаза не меняет ни деньги, ни занятость. Ни одного `create`/`update` по `Booking` и `Payment` в коде фазы нет — кроме записи в `AuditLog` при выгрузке.
- **`userId = null`** не применяется: системных действий нет, выгрузку всегда делает живой владелец.
- **Сообщений клиенту фаза не отправляет**, `MESSAGE_TEMPLATES` не трогает.

## 5. Изменения схемы (только добавляющие, новых значений enum нет)

Одна миграция `*_report_indexes`, только `CREATE INDEX`:

```prisma
model Booking {
  // ...
  @@index([kind, createdAt])    // всего заявок за период, источники
  @@index([kind, checkedInAt])  // заехавшие, начислено, долг за период
  @@index([rejectedAt])         // отклонённые за период
}
```

`Payment @@index([kind, status, paidAt])` — **в зоне Ф11** (сверка §3 «Ф11»). Если к началу кода Ф12 он уже в схеме — не дублируем. Если Ф11 ещё не слита — Ф12 добавляет его сам в свою миграцию, а Ф11 из своей убирает; решает оркестратор при слиянии, двух одинаковых индексов быть не должно.

Новых значений enum нет, поэтому отдельной миграции под enum не требуется. Таблицы на stage маленькие (13 броней), `CREATE INDEX` без `CONCURRENTLY` безопасен; на бою к моменту переезда объём тоже небольшой.

### Наброски ключевых кусков

**Период из адресной строки** (`report-math.ts`) — нормализуем, а не падаем:

```ts
export const MAX_PERIOD_DAYS = 366;
export type Period = { from: string; to: string };
const ISO = /^\d{4}-\d{2}-\d{2}$/;

// По умолчанию — с 1-го числа текущего месяца по сегодня (ТЗ 5.1).
// Мусор в адресной строке не ломает страницу: молча берём период по умолчанию.
export function normalizePeriod(from: unknown, to: unknown, today: string, monthStart: string): Period & { error?: string } {
  const f = typeof from === "string" && ISO.test(from) ? from : monthStart;
  const t = typeof to === "string" && ISO.test(to) ? to : today;
  if (f > t) return { from: t, to: t, error: "Начало периода позже конца — показан один день" };
  if (daysBetweenIso(f, t) > MAX_PERIOD_DAYS) return { from: f, to: addDays(f, MAX_PERIOD_DAYS), error: `Период больше ${MAX_PERIOD_DAYS} дней — обрезан` };
  return { from: f, to: t };
}
```

## 8. Чего ждём от соседних фаз

**От Ф9а (честное время заезда):**
- `checkedInAt` и `checkedOutAt` ставит сервер в момент действия; ручного ввода нет. Отчёт якорится на `checkedInAt` и без этого показывает то, что администратор напечатал руками.
- Значение не в будущем и не раньше создания брони — иначе заезд попадает в чужой месяц.

**От Ф10 (возвраты, сторно, «Исправить статус»):**
1. **Отметки отклонения не стираются задним числом.** Нужно, чтобы «заявка была отклонена в периоде» оставалось правдой после подтверждения из резерва. Предлагаемый вид: `rejectedAt` и `rejectKind` **не обнуляются**, добавляется `rejectRevokedAt DateTime?`. Отчёт тогда считает `rejectedAt` в периоде, а «из них позже подтверждены» — по `rejectRevokedAt`. Любой другой стабильный признак тоже подойдёт — важно, чтобы он не менялся.
2. **`Payment.reason`** — отдельное поле причины возврата (сейчас причина в `note`). Отчёт кладёт его в колонку «Причина» построчной выгрузки.
3. **Признак сторно.** Ошибочный платёж должен отличаться от настоящего одним полем или статусом (например `status = FAILED` либо `reversalOfId`), чтобы отчёт его исключал. Без признака сторнированные деньги будут считаться дважды.
4. **Момент при «забытом заезде датой без времени»** (решение 23.09 п. 5) обязан попадать **в московские сутки указанной даты**, то есть в интервал [00:00 МСК, 24:00 МСК) этого дня. Рекомендуем 12:00 по Москве — тогда заезд встаёт в отчёт за правильный день при любом поясе процесса. Полночь по UTC (03:00 МСК) тоже годится, а вот «00:00 UTC минус смещение» — нет.

**От Ф11 (касса):**
1. Модель `CashShift` с полями: кто открыл (имя пользователя), `openedAt`, `closedAt`, остаток на начало, снимок по четырём способам, возвраты, инкассации, расчётный остаток, фактический, расхождение, статус.
2. Функция `shiftsInRange(from, to)` в `src/server/services/cash.ts`, принимающая **московские ISO-даты** и возвращающая смены периода по `openedAt`. Отчёт её только вызывает и ничего не считает сам.
3. Индекс `Payment(kind, status, paidAt)` — если Ф11 его не добавит, добавим мы (§5).
4. Ответ на «к какой дате относится ночная смена» — общий с Ф13 и с нами (вопрос 6).

**От Ф3 (занятость):** по §4 сверки Ф3 идёт раньше по `dashboard/page`; мы правим дашборд после неё и трогаем только денежные плитки. `plannedMoment` в `dates.ts` — её, мы дописываем рядом и не пересекаемся.

**От МФ-3б:** `TZ=Europe/Moscow` в контейнере. Отчёт от этого не зависит и не должен зависеть — после установки пояса числа обязаны остаться теми же (это отдельный критерий приёмки).

## 6. Бронирование и онлайн-оплата

### 6.1. Визард бронирования

1. Даты заезда/выезда (+ время) → 2. Тип ТС (легковая / кроссовер / грузовая / фура / мото …) → 3. Опции (трансфер, комната отдыха) → 4. Контакт: имя, телефон, гос. номер ТС, предпочтительный мессенджер → 5. Цена + условия отмены (явно, до оплаты) → 6. Онлайн-оплата → подтверждение с номером брони.

- Согласие на обработку ПД и принятие условий отмены — чекбоксы до оплаты (обязательное требование для удержаний при отмене).
- После оплаты: страница подтверждения + автосообщение в выбранный мессенджер (номер брони, схема проезда, телефон охраны).
- Бронь без оплаты (по звонку) администратор создаёт вручную в CRM — статус «не оплачена».

### 6.2. Платёжный модуль

- Провайдер: **ЮKassa** (основной кандидат: API возвратов, виджет, СБП, фискализация чеков по 54-ФЗ через их решение). Альтернативы при необходимости: CloudPayments, Т-Касса. Финальный выбор — по согласованию с заказчиком (у кого расчётный счёт).
- Оплата: банковская карта + СБП. Сумма — полная стоимость брони *(или предоплата за первые сутки — открытый вопрос №1)*.
- Чек клиенту по 54-ФЗ на email/телефон.
- Все платежи и возвраты пишутся в CRM в карточку брони (сумма, статус, ID транзакции).

### 6.3. Отмена и автоматический возврат (требование заказчика)

Правила отмены реализуются как **настраиваемая политика** в админке — заказчик сам сможет менять параметры без программиста:

| Сценарий | Действие системы |
|---|---|
| Отмена **более чем за 24 ч** до заезда | **Автоматический возврат 100%** через API платёжного провайдера, без участия администратора |
| Отмена **менее чем за 24 ч** | Возврат суммы **минус удержание 500 ₽** — или **полный возврат** (переключатель в настройках; заказчик ещё решает — см. открытый вопрос №2) |
| Неявка (no-show) | Настраивается: удержание первых суток / 500 ₽ / без удержания |

- Настраиваемые параметры политики: порог времени (24 ч), размер удержания (500 ₽ / 0 ₽ / %), правило no-show.
- Отмена клиентом: по ссылке из подтверждения (без личного кабинета в v1) — страница «Управление бронью» по номеру брони + телефону.
- Каждая отмена/возврат: событие в CRM + уведомление администратору + автосообщение клиенту («Бронь отменена, возврат N ₽ поступит в течение 3–5 дней»).
- Условия отмены обязательно показываются клиенту до оплаты и фиксируются в оферте (юридическое основание удержания).

## 8. CRM-система

### 8.1. Архитектурный ориентир — Monday.com

Из Monday.com берём модель, а не клон:
- **Доски (boards)** = направления: «Парковка», «Комнаты отдыха», позже «Передержка».
- **Карточка (item)** = бронь/заявка, движется по **конвейеру статусов**; представления: **канбан** (для админа) и **таблица** с фильтрами/сортировкой (для владельца), + календарь заездов.
- **Кастомные поля** по типам (дата, деньги, телефон, селект, источник) — набор полей отличается по доскам, добавление поля не требует программиста.
- **Лента активности** в карточке: все события (звонок с записью, сообщение, платёж, смена статуса, комментарий) в хронологии.
- **Автоматизации** по правилу «когда {триггер} → {действие}»: «бронь оплачена → отправить подтверждение», «до заезда 24 ч → напоминание», «до конца оплаченного срока 2 дня → предложить продление», «выезд + 7 дней → спасибо + скидка».

### 8.2. Конвейер статусов брони (v1)

`Новая заявка → Ожидает оплаты → Подтверждена (оплачена) → Заехал → Выехал` + ветки `Отменена (возврат)` / `No-show`.

### 8.3. Сущности данных (ядро схемы)

- **Client** — телефон (ключ дедупликации), имя, мессенджер, история броней, LTV, источник первого касания.
- **Vehicle** — гос. номер, тип ТС, привязан к клиенту.
- **Resource** — машиноместо / комната / место передержки: тип, зона, номер, статус.
- **Booking** — клиент + ТС + ресурс + даты + сумма + статус + источник (UTM) + платежи.
- **Payment / Refund** — транзакции провайдера, привязаны к брони.
- **Interaction** — звонок (с аудио), сообщение (канал), заявка с сайта; привязка к клиенту и брони.
- **Tariff / CancellationPolicy** — редактируются в админке.
- **Pet** *(фаза 2)* — кличка, вид, вес, прививки; привязан к клиенту.

### 8.4. Роли и доступ

| Роль | Доступ |
|---|---|
| Владелец | Всё: дашборд, выручка, экспорт базы (с логом), настройки тарифов и политики отмены |
| Администратор | Заявки, брони, клиенты, единое окно сообщений, ручное создание брони |
| Охрана | Только «кто заезжает/выезжает сегодня»: номер ТС, место, время — упрощённый мобильный экран |

2FA для владельца и администратора; журнал действий (кто смотрел/менял/выгружал карточку).

### 8.5. Занятость мест

Карта/сетка занятости: сколько мест свободно по типам ТС на дату; проверка при бронировании (овербукинг — предупреждение, но допускается вручную, т.к. стоянка большая). Точная схема стоянки с номерами мест — по данным аудита (этап 1).

## 9. Телефония (позиция 3 договора)

Принцип «пропущенных звонков не существует» — 4 рубежа (детально в WORK_PLAN_Parking.md):

1. **Многоканальный виртуальный номер** (облачная АТС: Mango/Zadarma/UIS — выбор по тарифам): «занято» не бывает, звонки становятся в очередь.
2. **IVR:** 1 — бронирование, 2 — цены, 3 — как проехать, 0 — администратор. Цены и маршрут робот озвучивает сам и дублирует ссылкой в мессенджер (~50% звонков не доходят до админа).
3. **Каскад переадресации:** админ не взял за 15 сек → охрана/резервный номер. Ночной режим: IVR отвечает сам, заявка в CRM в утренний список «перезвонить».
4. **Последний рубеж:** сорвавшийся звонок → автосообщение со ссылкой на бронь + задача «перезвонить» в CRM с дедлайном.

Каждый звонок = Interaction в CRM: номер, время, запись разговора, статус, привязка к клиенту (по номеру телефона автоматически).

## 10. Мессенджеры MAX / WhatsApp / Telegram (позиция 4 договора)

- **Каскад доставки** каждого автосообщения: MAX (приоритет, не блокируется в РФ) → WhatsApp → Telegram → SMS. Клиент получает только первый успешно доставленный канал; выбранный клиентом канал запоминается в CRM.
- **Автосообщения:** подтверждение брони (место, схема, телефон охраны), видео-маршрут + фото-путеводитель, напоминание за 24 ч, продление за 2 дня до конца срока, «спасибо + скидка» через 7 дней после выезда, уведомления об отмене/возврате.
- **Единое окно** в CRM: диалоги MAX + WA + TG + чат сайта в одном интерфейсе, привязка к карточке клиента, автоответы на типовые вопросы, ответ уходит в канал клиента автоматически.

## 11. Аналитика и клиентская база (позиция 5 договора)

- Автопривязка источника к каждой заявке: UTM с сайта; для звонков — подменные номера или ручная отметка админа (2ГИС / Instagram / реклама / визитка / рекомендация).
- **Дашборд владельца:** заявки и конверсия по источникам, загрузка стоянки по дням/типам ТС, выручка, средний чек, повторные клиенты, отменённые брони и суммы возвратов.
- Экспорт базы — только владелец, с записью в журнал.
- Сквозная логика: источник → заявка → оплата → повторные визиты (эффективность канала в деньгах, а не в кликах).

## 12. Техническая архитектура

- **Монорепо:** Next.js (App Router, TypeScript) — публичный сайт + CRM (закрытая зона `/admin`) в одном приложении; PostgreSQL; Prisma/Drizzle ORM; Tailwind (дизайн-токены общие для сайта и CRM).
- **API-слой отделён** (route handlers / tRPC): та же бизнес-логика позже обслуживает мобильное приложение.
- **Путь к приложению:** v1 сайт делается как **PWA** (манифест, иконка «на главный экран», офлайн-заглушка) — водитель ставит «приложение» без сторов; при развитии — React Native/Expo поверх того же API. Никаких решений, ломающих этот путь (логика — на сервере, не в вёрстке).
- Интеграции через адаптеры (payment provider, telephony provider, messenger provider) — провайдера можно заменить без переписывания ядра.
- Фоновые задачи (напоминания, каскад доставки, проверка возвратов): очередь (BullMQ/Redis или pg_cron — по простоте сопровождения).
- Безопасность: HTTPS, RLS/скоупы доступа, шифрование ПД (телефоны, гос. номера), rate-limit и антибот на формах, ежедневные бэкапы с проверкой восстановления, SSH-ключи, закрытый порт БД. Соответствие 152-ФЗ: согласия, политика, хранение в РФ (VPS2 — проверить юрисдикцию до боевого запуска; для stage не критично).

# Тесты Parking24

Страховка перед доработкой по ТЗ от 21.09 (`docs/TZ_2026-09-21_PLAN.md`, этап 0). Задача тестов — ловить поломки расчётов, конвейера статусов и денег при дальнейших правках.

## Быстрый запуск

```bash
npm test          # юнит-тесты, 2 секунды, база и сервер не нужны
npm run test:e2e  # сценарии в браузере против локального сервера на :3100
```

## Юнит-тесты — `tests/unit/`

Встроенный тест-раннер Node, отдельных зависимостей нет. Покрывают чистые расчёты, которые нельзя ломать:

- `periods.test.ts` — сутки парковки по датам включительно (правило 21.09), 24-часовые периоды комнат с льготой 60 минут;
- `dates.test.ts` — `bookingDays` по видам ресурса, фактические сутки по московскому времени, формат дат;
- `phone.test.ts` — нормализация телефонов и госномеров, дедупликация клиентов держится на ней;
- `render.test.ts` — подстановка переменных в шаблоны сообщений, боевые шаблоны из `prisma/templates.ts` без имени и ссылок;
- `scheduler.test.ts` — ядро минутного тика (Ф1): изоляция сканов, «занят», режимы «выкл / пробно / вкл», пауза, журнал ошибок, состояние карточки, проверка секрета.
- `overstay.test.ts` — перестой (Ф2а): сутки, тариф, ДОЛГ, начисление при выезде и продлении, занятость; СП: льготный час до 01:00 МСК, остаток начисления после снижения суммы владельцем (правило «выезд в перестое только текущими сутками» удалено в Ф9а — задать другую дату нечем);
- `correction.test.ts` — «Исправить статус» датой (Ф9а): какие даты спросить (`neededDates`), проверки дат — формат, не в будущем, выезд не раньше заезда, не раньше создания брони;
- `dates.test.ts` — ещё и фактические сутки с льготным часом после плановой даты выезда (СП);
- `refund.test.ts` — возврат (СП): у «Выехал» сначала переплата, остаток уменьшает сумму, у остальных сумма не меняется; предел администратора после выезда; перебором — «не оплачено» у «Выехал» не меняется.

## Сценарии в браузере — `tests/e2e/`

Playwright берётся из глобального `~/node_modules` (в проекте его нет специально, чтобы не тянуть браузеры в образ). Если не установлен: `npm i -g playwright && npx playwright install chromium`.

```bash
npx next dev -p 3100                                  # в отдельном окне
node tests/e2e/site-lead.mjs                          # заявка с сайта → CRM
node tests/e2e/crm-pipeline.mjs                       # оплата → заезд → выезд → «по факту» → возврат переплаты, отказы
node tests/e2e/autoconfirm.mjs --login owner --password owner12345   # автоподтверждение и автоотклонение
node tests/e2e/scheduler.mjs --login owner --password owner12345    # планировщик: вход по секрету, пульс, пауза
node tests/e2e/overstay.mjs --login owner --password owner12345     # перестой: занятость, ДОЛГ, начисление при выезде, «Продлить»
node tests/e2e/roles.mjs                                            # МФ-UI: роли driver/parker (сиды driver12345/parker12345), мобильное меню, «← CRM»; на stage пароли через E2E_DRIVER_PASSWORD/E2E_PARKER_PASSWORD/E2E_GUARD_PASSWORD/E2E_OWNER_PASSWORD
node tests/e2e/f9a-no-manual-time.mjs --login owner --password owner12345   # Ф9а: без ручного времени, «Исправить статус» датой; второй вход admin — на stage E2E_ADMIN_PASSWORD или --admin-password
node tests/e2e/site-lead.mjs --base https://parking24.168-231-118-173.sslip.io --password '<пароль admin>'
node tests/e2e/site-lead.mjs --headed                 # смотреть глазами
```

Параметры: `--base` (по умолчанию `http://localhost:3100`), `--login`, `--password`, `--headed`, `--secret` (секрет планировщика). Те же значения читаются из `E2E_BASE`, `E2E_LOGIN`, `E2E_PASSWORD`, `E2E_CRON_SECRET`; секрет без параметра берётся из `CRON_SECRET` локального `.env`.

На stage — только со stage-логинами (`--login admin --password <пароль admin>`, для автоподтверждения и планировщика — владелец) и, для планировщика, с секретом stage (`--secret`, лежит в `/opt/parking24/.env`).

**Что проверяет `site-lead.mjs`:** цена на калькуляторе по правилу «даты включительно» (3 суток = 1 050 ₽), экран «Заявка принята» с номером, заявка в CRM с именем и источником «Сайт», сообщение в очереди в выбранном клиентом мессенджере.

**Что проверяет `crm-pipeline.mjs`:** расчёт в быстрой заявке, полная оплата переводит бронь в «Подтверждена», «Заехал» и «Выехал» одним нажатием — поля времени нет, диалогов нет, время события серверное и стоит в строке ленты «Заехал → Выехал», после выезда в тот же день — баннер «Стоянка по факту» → «Пересчитать по факту» (350 ₽) → «Возврат» подставляет переплату 700, без причины кнопка недоступна, возврат 350 с причиной (сумма та же, «оплачено»), отказы сервера: 800 — «больше оплаченного», 400 — «только переплату»; в карточке клиента «К оплате» — «—». Входит администратором.

**Что проверяет `scheduler.mjs`:** запасной вход `POST /api/cron/automations` без секрета и с чужим — 404, `GET` не принимается, с секретом — результат тика; пять вызовов подряд без 500; карточка «Планировщик» в настройках показывает время последнего тика; пауза останавливает тик и снимается обратно (в `finally`). Требует входа владельцем.

**Что проверяет `autoconfirm.mjs`:** заявка подтверждается сама, когда места есть; следующая на те же даты отклоняется; администратор получает уведомление; с выключенной настройкой заявка снова ждёт администратора. Требует входа владельцем. Сценарий сам опускает порог до «занято в пуле на эти даты + 1» (по сетке `/admin/occupancy`: машины в перестое держат место и на дальние даты), берёт случайные дальние даты и возвращает настройки как были, в том числе при сбое.

**Что проверяет `overstay.mjs` (Ф2а):** легковая бронь на позавчера–вчера по Москве, оплачена и «Заехал» → плашка «ПЕРЕСТОЙ · 1 сут. · ДОЛГ 350 ₽» и строка долга в карточке, «занято бронями» +1, подписи на «Сегодня», у охраны и на доске; «Выехал» → 1 050 ₽, 3 сут., «не хватает 350 ₽», запись «Начислен перестой», без баннера «по факту»; исправление статуса назад и повторный выезд второй раз не начисляют; долг, принятый заранее, гасит строку; два одновременных «Выехал» из двух вкладок (нажаты разом, confirm в обеих) — одно начисление; «Продлить» до завтра — 1 400 ₽; «Исправить статус» в «Выехал» с датой выезда (сегодня) долг не начисляет и пишет в ленту «Исправление: … · выезд <дата>, без времени · причина» и «Перестой 1 сут. не начислен (350 ₽) · по дате выезда <дата> · причина». Ф9а: «Выехал» в перестое — одно нажатие после confirm «…ДОЛГ 1 сут. × 350 ₽ = 350 ₽. Отметить выезд?» (сценарий соглашается и считает диалоги), подсказки «текущими сутками» нет. СП: в перестое «Изменить бронь» не меняет дату выезда (поле недоступно, сервер отказывает и в обход формы), сумма в обход формы — отказ; после выезда «Снять начисление за перестой» с причиной (1 050 → 700 ₽); после «Продлить» уменьшить сумму в «Изменить бронь» нельзя; возврат владельца после выезда уменьшает сумму (1 050 → 700 ₽) и гасит начисление, которое можно снять. Не запускать с 00:00 до 01:00 МСК (льготный час — перестоя ещё нет). Требует входа владельцем.

**Что проверяет `f9a-no-manual-time.mjs` (Ф9а, `docs/phases/PHASE_09A_MANUAL_TIME.md`):** «Ожидает оплаты» → «Заехал» → «Выехал» в карточке — по одному нажатию, подсказка «Время события поставит система», в полосе этапов сегодняшняя дата и текущее московское время, диалогов нет; владелец возвращает закрытую бронь в «Заехал» без дат и снова закрывает датой — баннер «Стоянка по факту» от снятого выезда не всплывает; на доске перетаскивание в «Заехал» и «Выехал» без prompt и confirm, у владельца «Отменить» возвращает «Выехал» → «Заехал»; у администратора тост закрытого статуса без «Отменить» («вернуть может владелец — „Исправить статус“»), в закрытой брони серый текст вместо «Исправить статус»; «Исправить статус» → «Заехал»: поле «Дата заезда» (min — дата создания, max — сегодня), подпись «Время не ставим: в карточке будет только дата.», кнопка заблокирована без даты (красного текста у пустого поля нет), будущая дата и дата раньше создания брони — ошибка под полем и отказ сервера в обход формы; «Заехал» → «Выехал»: только «Дата выезда», вчерашняя при сегодняшнем заезде — «Выезд не может быть раньше заезда» (дата заезда из сохранённой отметки), успех — «<дата> · без времени» в полосе, шапка «Выехал <дата> · без времени (отмечено …)», строки «по факту N ч» и баннера нет, сумма и «оплачено» те же, одна запись в ленте и `STATUS_CHANGE` с признаком, причиной и датой в журнале; признак «без времени» не залипает (датой → «Подтверждена» → кнопкой — снова время); заезд датой + выезд кнопкой — баннер «Стоянка по факту: 1 сут. (по плану 3)» без часов и «по датам: 1 сут.»; «Ожидает оплаты» → «Выехал» спрашивает обе даты; перестой — confirm с суммой в карточке, на «Сегодня» и на доске (отказ ничего не меняет, согласие начисляет), исправление в «Выехал» (из «Заехал» и из «Подтверждена» двумя датами) — сумма та же, «Перестой 1 сут. не начислен (350 ₽) · по дате выезда <дата> · причина» одной строкой, экран охраны — одно нажатие без диалогов; поле `datetime-local` не появляется ни разу. Брони создаются сегодня, а дата исправления не бывает раньше создания брони: успешные исправления — сегодняшней датой, прошедшая дата в успешном пути — только в юните `correction.test.ts`. Входит владельцем, второй контекст — `admin` (`E2E_ADMIN_PASSWORD` или `--admin-password`, по умолчанию `admin12345`). Не запускать с 00:00 до 01:00 МСК.

### Подводные камни

- **Считать строки на странице — по `innerText`, не по `textContent`.** После полной загрузки страницы в `body` лежат скрипты Next с теми же данными, и `textContent` находит каждую строку ленты дважды.
- **Даты перестоя — `moscowPlus`, не `isoPlus`.** `isoPlus` считает по UTC и с 21:00 до 24:00 UTC отстаёт от Москвы на день.

- **Антибот.** `/api/public/lead` молча отвечает «ок» и не создаёт заявку, если форму отправили быстрее 1,5 секунды после загрузки. Сценарий выдерживает паузу; при отладке помнить об этом.
- **Быстрая заявка не открывает карточку** — после создания появляется тост «Заявка №N создана · открыть», сценарий переходит по этой ссылке.
- **Ручного времени нет (Ф9а).** «Заехал» и «Выехал» — одно нажатие, время ставит сервер. В перестое перед «Выехал» в CRM (не у охраны) — `window.confirm`: Playwright без обработчика `dialog` молча его отклоняет, и выезд не проходит — сценарии перестоя вешают обработчик и считают диалоги.
- **Гидратация кнопок.** Нажатие до гидратации молчит, а повтор может провести переход дважды. Новые сценарии ждут, пока у самого элемента появятся обработчики React (`__reactProps…`), и только потом нажимают.
- **Дата «Исправить статус» не раньше создания брони.** Брони e2e создаются сегодня — прошедшей датой исправить нельзя; отказы проверяются снятием `min`/`max` у поля.
- **Ограничение частоты.** Сайт принимает 8 заявок за 10 минут с одного адреса. Несколько прогонов подряд упираются в него, и сценарий скажет об этом прямо. Счётчик хранится в памяти процесса: перезапуск сервера его сбрасывает.
- **Планировщик локально выключен.** В `.env` `RUN_SCHEDULER=0`: таймера нет, тик дёргается только через `/api/cron/automations`, поэтому e2e детерминированы. Таймер в dev работает на коде, загруженном при старте сервера (`register()` после правок не перевызывается), а HTTP-вход — уже на новом коде: после правки скана перезапустить dev или звать тик через вход.
- **Гидратация.** Поля форм управляются React: если заполнить их сразу после загрузки страницы, значение откатится. Для ввода используется `fillReliably` из `lib.mjs`, который проверяет результат и повторяет.

## Тестовые данные

Сценарии создают брони с госномером `Т000…` и клиентов с телефоном `+7999…`. Эти признаки не пересекаются с реальными данными.

```bash
node tests/e2e/cleanup.mjs                                         # локально
docker exec -i parking24-db psql -U parking24 -d parking24 < tests/e2e/cleanup.sql   # на stage
```

**На stage чистить обязательно:** тестовые брони занимают места в сетке занятости и попадут в автоподтверждение и отчёты.

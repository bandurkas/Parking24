# Тесты Parking24

Страховка перед доработкой по ТЗ от 21.09 (`docs/TZ_2026-09-21_PLAN.md`, этап 0). Задача тестов — ловить поломки расчётов, конвейера статусов и денег при дальнейших правках.

## Быстрый запуск

```bash
npm test          # юнит-тесты, 2 секунды, база и сервер не нужны
npm run test:e2e  # сценарии в браузере против локального сервера на :3100
```

## Юнит-тесты — `tests/unit/`

Встроенный тест-раннер Node, отдельных зависимостей нет. Покрывают чистые расчёты, которые нельзя ломать:

- `periods.test.ts` — сутки парковки по датам включительно (правило 21.09), 24-часовые периоды комнат с льготой 60 минут;
- `dates.test.ts` — `bookingDays` по видам ресурса, фактические сутки по московскому времени, формат дат;
- `phone.test.ts` — нормализация телефонов и госномеров, дедупликация клиентов держится на ней;
- `render.test.ts` — подстановка переменных в шаблоны сообщений.

## Сценарии в браузере — `tests/e2e/`

Playwright берётся из глобального `~/node_modules` (в проекте его нет специально, чтобы не тянуть браузеры в образ). Если не установлен: `npm i -g playwright && npx playwright install chromium`.

```bash
npx next dev -p 3100                                  # в отдельном окне
node tests/e2e/site-lead.mjs                          # заявка с сайта → CRM
node tests/e2e/crm-pipeline.mjs                       # оплата → заезд → выезд → возврат
node tests/e2e/autoconfirm.mjs --login owner --password owner12345   # автоподтверждение и автоотклонение
node tests/e2e/site-lead.mjs --base https://parking24.168-231-118-173.sslip.io --password '<пароль admin>'
node tests/e2e/site-lead.mjs --headed                 # смотреть глазами
```

Параметры: `--base` (по умолчанию `http://localhost:3100`), `--login`, `--password`, `--headed`. Те же значения читаются из `E2E_BASE`, `E2E_LOGIN`, `E2E_PASSWORD`.

**Что проверяет `site-lead.mjs`:** цена на калькуляторе по правилу «даты включительно» (3 суток = 1 050 ₽), экран «Заявка принята» с номером, заявка в CRM с именем и источником «Сайт», сообщение в очереди в выбранном клиентом мессенджере.

**Что проверяет `crm-pipeline.mjs`:** расчёт в быстрой заявке, полная оплата переводит бронь в «Подтверждена», переходы «Заехал» и «Выехал» с фиксацией времени, возврат в платежах.

**Что проверяет `autoconfirm.mjs`:** заявка подтверждается сама, когда места есть; следующая на те же даты отклоняется; администратор получает уведомление; с выключенной настройкой заявка снова ждёт администратора. Требует входа владельцем. Сценарий сам опускает порог до 1 места, берёт случайные дальние даты и возвращает настройки как были, в том числе при сбое.

### Подводные камни

- **Антибот.** `/api/public/lead` молча отвечает «ок» и не создаёт заявку, если форму отправили быстрее 1,5 секунды после загрузки. Сценарий выдерживает паузу; при отладке помнить об этом.
- **Быстрая заявка не открывает карточку** — после создания появляется тост «Заявка №N создана · открыть», сценарий переходит по этой ссылке.
- **Ручной ввод времени.** По этапу 3 ТЗ поле фактического времени при «Заехал» и «Выехал» убирается. Сценарий работает в обоих случаях: если поле есть, подтверждает его, если нет — идёт дальше.
- **Ограничение частоты.** Сайт принимает 8 заявок за 10 минут с одного адреса. Несколько прогонов подряд упираются в него, и сценарий скажет об этом прямо. Счётчик хранится в памяти процесса: перезапуск сервера его сбрасывает.
- **Гидратация.** Поля форм управляются React: если заполнить их сразу после загрузки страницы, значение откатится. Для ввода используется `fillReliably` из `lib.mjs`, который проверяет результат и повторяет.

## Тестовые данные

Сценарии создают брони с госномером `Т000…` и клиентов с телефоном `+7999…`. Эти признаки не пересекаются с реальными данными.

```bash
node tests/e2e/cleanup.mjs                                         # локально
docker exec -i parking24-db psql -U parking24 -d parking24 < tests/e2e/cleanup.sql   # на stage
```

**На stage чистить обязательно:** тестовые брони занимают места в сетке занятости и попадут в автоподтверждение и отчёты.
